# 11.2 — Documentation Structure and Organization

## Purpose

Establish a consistent directory structure and organizational system for the application's documentation, research records and development history.

The structure should make information easy to locate, maintain and reference while accommodating the application's growth.

It must support both human contributors and AI development partners, preserve authoritative document locations and avoid unnecessary duplication.

## 11.2.1 Documentation Directory

**Core requirements**

- Maintain a dedicated central documentation directory named `docs/` in the project repository.
- Organize documentation into clearly identifiable categories.
- Keep important project-wide documents in predictable locations.
- Use subdirectories where they improve organization and retrieval.
- Avoid excessive directory nesting or unnecessarily complicated structures.
- Allow the documentation system to expand as the application develops.
- Maintain a central documentation index identifying important documents and their purposes.

**Proposed structure**

```text
project/
│
├── docs/
│   │
│   ├── README.md
│   ├── MASTER_DEVELOPMENT_ROADMAP.md
│   │
│   ├── requirements/
│   │
│   ├── science/
│   │
│   ├── architecture/
│   │
│   ├── technical/
│   │
│   ├── development/
│   │   ├── DEVELOPMENT_LOG.md
│   │   ├── decisions/
│   │   ├── problems/
│   │   ├── test_reports/
│   │   ├── research_reviews/
│   │   ├── handoffs/
│   │   └── improvements/
│   │
│   ├── resources/
│   │
│   └── templates/
│
├── application/
│
├── tests/
│
└── other project files...
```

This is a proposed organizational foundation, not a requirement to use these exact source-code directories or a finalized application architecture.

The actual project structure should be evaluated during technical planning. Documentation categories may be adjusted when practical needs become clearer.

## 11.2.2 Documentation Categories

The documentation system should organize information according to its purpose.

**Requirements**

- Overall application vision and purpose.
- Scientific scope and disciplines.
- Functional requirements.
- User experience and design requirements.
- Community and collaboration requirements.
- Platform and technical requirements.
- AI development partner responsibilities.

**Scientific knowledge**

- Scientific principles and research findings.
- Mathematical and physical foundations.
- Scientific methods and analytical procedures.
- Observational techniques and instrumentation.
- Scientific limitations and unresolved questions.
- Supporting literature and references.

**Architecture**

- System architecture and component responsibilities.
- Data models and relationships.
- Internal interfaces and communication.
- Shared services and dependencies.
- Architectural decisions and diagrams.
- Technical constraints and future considerations.

**Technical research**

- Technology and framework evaluations.
- Library and dependency investigations.
- Database and external service research.
- Platform compatibility findings.
- Integration feasibility and limitations.
- Technical recommendations and alternatives.

**Development records**

- Chronological development history.
- Decisions and approvals.
- Problem investigations.
- Test reports.
- Scientific and technological review records.
- Session handoffs.
- Improvement proposals and tracking.

**Resources**

- External scientific databases and archives.
- Scientific software and libraries.
- Documentation and reference links.
- Research source catalogues.
- Relevant technical resources.

**Templates**

- Standardized formats for recurring documentation.
- Problem records.
- Decision records.
- Test reports.
- Research reviews.
- Handoff summaries.
- Other recurring development records.

## 11.2.3 Canonical Document Locations

Important documents must have clearly established locations.

**Core requirements**

- Maintain one authoritative location for each major document or record.
- Do not create competing copies of authoritative documents.
- Use links or references when information is relevant to multiple documentation categories.
- Preserve established file locations unless there is a practical reason to change them.
- Update references and indexes when documents are moved or renamed.

**Established locations**

| Document | Canonical location |
|---|---|
| Documentation index | `docs/README.md` |
| Master Development Roadmap | `docs/MASTER_DEVELOPMENT_ROADMAP.md` |
| Rolling Development Record | `docs/development/DEVELOPMENT_LOG.md` |
| Decision records | `docs/development/decisions/` |
| Problem records | `docs/development/problems/` |
| Test reports | `docs/development/test_reports/` |
| Scientific and technological reviews | `docs/development/research_reviews/` |
| Session handoffs | `docs/development/handoffs/` |
| Improvement records | `docs/development/improvements/` |
| Documentation templates | `docs/templates/` |

These locations establish a recommended documentation structure. The Master Development Roadmap location is already mandatory under Section 10.3; the other locations establish the proposed organization for Section 11.

## 11.2.4 File Naming and Identification

**Core requirements**

- Use descriptive filenames that communicate document purpose.
- Prefer consistent naming conventions.
- Use Markdown (`.md`) for ordinary text-based project documentation where appropriate.
- Use clear identifiers for individual records.
- Include dates in chronological records where useful.
- Avoid ambiguous names such as `notes2`, `final_new` or `latest_version`.
- Avoid creating multiple files that appear to be competing authoritative versions.
- Preserve established filenames when updating existing documents unless renaming is justified.

**Design guidance**

Examples:

- `MASTER_DEVELOPMENT_ROADMAP.md`
- `DEVELOPMENT_LOG.md`
- `DEC-001-database-selection.md`
- `PROB-001-data-import-failure.md`
- `TEST-001-data-import.md`
- `REVIEW-001-spectroscopy-methods.md`

Record identifiers should remain unique and understandable.

The exact identifier format may be refined as the documentation system is implemented.

## 11.2.5 Document Structure and Internal Organization

**Core requirements**

- Use consistent heading hierarchies.
- Include a clear title and purpose for substantial documents.
- Organize long documents into numbered sections or meaningful headings.
- Use tables where they improve comparison or retrieval.
- Use lists for requirements, procedures and checklists.
- Include relevant references and cross-links.
- Identify document status where appropriate, such as Draft, Under Review, Approved or Superseded.
- Include creation or revision dates when they provide useful historical context.
- Keep documents understandable without requiring the reader to reconstruct their original conversation.

**Design guidance**

Documents should contain enough context to explain their purpose and meaning without repeating extensive information already maintained elsewhere.

## 11.2.6 Documentation Index and Navigation

**Core requirements**

- Maintain a central documentation index.
- Identify major documents, their locations and their purposes.
- Organize links by documentation category.
- Identify important authoritative records, including the Master Development Roadmap.
- Update the index when significant documents are created, renamed, moved or retired.
- Make it possible to locate relevant documentation without knowing its exact filename.
- Maintain links between related requirements, architecture, development records and technical findings.

**Future possibilities**

- Automatically generated documentation indexes.
- Search across documentation and development records.
- Automated checks for broken links or missing references.
- Documentation relationship maps.

## 11.2.7 Separation of Project Documentation and Application Data

**Core requirements**

- Keep development documentation separate from the application's runtime scientific data and user research materials.
- Do not treat the `docs/` directory as a storage location for ordinary user projects, observations or large scientific datasets.
- Keep credentials, API keys, private user information and sensitive research materials out of public or version-controlled documentation.
- Store application configuration and user data according to the relevant storage and security requirements.
- Document relevant data-storage locations and procedures without exposing sensitive contents.
- Preserve the distinction between internal development knowledge and user-facing educational content.

**Design guidance**

The documentation repository may describe how the application manages scientific data, but it should not become an informal substitute for the application's actual data-management system.

## General Principles

- Maintain one central documentation directory.
- Organize records by purpose and responsibility.
- Keep authoritative documents in predictable locations.
- Use descriptive filenames and consistent identifiers.
- Maintain a central index.
- Link related records instead of duplicating information.
- Keep development documentation separate from runtime scientific data.
- Allow the structure to expand without unnecessary complexity.

**General principle:** Documentation should be easy to locate, understand and maintain. Its organization should support reliable development and long-term knowledge preservation without becoming a project of its own.
