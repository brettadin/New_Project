# 11.3 — Authoritative Records and Sources of Truth

## Purpose

Establish clear authority and ownership for the application's documentation and development records.

The project must have identifiable sources of truth for its requirements, architecture, scientific knowledge, development status, decisions, implementation and verification.

When multiple documents discuss related information, the system must make clear which record is authoritative and how other documents should reference it.

## 11.3.1 Authoritative Documentation

**Core requirements**

- Designate authoritative documents for major categories of project information.
- Maintain one authoritative source for each established requirement, decision, development status or record.
- Avoid competing documents containing conflicting versions of the same information.
- Allow other documents to summarize or reference authoritative information without independently redefining it.
- Preserve historical versions and significant changes where necessary.
- Identify outdated, superseded or incomplete documentation.
- Ensure authoritative records reflect approved decisions rather than unapproved suggestions.

**Design guidance**

A document does not become authoritative simply because it is newer or contains more detail.

Its authority must be established by its designated purpose and relationship to the project's documentation system.

## 11.3.2 Requirements and Application Vision

**Authoritative source:** The approved application requirements and vision documentation.

**Core requirements**

- Maintain the approved overall application vision, purpose and scientific scope.
- Preserve functional requirements and design principles.
- Identify approved requirements separately from proposals and future possibilities.
- Record significant changes to established requirements.
- Ensure implementation and development planning remain consistent with approved requirements.
- Identify conflicts between requirements rather than silently choosing one interpretation.

The requirements documentation establishes what the application is intended to become.

The Master Development Roadmap establishes how development is organized and tracked.

## 11.3.3 Development Status and Priorities

**Authoritative source:** `docs/MASTER_DEVELOPMENT_ROADMAP.md`

**Core requirements**

- The Master Development Roadmap is the single authoritative overview of development status and priorities.
- Use it to determine planned, approved, active, completed, deferred, cancelled and blocked work.
- Maintain dependencies, milestones, risks and outstanding work.
- Reflect verified implementation and testing status.
- Update the roadmap when development status or priorities change.
- Other documents may reference roadmap information but must not maintain competing development-status summaries.

Detailed implementation history belongs in the rolling development record and relevant technical documentation.

## 11.3.4 Architecture and Technical Decisions

**Authoritative sources:** Approved architecture documentation and consequential decision records.

**Core requirements**

- Maintain authoritative descriptions of system architecture, component responsibilities, data relationships, interfaces and dependencies.
- Record consequential technical and architectural decisions.
- Distinguish current architecture from proposed or superseded designs.
- Document the reasoning and alternatives behind significant decisions.
- Update architecture documentation when approved changes alter the actual system.
- Identify discrepancies between documented architecture and implementation.

Architecture documentation describes the current intended technical structure. Decision records explain why significant choices were made.

## 11.3.5 Scientific Knowledge and Research Findings

**Authoritative sources:** Scientific research documentation, designated knowledge records and referenced external scientific sources.

**Core requirements**

- Preserve scientific findings, methods, equations, assumptions, limitations and supporting references.
- Distinguish established scientific knowledge from hypotheses, interpretations, experimental methods and unresolved questions.
- Identify original sources wherever practical.
- Preserve the date and context of research when relevant.
- Reassess information when new scientific evidence or developments make it necessary.
- Avoid treating internal AI-generated explanations or research notes as independently verified scientific facts.
- Keep scientific knowledge used for development distinguishable from approved user-facing educational content.

Scientific knowledge records should explain what is understood and the evidence supporting it, while external sources remain identifiable and inspectable.

## 11.3.6 Implementation and Codebase State

**Authoritative source:** The actual current codebase and its associated configuration, dependency and implementation files.

**Core requirements**

- Treat the current implementation as the authority on what code and functionality actually exist.
- Do not assume documentation or previous conversations accurately reflect implementation without checking.
- Use version control history to investigate significant changes where available.
- Keep implementation documentation synchronized with actual code.
- Identify incomplete, experimental, temporary or placeholder functionality.
- Document discrepancies between intended requirements and implemented behavior.
- Never report functionality as implemented solely because it appears in a plan or document.

The codebase establishes what currently exists. Requirements and architecture documentation establish what it is intended to do and how it should be organized.

## 11.3.7 Testing and Verification Records

**Authoritative sources:** Individual test reports and relevant scientific validation records.

**Core requirements**

- Preserve detailed test results in designated test reports.
- Record what was tested, how it was tested and the exact outcome.
- Distinguish passed, failed, skipped and unexecuted tests.
- Preserve relevant evidence, commands, environments and limitations.
- Distinguish software testing, functional verification, scientific verification and scientific validation.
- Do not treat successful test execution as proof of scientific validity.
- Update development status only to the level supported by actual verification.
- Reference authoritative test reports from the roadmap and rolling development record.

A summary in another document must not replace the detailed test evidence.

## 11.3.8 Decisions, Problems and Development History

**Authoritative sources:**

- Consequential decision records.
- Individual problem records.
- Rolling development record.

**Core requirements**

- Decision records establish the outcome and reasoning of consequential decisions.
- Problem records preserve individual investigations, attempted solutions, findings and resolutions.
- The rolling development record maintains chronological context across development sessions.
- Preserve relationships between these records and affected requirements, architecture, implementation and roadmap entries.
- Distinguish resolved problems from ongoing or deferred investigations.
- Preserve unsuccessful approaches where they provide useful historical knowledge.
- Avoid duplicating detailed records in the roadmap or other documents.

Each record type must have a clearly defined purpose and authority.

## 11.3.9 Conflicting, Outdated and Superseded Information

**Core requirements**

- Identify conflicting information between documents and records.
- Investigate which source is authoritative before changing or relying on conflicting information.
- Consider document purpose, approval status, revision history and supporting evidence.
- Do not silently resolve consequential conflicts through assumptions.
- Correct outdated information when appropriate.
- Preserve historical records when they explain previous decisions or development states.
- Clearly identify superseded documents and provide references to their replacements.
- Record significant corrections and changes where traceability matters.

When the correct interpretation is uncertain and materially affects development, the AI must investigate or request clarification rather than inventing a resolution.

## 11.3.10 Authority and Change Control

**Core requirements**

- The user retains final authority over application direction and consequential project decisions.
- Approved requirements and decisions must be followed unless formally reconsidered.
- AI recommendations do not become requirements without approval where approval is required.
- Changes to authoritative records must reflect actual decisions, evidence or verified developments.
- Significant changes must preserve their reasoning, date and relevant history.
- The AI must not silently rewrite established requirements or reinterpret user decisions.
- When a decision is reconsidered, preserve the original decision and document the revised outcome.
- Update affected documentation and cross-references when authoritative information changes.

**Design guidance**

Authority and change control should protect continuity without making routine documentation updates unnecessarily difficult.

## General Principles

- Every major category of project information must have a clear authoritative source.
- The roadmap is the authority for overall development status.
- Requirements documentation is the authority for approved application requirements.
- Architecture documentation describes the intended technical structure.
- The actual codebase establishes what has been implemented.
- Test reports preserve verification evidence.
- Decision and problem records preserve their respective histories.
- Scientific knowledge must remain traceable to supporting evidence.
- Conflicts and outdated information must be handled transparently.
- Historical context must be preserved when authoritative information changes.

**General principle:** Anyone continuing development should be able to determine what is required, what has been decided, what currently exists, what has been verified and which records provide the evidence, without encountering competing or ambiguous sources of truth.
