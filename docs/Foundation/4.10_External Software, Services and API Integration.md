

# 4.10 — External Software, Services and API Integration

## Purpose

The application should support integration with relevant external scientific software, services, APIs and computational resources where doing so provides meaningful research capabilities.

Astronomical research frequently involves specialized software, online services, scientific databases, computational tools and established research platforms. Requiring every capability to be developed internally would be impractical and could unnecessarily duplicate existing scientific work.

The application should therefore accommodate appropriate external integrations while maintaining a coherent user experience, preserving scientific data relationships and making the role of external tools understandable.

Integrations should be evaluated according to their scientific value, reliability, compatibility, maintainability and relevance to the application's overall purpose.

## 4.10.1 External Integration Framework

### Core Requirements

- Support integration with relevant external scientific software, services and computational resources.
- Accommodate different integration approaches according to the capabilities of each external resource.
- Support both online services and locally installed scientific software where appropriate.
- Allow external tools to contribute to scientific workflows without requiring the entire application to depend on them.
- Preserve the distinction between native application capabilities and externally provided functionality.
- Maintain clear relationships between the application and integrated external resources.
- Allow integrations to be introduced, updated, replaced or discontinued without unnecessarily disrupting unrelated application functionality.
- Avoid requiring integrations that provide little meaningful value or duplicate existing capabilities without justification.
- Support future integration opportunities as scientific requirements evolve.

### Design Guidance

External integration should extend the application's capabilities rather than turn it into a collection of unrelated software launchers.

An integrated external tool should have a clearly defined purpose and relationship to the surrounding research workflow.

The application should remain useful when individual integrations are unavailable or have not been configured.

## 4.10.2 External Scientific Software

### Core Requirements

Support integration with relevant scientific software where it provides capabilities that are useful to astronomical research.

Potential categories include:

- Spectroscopic analysis and modelling software.
- Photometric and time-series analysis tools.
- Astronomical image-processing software.
- Orbital and dynamical modelling tools.
- Atmospheric and planetary modelling software.
- Numerical and scientific computing libraries.
- Statistical analysis and visualization tools.
- Specialized observational data-processing software.
- Established astronomical research packages.

Allow the application to make use of suitable external software through supported interfaces or workflows.

Distinguish between software that is directly integrated, software that can be launched or invoked externally and software that is merely recommended as an independent resource.

Preserve information about the external software involved in relevant scientific operations.

### Design Guidance

The application should not attempt to reproduce every established scientific capability internally.

Where a mature external package provides a specialized method, integration may be more appropriate than developing a competing implementation.

However, external software should be evaluated for scientific suitability, documentation, licensing, compatibility, maintenance and practical usability before being incorporated into research workflows.

## 4.10.3 API and Web-Service Integration

### Core Requirements

- Support appropriate APIs and web services provided by scientific archives, databases, research institutions and other relevant organizations.
- Accommodate different API conventions and communication methods.
- Support retrieval of structured scientific information where available.
- Support submission of supported queries and requests.
- Preserve relevant request and response information where necessary for traceability.
- Handle incomplete responses, service errors and communication failures.
- Identify unsupported operations and unavailable service functionality.
- Avoid assuming that all external resources provide equivalent API capabilities.
- Allow integrations to adapt when external services change their interfaces.
- Avoid requiring direct user interaction with technical API details for routine supported workflows.

### Design Guidance

External services may provide different levels of functionality.

One resource may support searching, metadata inspection and dataset retrieval, while another may provide only catalogue queries or limited reference information.

The application should reflect the capabilities of each integration rather than presenting every external service as though it supports the same operations.

## 4.10.4 Data Exchange and Interoperability

### Core Requirements

- Support appropriate exchange of scientific data between the application and external tools.
- Preserve relevant data structures, metadata, units, conventions and source information during exchange.
- Support established scientific data formats and standards where appropriate.
- Identify when external tools require data conversion or restructuring.
- Distinguish lossless transformations from transformations that may discard or alter information.
- Preserve original data when preparing external-tool inputs.
- Identify outputs produced by external software.
- Maintain relationships between original inputs, external processing operations and resulting outputs.
- Support returning external results to appropriate scientific workspaces and research projects.
- Identify when data cannot be transferred without losing important scientific information.

### Design Guidance

Data exchange should not be treated as a simple file-transfer operation.

Scientific data may contain metadata, coordinate systems, measurement conventions, uncertainty information and specialized structures that are essential to interpretation.

The application should preserve these characteristics wherever possible and communicate when an external tool cannot accommodate them.

## 4.10.5 External Processing and Computational Operations

### Core Requirements

- Support appropriate use of external software and computational resources for scientific operations.
- Allow compatible datasets and configurations to be supplied to external processing tools.
- Identify the external software and relevant processing method used.
- Preserve relevant input information and operation parameters.
- Capture or import resulting outputs where supported.
- Maintain relationships between external processing inputs and outputs.
- Identify when processing is incomplete or unsuccessful.
- Communicate relevant external-tool warnings and errors.
- Allow users to inspect externally produced results before incorporating them into research.
- Avoid silently treating external results as validated scientific conclusions.

### Design Guidance

Some scientific operations may be performed more effectively by specialized external software.

For example, an external modelling package may perform a computationally intensive calculation while the application provides the surrounding research context, input management and result inspection.

The application should make clear which operations were performed internally and which were delegated to external tools.

Scientific interpretation and validation remain subject to the requirements established in Section 5.

## 4.10.6 Local Software and Environment Detection

### Core Requirements

- Support identifying relevant locally installed scientific software where practical.
- Determine whether required external tools are available before attempting to use them.
- Identify relevant software versions and dependencies where accessible.
- Communicate when an integration requires software that is not installed or configured.
- Allow users to configure supported external software locations or execution settings where appropriate.
- Avoid assuming that all users have the same external software installed.
- Identify compatibility problems between external software and the application.
- Allow supported integrations to be disabled or reconfigured.
- Avoid modifying user-installed software or system environments without authorization.

### Design Guidance

Some scientific integrations may depend on software installed on the user's computer rather than an online service.

The application should make these dependencies understandable and avoid failing unexpectedly when required software is unavailable.

Detection and configuration should remain proportionate to the complexity of the integration.

## 4.10.7 Integration Configuration and User Control

### Core Requirements

- Allow users to configure supported external integrations where necessary.
- Make integration status understandable.
- Identify whether an integration is available, configured, unavailable, disabled or experiencing errors.
- Allow users to enable or disable optional integrations.
- Preserve appropriate integration preferences between sessions.
- Support configuration of relevant connection and execution parameters.
- Clearly identify when an operation will use an external service or application.
- Require appropriate user authorization before operations that involve external accounts, restricted resources or consequential external actions.
- Avoid silently changing external integration settings.
- Provide a means to review and revise integration configurations.

### Design Guidance

External integrations should remain understandable and manageable.

Users should know when an external tool or service is involved and what role it plays in a scientific operation.

Configuration complexity should depend on the integration. Routine services should not require users to manage unnecessary technical details, while advanced users should retain appropriate control over specialized tools.

## 4.10.8 External Dependencies and Compatibility

### Core Requirements

- Identify dependencies required by supported integrations.
- Evaluate compatibility with the application's supported operating environments.
- Identify relevant software and service version requirements.
- Communicate when an external dependency is missing, outdated or incompatible.
- Avoid allowing optional integrations to compromise unrelated application functionality.
- Support appropriate handling of integration failures.
- Maintain awareness of external dependencies that may become unavailable or unsupported.
- Document significant compatibility limitations.
- Avoid silently replacing one external tool or version with another when this could change scientific behavior.
- Preserve information about relevant dependencies used in scientific operations.

### Design Guidance

External integrations introduce dependencies that may change independently of the application.

A software update, API revision or discontinued package may affect an existing workflow.

The application should make these dependencies visible enough to support maintenance and reproducibility without requiring users to manage every technical detail themselves.

## 4.10.9 Integration Errors and Failure Handling

### Core Requirements

- Distinguish integration failures from unrelated application errors.
- Communicate useful information about unsuccessful external operations.
- Identify relevant causes where possible, such as missing software, incompatible versions, unavailable services, invalid requests or failed data exchange.
- Preserve user work when an external operation fails.
- Avoid treating partial or unsuccessful external results as complete outputs.
- Support retrying operations where appropriate.
- Allow users to inspect relevant warnings and error information.
- Identify when a failure may have affected the resulting data.
- Avoid silently switching to an alternative external tool or service when this could change the scientific method or result.
- Preserve relevant failure information when it affects research continuity.

### Design Guidance

External tools and services may fail for reasons outside the application's control.

The application should communicate what happened without unnecessarily exposing users to technical implementation details.

When an alternative integration is available, it may be presented as an option, but the application should not silently change the scientific method or source of a result.

## 4.10.10 External Tool and Service Attribution

### Core Requirements

- Identify external software and services involved in scientific operations.
- Preserve relevant software names, versions and provider information.
- Retain available references to scientific methods, documentation and associated publications.
- Record relevant external processing information where necessary for reproducibility.
- Preserve attribution requirements associated with external tools and services.
- Distinguish externally produced results from results generated by native application capabilities.
- Maintain relevant integration information when research materials are transferred or exported.
- Avoid presenting external capabilities or outputs as though they were developed or independently validated by the application.

### Design Guidance

External software may contribute directly to scientific results.

Users should be able to identify which tools and methods were involved, particularly when reproducing or reporting research.

Attribution should reflect the actual role of external software and services rather than treating all integrations as interchangeable dependencies.

## 4.10.11 Integration Maintenance and Lifecycle

### Core Requirements

- Maintain awareness of changes affecting supported integrations.
- Identify when external APIs, software packages or services become outdated or unsupported.
- Evaluate the impact of external changes on existing functionality.
- Support updating or replacing integrations where appropriate.
- Preserve relevant configuration and historical records when integrations change.
- Communicate when an integration is temporarily unavailable or permanently discontinued.
- Avoid silently changing the external tool or service used by an existing research workflow.
- Support disabling or retiring integrations that are no longer reliable or maintainable.
- Preserve access to previously generated research outputs when an integration is discontinued.
- Coordinate integration maintenance with the broader resource evaluation requirements in Section 4.12.

### Design Guidance

Integrations should be treated as maintained components of the research environment rather than permanent connections that can be assumed to work indefinitely.

External software and services may change their interfaces, discontinue support or become unsuitable for particular research activities.

The application should be able to respond to these changes without unnecessarily disrupting existing projects or invalidating historical research.

## General Principles

External software, services and API integration should:

- Extend the application's scientific capabilities where justified.
- Support appropriate external scientific software and computational resources.
- Accommodate different APIs and service capabilities.
- Preserve scientific data structures and metadata during exchange.
- Maintain traceable relationships between external processing inputs and outputs.
- Make external dependencies and integration status understandable.
- Provide appropriate user control over integration configuration and execution.
- Handle external failures without compromising unrelated application functionality.
- Preserve attribution and relevant processing information.
- Remain maintainable as external software and services evolve.
- Avoid unnecessary dependencies and duplicated functionality.
- Keep external integrations subordinate to the application's overall scientific purpose.

## General Principle

External software and services should strengthen the application's scientific capabilities without compromising its independence, reliability or coherence.

Integrations should be selected and maintained because they provide meaningful research value, with their roles, dependencies and limitations remaining transparent to users.

## Implementation Boundary

This subsection establishes requirements for external scientific software, APIs, services, computational integrations, data exchange and integration lifecycle management.

It does not prescribe specific APIs, programming languages, software packages, integration frameworks, dependency managers or implementation technologies.

Scientific data discovery and retrieval are addressed in Sections 4.1–4.5. Data lineage and provenance are addressed in Sections 4.6 and 4.7. External resource quality and availability are addressed in Section 4.8. Access, licensing, privacy and authentication are addressed in Section 4.11. Broader resource evaluation and expansion are addressed in Section 4.12. Platform architecture and computational infrastructure are addressed in Section 9.
