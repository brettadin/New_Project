

# 5.2 — Automation Levels and User Control

## Purpose

The application should provide flexible automation that accommodates different user experience levels, research requirements and working preferences.

Some users may prefer to perform every operation manually, while others may benefit from guided assistance or more extensive automation of routine scientific workflows.

Automation should therefore be configurable rather than imposed as a universal application behavior.

The application should establish four consistent automation levels:

1. Manual.
2. Guided.
3. Balanced.
4. Advanced automation.

These levels should determine how the application assists with scientific operations, processes data, recommends actions and requests user approval.

Automation must remain transparent and scientifically appropriate. Increasing the level of automation should not remove the ability to inspect relevant operations, understand their consequences or maintain control over consequential scientific decisions.

## 5.2.1 Four-Level Automation Framework

### Core Requirements

- Provide four clearly defined automation levels across the application:
  - **Manual:** The user controls and performs operations directly.
  - **Guided:** The application provides structured assistance and recommendations while the user directs the workflow.
  - **Balanced:** The application automates appropriate routine operations while requesting user input for consequential decisions.
  - **Advanced automation:** The application can execute more extensive compatible workflows with reduced routine intervention while preserving appropriate safeguards and user oversight.
- Maintain consistent definitions of these levels across scientific workspaces and application capabilities.
- Make the active automation level visible and understandable.
- Allow users to change automation levels without losing research progress.
- Ensure automation behavior remains appropriate to the scientific operation being performed.
- Do not assume that every operation supports all four levels.
- Identify when an operation requires manual input or approval regardless of the selected level.
- Avoid interpreting advanced automation as unrestricted or unsupervised scientific authority.

### Design Guidance

The four levels should represent progressively greater delegation of routine operations to the application.

They should not represent different standards of scientific accuracy or reliability.

All four levels must follow the same scientific integrity, data preservation and validation requirements established throughout Section 5.

## 5.2.2 Manual Mode

### Core Requirements

- Allow users to perform scientific operations directly.
- Require explicit user initiation of individual operations.
- Avoid automatically applying optional processing, analytical methods or configuration changes.
- Provide access to available tools and their relevant parameters.
- Allow users to inspect and configure operations before execution.
- Preserve user control over data selection, processing choices and analytical procedures.
- Provide appropriate warnings when an operation may be scientifically unsuitable or could affect existing research materials.
- Allow users to inspect results before deciding how to proceed.

### Design Guidance

Manual mode should provide the greatest direct user control.

The application may still provide essential information, error messages, compatibility checks and safety warnings.

Manual mode does not mean that the application must withhold useful information or allow scientifically invalid operations without warning.

It means that the user remains responsible for initiating and directing the workflow rather than delegating routine decisions to automation.

## 5.2.3 Guided Mode

### Core Requirements

- Provide structured assistance throughout supported scientific workflows.
- Suggest appropriate next steps based on the current task and available information.
- Explain relevant operations, parameters and methodological considerations.
- Allow users to review recommended actions before proceeding.
- Provide contextual guidance when required information is missing or ambiguous.
- Help users identify potential compatibility problems and unsuitable operations.
- Allow users to accept, modify or reject recommendations.
- Preserve user control over consequential processing and analytical decisions.
- Avoid executing significant operations without appropriate user authorization.
- Provide explanations suitable for users with different levels of scientific and technical experience.

### Design Guidance

Guided mode should help users understand and complete scientific tasks without taking control away from them.

For example, when preparing a spectral dataset, the application may identify its measurement columns, suggest a wavelength unit and recommend an appropriate normalization method.

The user should be able to review these recommendations and decide whether they are suitable.

Guided mode should make scientific workflows more approachable while preserving meaningful user participation.

## 5.2.4 Balanced Mode

### Core Requirements

- Automate appropriate routine operations within supported workflows.
- Allow users to establish general preferences for commonly repeated tasks.
- Automatically perform compatible operations when their requirements and parameters are sufficiently established.
- Request user input when important information is missing, ambiguous or uncertain.
- Request approval before consequential scientific decisions or operations.
- Identify which operations are being performed automatically.
- Communicate significant warnings, errors and unexpected results.
- Allow users to inspect automated operations and their outcomes.
- Preserve the ability to modify configurations and repeat operations.
- Avoid automatically accepting scientifically questionable results.

### Design Guidance

Balanced mode should provide practical automation while maintaining meaningful oversight.

For example, the application may automatically identify a recognized data format, inspect metadata, prepare a compatible visualization and perform routine validation.

However, if the dataset contains ambiguous units or requires a consequential methodological choice, the application should request user input rather than silently making an unsupported assumption.

This should be the default automation level unless a different default is established through the application's broader user-experience requirements.

## 5.2.5 Advanced Automation Mode

### Core Requirements

- Support more extensive automation of compatible scientific workflows.
- Allow users to configure and execute multi-step operations with reduced routine intervention.
- Support automated selection and execution of appropriate operations within established constraints.
- Allow users to establish permitted methods, parameters and processing preferences.
- Support background execution of suitable operations.
- Identify important assumptions and decisions made during automated workflows.
- Preserve records of operations, configurations, inputs and outputs.
- Communicate significant warnings, failures and unexpected conditions.
- Pause or request user intervention when an operation exceeds its authorized scope or encounters an unresolved consequential decision.
- Allow users to inspect, review and reproduce automated workflows.
- Preserve user control over destructive, externally consequential or otherwise restricted operations.
- Avoid treating advanced automation as permission to make unsupported scientific conclusions.

### Design Guidance

Advanced automation should reduce repetitive work and support complex workflows without making their behavior opaque.

For example, a user may configure an automated workflow to retrieve compatible observations, prepare datasets, apply established processing configurations, generate visualizations and produce preliminary analytical outputs.

The application should preserve a record of what was performed and identify where user intervention or further scientific validation remains necessary.

Advanced automation should be particularly useful for repeated procedures, batch operations and multi-step research activities.

## 5.2.6 Global and Context-Specific Automation Preferences

### Core Requirements

- Allow users to establish a global default automation level.
- Preserve global automation preferences between sessions.
- Allow appropriate overrides for individual workspaces, projects, workflows or tasks.
- Make active automation settings and overrides visible.
- Define how conflicting automation preferences are resolved.
- Ensure project-specific requirements are not silently overridden by global defaults.
- Allow users to restore their preferred settings.
- Preserve relevant automation configurations with associated research activities.
- Support different automation levels for different operations when appropriate.
- Avoid requiring users to repeatedly configure the same preferences.

### Design Guidance

Automation preferences should be flexible enough to accommodate different research activities.

For example, a user may prefer Balanced mode for routine observational data preparation, Guided mode when learning a new analytical method and Advanced automation for a previously established batch workflow.

The application should support these differences without creating confusing or conflicting settings.

This should remain consistent with the global, workspace-specific and project-specific preference hierarchy established in Section 6.8.

## 5.2.7 Operation-Specific Automation Compatibility

### Core Requirements

- Identify which automation levels are supported by individual operations.
- Determine whether an operation can be automated reliably with the available information.
- Identify when an operation requires user input, confirmation or manual configuration.
- Prevent automation from bypassing essential scientific requirements.
- Distinguish operations that can be fully automated from those that require scientific judgment.
- Communicate when a selected automation level cannot be applied to a particular operation.
- Allow the application to use a more restrictive execution approach when necessary.
- Avoid implying that all scientific operations can or should be automated.
- Preserve consistent scientific safeguards regardless of the selected level.

### Design Guidance

Automation suitability depends on the operation, available data and scientific context.

Some tasks, such as recognized file-format inspection or routine unit conversion, may be suitable for extensive automation.

Other tasks, such as selecting an appropriate physical model or interpreting an ambiguous spectral feature, may require user judgment or additional scientific evaluation.

The application should determine automation compatibility according to the operation rather than assuming that a user's global preference applies without qualification.

## 5.2.8 User Approval and Consequential Decisions

### Core Requirements

- Identify operations that require explicit user approval.
- Distinguish routine automated actions from consequential scientific or administrative decisions.
- Request appropriate approval before:
  - Overwriting or deleting original scientific data.
  - Permanently removing retained research resources.
  - Applying irreversible or destructive transformations.
  - Changing significant analytical assumptions or methodologies.
  - Replacing established configurations in ways that may affect results.
  - Sharing private research materials externally.
  - Submitting data to external services when authorization is required.
  - Performing operations with financial, subscription or other external consequences.
- Communicate the purpose and potential consequences of operations requiring approval.
- Allow users to approve, reject or modify proposed actions where appropriate.
- Preserve relevant approval and execution records.
- Avoid treating the selection of Advanced automation as blanket authorization for every possible operation.

### Design Guidance

Automation should operate within clearly defined boundaries.

A user may authorize extensive routine processing without authorizing the application to overwrite original observations, publish research or transmit private datasets to external services.

The application should distinguish permission to automate a workflow from permission to perform consequential actions.

## 5.2.9 Automated Recommendations and Decision Transparency

### Core Requirements

- Identify when the application recommends an operation or methodological choice.
- Distinguish recommendations from automatically executed actions.
- Explain relevant reasons and assumptions behind significant recommendations where practical.
- Identify when recommendations are based on incomplete or uncertain information.
- Allow users to inspect and modify recommendations before application.
- Avoid presenting recommendations as mandatory unless a genuine technical or scientific requirement exists.
- Communicate when an alternative method may be appropriate.
- Preserve relevant information about significant automated decisions.
- Avoid silently changing scientific methods or parameters through recommendation systems.

### Design Guidance

Recommendations should help users make informed decisions rather than create the impression that the application always knows the correct scientific approach.

For example, the application may recommend a particular fitting method based on the characteristics of a dataset while identifying alternative approaches and relevant assumptions.

The user should be able to understand why the recommendation was made and whether it is appropriate for the research objective.

## 5.2.10 Automation Monitoring and Intervention

### Core Requirements

- Provide appropriate visibility into ongoing automated operations.
- Identify active tasks, progress and relevant execution states.
- Communicate when an operation requires user input or approval.
- Allow users to pause, cancel or stop supported operations.
- Preserve completed work when an operation is interrupted where practical.
- Distinguish successful completion from partial completion or failure.
- Communicate unexpected conditions and significant warnings.
- Avoid continuing operations when essential scientific requirements are no longer satisfied.
- Support appropriate recovery or continuation of interrupted workflows.
- Preserve relevant execution records.

### Design Guidance

Users should not have to guess what the application is doing during an automated workflow.

Automation should remain observable and interruptible where appropriate, particularly when operations involve large datasets, multiple processing stages or significant computational resources.

## 5.2.11 Automation History and Reproducibility

### Core Requirements

- Record significant automated operations.
- Identify the automation level active when an operation was performed.
- Preserve relevant inputs, configurations, parameters and outputs.
- Record significant automated decisions and user approvals.
- Identify where manual intervention occurred within an automated workflow.
- Preserve the sequence of operations in multi-step workflows.
- Allow users to inspect relevant automation history.
- Support reproduction of automated workflows when the necessary resources remain available.
- Distinguish automated operations from manual actions in research records.
- Coordinate detailed automation records with Section 5.5.

### Design Guidance

Automation should not make research less reproducible.

Users should be able to determine which operations were automated, which decisions were made by the application and which actions required their intervention.

The resulting records should provide enough information to understand and, where practical, repeat the workflow.

## 5.2.12 Automation Errors and Scientific Safeguards

### Core Requirements

- Apply appropriate scientific validation to automated operations.
- Identify when automated processing produces incomplete, invalid or unexpected results.
- Avoid treating successful execution as evidence of scientific validity.
- Communicate errors and limitations that affect automated outputs.
- Prevent automation from silently continuing through conditions that invalidate essential assumptions.
- Allow users to inspect problematic operations and their inputs.
- Preserve previous valid results when subsequent automated operations fail.
- Support appropriate recovery and correction.
- Apply the scientific integrity requirements established in Section 5.1 to every automation level.
- Coordinate validation and quality-control requirements with Section 5.6.

### Design Guidance

Automation can execute operations consistently, but it cannot guarantee that the selected method or resulting interpretation is scientifically appropriate.

The application should identify conditions that require review and avoid allowing automation to turn uncertain or invalid inputs into apparently authoritative results.

## 5.2.13 Automation Preferences and Accessibility

### Core Requirements

- Make automation settings understandable to users with different levels of technical experience.
- Explain the practical differences between the four automation levels.
- Provide accessible controls for selecting and modifying automation preferences.
- Avoid requiring users to understand internal technical implementation details.
- Allow users to change automation levels without losing progress.
- Provide suitable defaults for common research activities.
- Avoid making advanced automation the only efficient way to use the application.
- Support users who prefer direct manual control.
- Coordinate automation preferences with the customization and user-preference requirements in Section 6.8.

### Design Guidance

Automation should make the application more accessible rather than creating a new barrier for users who are unfamiliar with scientific software.

The four levels should communicate practical differences in user involvement and application behavior, not technical complexity or user competence.

## General Principles

Automation and user control should:

- Provide four consistent automation levels: Manual, Guided, Balanced and Advanced automation.
- Allow users to establish global preferences and appropriate contextual overrides.
- Adapt automation to the scientific suitability of individual operations.
- Preserve user control over consequential decisions.
- Make automated operations and recommendations understandable.
- Communicate when user input or approval is required.
- Allow appropriate monitoring and intervention during automated workflows.
- Preserve research progress and execution history.
- Maintain scientific integrity at every automation level.
- Avoid interpreting advanced automation as unrestricted authority.
- Support different working preferences without imposing a single workflow on all users.

## General Principle

Automation should reduce unnecessary effort while preserving scientific judgment, transparency and user authority.

The application should allow users to delegate appropriate tasks without losing the ability to understand, inspect and control the scientific work being performed.

## Implementation Boundary

This subsection establishes the four automation levels, user-control requirements, approval boundaries and general expectations for automated scientific workflows.

It does not prescribe specific automation engines, scheduling systems, workflow frameworks, AI models or implementation technologies.

Scientific integrity requirements are established in Section 5.1. Data processing safeguards are addressed in Section 5.3. Scientific interpretation and uncertainty are addressed in Section 5.4. Automation records and reproducibility are addressed in Section 5.5. Validation and quality control are addressed in Section 5.6. AI-assisted scientific analysis is addressed in Section 5.7. Global and context-specific automation preferences are coordinated with Section 6.8.
