# Section 6.7 — Scientific Data Presentation and Interaction

This section establishes how scientific data should be displayed, explored, inspected and interacted with throughout the application.

Section 3 established the scientific capabilities and visualization requirements. Section 4 addressed data discovery, retrieval and integration. Section 6.5 established the visual design principles.

Section 6.7 focuses on the actual user experience of working with scientific data: how users see it, explore it, compare it, select it, manipulate its presentation and understand the information being displayed.

The application should provide a flexible scientific presentation environment that accommodates different data types, disciplines, analytical requirements and levels of user experience.

## 6.7.1 — Scientific Data Presentation Principles

Scientific information should be accurate, sufficiently detailed and adaptable to different levels of user experience.

### Core requirements

- Present scientific data with appropriate labels, units, scales and context.
- Preserve scientific precision and avoid misleading visual representations.
- Make uncertainties, missing values, data-quality issues and relevant limitations visible.
- Distinguish observations, processed measurements, derived results, model predictions and simulated data.
- Allow users to inspect underlying numerical values rather than relying exclusively on visual interpretation.
- Support different presentation formats according to the scientific data type.
- Maintain appropriate scientific context when presenting data independently or alongside other datasets.
- Avoid forcing different scientific disciplines or data types into identical presentation formats.

Examples of appropriate scientific presentation include:

- Spectra communicating wavelength, intensity or flux, units, resolution and relevant observational context.
- Light curves communicating time, brightness or flux, uncertainties and relevant event markers.
- Tables preserving scientific precision and providing meaningful units and metadata.
- Model outputs that are clearly distinguishable from actual observations.

### Presentation levels

The application should support different levels of scientific presentation:

1. **Simplified:** Important information presented clearly for quick interpretation and general understanding.
2. **Detailed:** More comprehensive scientific information, measurements, metadata and relevant context.
3. **Advanced:** Extensive technical details, diagnostics, analytical information and additional presentation controls.

These levels should change how information is presented, not unnecessarily restrict access to scientific functionality.

### Design principle

Scientific presentation should accommodate different levels of experience without compromising accuracy, detail or transparency.

## 6.7.2 — Interactive Data Exploration

Scientific visualizations should function as interactive research tools rather than static outputs.

### Core requirements

- Allow users to zoom into specific regions of graphs and visualizations.
- Support panning across datasets and adjusting visible ranges.
- Allow users to inspect numerical values and relevant metadata by interacting with data points.
- Support selection of individual measurements, spectral features, events and regions.
- Highlight selected data and connect selections to relevant scientific information.
- Allow users to adjust axes, scales, units and displayed ranges.
- Allow individual datasets, series, markers and overlays to be shown or hidden.
- Support selecting regions of interest for further analysis.
- Preserve connections between selected visual elements and their underlying datasets.
- Support interactive exploration without modifying original scientific data.

### Linked Visualizations and Cross-Component Interaction

Where scientifically and technically appropriate, different visualizations and data presentation components should be interconnected.

Examples include:

- Selecting an absorption feature in a spectrum highlights its wavelength in related graphs.
- Selecting a measurement in a graph identifies the corresponding entry in a data table.
- Selecting a spectral feature can display matching molecular or atomic reference information.
- Selecting an event in a light curve can highlight its corresponding position in an orbital visualization.
- Changing a dataset selection can update related graphs, tables and analytical displays.
- Selecting an object or observation can reveal associated measurements, metadata and research information.

These interactions should preserve the relationships between the underlying datasets and their representations.

### Future possibilities

- More advanced multidimensional data exploration.
- Interactive filtering and selection of large datasets.
- Configurable interaction tools for different scientific workspaces.
- More extensive linked interactions between analytical components.
- User-configurable relationships between visualizations.

### Design principle

Scientific visualizations should allow users to investigate data and move naturally between related measurements, representations and scientific information.

## 6.7.3 — Graphs, Charts and Scientific Visualizations

The application should provide a comprehensive graphing and visualization environment, building upon the shared scientific visualization capabilities established in Section 3.10.

### Core requirements

- Support a broad range of scientific graph types, not just basic line graphs.
- Provide specialized graphing capabilities for spectroscopy, photometry, time series, modelling and statistical analysis.
- Allow multiple datasets to be plotted together.
- Support linear, logarithmic and other scientifically appropriate axis scales.
- Provide configurable axes, units, legends, markers, labels and annotations.
- Display uncertainty information, error bars and confidence intervals where applicable.
- Allow users to customize graph appearance without changing the underlying scientific data.
- Support 2D and 3D visualizations where scientifically useful.
- Ensure graphs remain readable when displaying large or complex datasets.
- Allow users to export graphs in suitable scientific and publication-quality formats.

### Graph Appearance and Customization

Users should have substantial control over how their graphs look and present information.

Customization should include:

- Line colours and styles.
- Data-point markers, shapes and sizes.
- Axis labels, formatting, ranges and scales.
- Grid visibility and appearance.
- Legend placement and formatting.
- Font sizes and text presentation.
- Backgrounds and graph presentation colours.
- Annotation styles and placement.
- Error bars and uncertainty presentation.
- Individual dataset and series appearance.

The application should provide sensible default styles while allowing users to depart from them according to their preferences and scientific or publication requirements.

Customization must not compromise scientific accuracy or make important information misleading.

### Future possibilities

- Advanced graph templates and reusable presentation presets.
- Publication-specific formatting presets.
- Custom graph themes and palettes.
- More extensive 3D and multidimensional visualization controls.
- User-created visualization configurations.

### Design principle

Provide good default scientific visualizations while allowing users to customize their presentation extensively without changing the underlying data or its scientific meaning.

## 6.7.4 — Tables and Structured Data Presentation

Scientific work involves substantial amounts of numerical and structured information. Tables should therefore be flexible, configurable and suitable for working with scientific datasets.

### Core requirements

- Provide configurable tables for displaying scientific measurements and structured datasets.
- Support sorting and filtering of columns.
- Display appropriate scientific units and numerical precision.
- Support large datasets without making tables unusable.
- Allow users to select, highlight and inspect individual entries.
- Provide controls for column visibility and ordering.
- Apply appropriate formatting for different scientific data types.
- Provide access to associated metadata and provenance.
- Allow tables to be exported into suitable scientific formats.
- Connect table selections to corresponding graphs and visualizations where appropriate.

### Table Customization

Users should have substantial control over how scientific information is organized and displayed.

Customization should include:

- Selecting which columns are visible.
- Rearranging column order.
- Adjusting column widths.
- Changing numerical precision and display formatting.
- Applying filters and sorting criteria.
- Choosing how missing or unavailable values are represented.
- Adjusting row density and table appearance.
- Saving preferred table configurations.
- Restoring default table arrangements.

Customization should affect presentation rather than silently modifying underlying scientific values.

### Future possibilities

- Reusable table templates and presets.
- Advanced filtering and conditional highlighting.
- More extensive table-to-graph interactions.
- Custom column calculations and derived-value displays.
- User-defined table configurations for different scientific workspaces.

### Design principle

Tables should be flexible scientific tools that users can adapt to their investigations, rather than rigid displays with permanently fixed columns and formatting.

## 6.7.5 — Multi-Dataset Comparison and Overlay

The application should support comparing multiple scientific datasets wherever scientifically appropriate.

This is particularly important in astronomy, where comparing observations, models, reference spectra and measurements is a major part of scientific investigation.

### Core requirements

- Allow multiple datasets to be displayed together where scientifically appropriate.
- Provide controls for enabling, disabling and identifying individual datasets.
- Make differences between observations, models and reference data visually distinguishable.
- Support comparison of datasets with different instruments, observation dates or sources.
- Identify relevant compatibility issues such as units, wavelength coverage, resolution and calibration.
- Allow users to adjust individual dataset appearances.
- Preserve the identity and provenance of each dataset.
- Avoid silently applying transformations simply to make datasets appear compatible.
- Provide appropriate tools for direct and normalized comparisons where scientifically valid.

### Comparison Presentation Modes

The application should support multiple ways of presenting comparisons, with users able to switch between them as needed.

1. **Combined overlay:** Display multiple datasets on the same graph, allowing direct visual comparison.
2. **Side-by-side:** Display datasets in separate panels, making individual characteristics easier to inspect.
3. **Synchronized panels:** Separate visualizations that share relevant axes, ranges, zooming or selection interactions.
4. **Flexible arrangements:** Where practical, allow users to choose how many datasets appear together and how they are arranged.

Switching presentation modes should preserve relevant dataset selections and visualization configurations wherever possible.

### Future possibilities

- Advanced comparison layouts.
- Difference and residual plots.
- Statistical comparison tools.
- Automated identification of potentially significant differences.
- Reusable comparison configurations.

### Important considerations

- Different datasets may require unit conversion, wavelength alignment, resolution matching or other scientifically justified preparation before direct comparison.
- Any transformations should be explicit, traceable and appropriately controlled.
- Visual similarity should not be mistaken for scientific equivalence.
- The application should communicate when datasets are not directly comparable.

### Design principle

Users should be able to compare scientific data in whichever presentation arrangement best supports their investigation, without losing scientific context or control.

## 6.7.6 — Data Selection, Inspection and Interaction

Users should be able to interact with individual measurements and portions of datasets beyond simply viewing them.

### Core requirements

- Allow users to select individual data points, rows, regions and scientific features.
- Provide detailed information associated with selected measurements.
- Identify the original dataset and relevant metadata behind displayed measurements.
- Support selecting multiple points or regions for comparison or further analysis.
- Allow interactive filtering of datasets.
- Highlight selected or excluded measurements without deleting them.
- Provide clear visual distinctions between selected, unselected, flagged and excluded data.
- Allow selections to be passed into relevant scientific tools and workflows.
- Preserve selection information where it contributes to analysis reproducibility.

### Cross-Tool Data Selection

Users should be able to select portions of scientific datasets directly from graphs, tables and other visualizations and pass those selections into relevant tools.

Examples include:

- Selecting a wavelength range from a spectrum and sending it to a spectral analysis tool.
- Selecting an absorption feature for molecular or atomic identification.
- Selecting a transit event from a light curve for further examination.
- Selecting particular measurements from a table for statistical analysis.
- Selecting regions of interest from an observation for modelling or comparison.

Selections should retain their relationship to the original dataset and relevant metadata.

### Future possibilities

- More advanced multi-region selection.
- Reusable selection configurations.
- Saving and revisiting frequently used regions of interest.
- More sophisticated selection and filtering tools.
- Linking selections across multiple datasets and visualizations.

### Important considerations

- Selecting or excluding data for an analysis must not delete or silently modify the original observations.
- Users should be able to inspect which measurements are included or excluded from a particular operation.
- Selection-dependent analytical results should record the relevant selections where necessary for reproducibility.
- The application should distinguish temporary visual selections from deliberate analytical exclusions.

### Design principle

Users should be able to move naturally from inspecting scientific data to investigating selected portions of it, without losing the connection to the original observations.

## 6.7.7 — Scientific Annotations and Visual Markers

Users should be able to add annotations throughout the application's scientific visualizations, allowing them to identify important information and record their observations and interpretations.

### Core requirements

- Allow users to add notes and annotations to graphs and scientific visualizations.
- Support marking important measurements, spectral features, events and regions.
- Allow labels, reference markers and explanatory text to be added.
- Distinguish user-created annotations from automatically generated scientific markers.
- Associate annotations with relevant datasets, analyses and research projects.
- Preserve annotations when saving and reopening visualizations.
- Allow annotations to be edited, hidden or removed without changing underlying scientific data.
- Support annotations identifying uncertainty, possible features or areas requiring further investigation.

### Contextual Research Annotations

Annotations should support more than visual identification. Users should be able to attach meaningful research information to individual features or measurements.

This may include:

- Explanatory notes and observations.
- Scientific references and literature citations.
- Hypotheses or possible interpretations.
- Questions requiring further investigation.
- Reasons for marking or excluding particular measurements.
- Links to related datasets, analyses or scientific resources.
- Relevant uncertainties or limitations.

### Future possibilities

- More advanced annotation categories and organization.
- Shared annotations for collaborative research.
- Annotation templates.
- Searching and filtering annotations across projects.
- Linking annotations between related datasets and visualizations.

### Important considerations

- Annotations must remain distinguishable from actual observational measurements.
- User interpretations and hypotheses must not be presented as established scientific findings.
- Annotations should retain their association with the relevant dataset and visualization when projects are reorganized or exported.
- Removing an annotation must not affect the underlying scientific data.

### Design principle

Scientific visualizations should allow users to record not only what they observe, but also what they think it means, why it matters and what they might investigate next.

## 6.7.8 — Visualization Configuration and Persistence

Users should be able to save, revisit and reuse customized visualization configurations rather than having to recreate their preferred presentations repeatedly.

### Core requirements

- Allow users to save customized graph, chart and table configurations.
- Preserve axis settings, scales, units, colours, markers, labels and annotations.
- Allow users to reopen visualizations in their previously saved state.
- Associate saved visualizations with relevant projects, datasets and analyses.
- Support multiple visualizations of the same dataset.
- Allow users to duplicate and modify existing configurations.
- Preserve visualization settings independently of the underlying scientific data.
- Avoid losing customized arrangements when closing or switching workspaces.

### Visualization Presets and Reusable Configurations

Users should be able to save preferred visualization configurations as reusable presets.

This should include:

- Saving customized graph and table appearances as presets.
- Applying saved presets to other compatible datasets.
- Creating multiple presets for different scientific purposes.
- Editing, duplicating, renaming and deleting personal presets.
- Providing sensible built-in presets for common scientific visualization tasks.
- Allowing users to return to default presentation settings.
- Preserving relevant settings when presets are reused.

Examples could include:

- Spectroscopy overview.
- Detailed spectral feature identification.
- Multi-spectrum comparison.
- Photometric light-curve analysis.
- Transit event examination.
- Model-observation comparison.
- Publication-ready graph presentation.

### Future possibilities

- Workspace-specific visualization presets.
- Importing and exporting visualization configurations.
- Sharing presets with other users.
- Community-created visualization presets.
- Presets associated with reusable scientific workflows.
- Advanced preset compatibility checks for different dataset types.

### Important considerations

- Applying a visualization preset must not modify the underlying scientific data.
- Presets should identify settings that cannot be applied to a particular dataset.
- Incompatible settings should be handled transparently rather than silently ignored.
- Presets should retain their own versions where changes could affect reproducibility.
- Reusing a preset should not automatically imply that its presentation is scientifically appropriate for every dataset.

### Design principle

Users should be able to develop preferred ways of presenting scientific information, save them and reuse them without repeatedly rebuilding visualizations.

## 6.7.9 — Data Presentation, Export and Reporting

The application should allow users to take scientific data and visualizations beyond their immediate workspace, preserving relevant information and scientific context.

### Core requirements

- Allow users to export graphs and visualizations in common image and scientific formats.
- Allow underlying numerical data to be exported separately from graph images.
- Support high-resolution and publication-quality exports.
- Preserve labels, units, legends, annotations and uncertainty information.
- Allow users to export tables in appropriate structured formats.
- Support exporting multiple related visualizations together.
- Clearly identify whether exported material contains original data, processed data, derived results or model outputs.
- Preserve relevant provenance and citations when exporting scientific material.

### Future possibilities — Scientific Reporting and Presentation

Dedicated scientific reporting and presentation capabilities are a future possibility rather than an initial development requirement.

Potential functionality includes:

- Allowing users to assemble selected graphs, tables, annotations and research findings into structured reports.
- Supporting explanatory notes and descriptions alongside scientific results.
- Generating reports associated with research projects and individual analyses.
- Providing reusable report templates.
- Supporting different report formats and presentation styles.
- Integrating reporting with the broader research documentation and project-management systems.

This functionality should be developed progressively as the application matures and the need for more comprehensive reporting becomes clearer.

### Important considerations

- Exported material should retain relevant scientific context and provenance.
- Images and visualizations should not be treated as substitutes for exporting underlying numerical data.
- Reports should distinguish observations, processed measurements, model outputs and interpretations.
- Automatically generated reports should not present unverified interpretations as established findings.
- Reporting functionality should complement, rather than duplicate, the project's existing documentation and reproducibility systems.

### Design principle

Users should be able to take scientific data and visualizations beyond the application, with more comprehensive reporting capabilities introduced as the platform matures.

## Section 6.7 — Overall Design Principles

The scientific data presentation and interaction environment should follow these overarching principles:

1. **Scientific accuracy:** Present data faithfully, preserving precision, context, uncertainties and limitations.
2. **Interactivity:** Allow users to investigate and manipulate how information is presented rather than relying on static outputs.
3. **Flexibility:** Accommodate different scientific data types, disciplines and investigative approaches.
4. **Comparability:** Support meaningful comparisons between observations, models, reference datasets and derived results.
5. **Traceability:** Maintain connections between displayed information, underlying datasets, annotations and analysis history.
6. **Customization:** Provide substantial control over graphs, tables, comparisons and visualization configurations.
7. **Consistency:** Maintain shared presentation and interaction conventions throughout the application where appropriate.
8. **Accessibility:** Ensure scientific information remains understandable and usable without relying exclusively on colour or visual presentation.
9. **User control:** Preserve the distinction between changing how information is displayed and changing the scientific data itself.
10. **Extensibility:** Allow additional visualization types, interaction methods and presentation capabilities to be introduced as scientific functionality expands.

### Initial Development Priorities

The initial application should prioritize:

- Accurate and adaptable scientific data presentation.
- Interactive graphs and visualizations.
- Configurable scientific graphs and tables.
- Multi-dataset overlays and comparison views.
- Data selection and inspection.
- Linked visualizations and cross-component interaction where appropriate.
- Scientific annotations and contextual notes.
- Saving and reusing visualization configurations and presets.
- Scientific data and visualization export.

Dedicated scientific reporting, community-shared presets, advanced multidimensional exploration and more extensive customization systems can be developed progressively.

### General Principle

Scientific data presentation should be a central part of the research experience, not merely a way of displaying analytical outputs.

Users should be able to explore, inspect, compare, annotate, customize and export scientific information while maintaining a clear connection to the underlying data and its scientific context.

The system should provide strong defaults without imposing rigid presentation methods, allowing users to develop their own working approaches without compromising scientific accuracy, transparency or reproducibility.
