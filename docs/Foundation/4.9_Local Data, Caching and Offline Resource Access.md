# 4.9 — Local Data, Caching and Offline Resource Access

## Purpose

The application should support local storage and reuse of scientific data and external resources, allowing users to work efficiently without repeatedly retrieving the same information.

Astronomical datasets can be large, external services may be unavailable and research activities may extend across multiple sessions. The application should therefore provide appropriate mechanisms for temporarily caching, retaining and accessing previously acquired resources.

Local data access should reduce unnecessary network requests, improve responsiveness and support continued research when external services are unavailable.

The application should distinguish temporary cached information from deliberately retained resources, saved workspace materials and project-associated data. Users should retain control over what is stored, how long it is retained and when it may be removed.

Local storage and retention should accommodate different research needs without requiring users to manage every underlying file manually or risking the accidental removal of important research materials.

## 4.9.1 Local Resource Storage

### Core Requirements

- Support local storage of scientific datasets and external resources.
- Allow retrieved resources to be retained for future use.
- Support local access to previously acquired datasets without requiring repeated external retrieval.
- Preserve relevant metadata, identifiers, source information and data relationships.
- Support different storage requirements for large observational datasets, smaller reference resources and supporting metadata.
- Allow users to identify where relevant resources are stored within the application's storage environment.
- Maintain a distinction between temporary resources and deliberately retained materials.
- Avoid unnecessary duplication of identical underlying datasets where practical.
- Preserve independent derived representations when different research activities require different processing.
- Coordinate local resource storage with the project's broader storage and portability requirements in Section 9.

### Design Guidance

Local storage should support both routine research activities and longer-term investigations.

A user may temporarily retrieve an observation to inspect its contents, retain it for repeated analysis or incorporate it into a persistent research project.

These uses have different storage and retention requirements.

The application should support them without requiring users to manage every underlying file manually.

## 4.9.2 Temporary Caching

### Core Requirements

- Support temporary caching of external data and resource information where beneficial.
- Cache information that can improve search performance, previews, repeated inspection and routine access.
- Avoid automatically downloading complete large datasets solely to populate a cache.
- Distinguish temporary cached resources from permanently retained datasets.
- Allow temporary caches to be cleared or managed.
- Support configurable retention policies for cached resources.
- Allow cache-retention preferences to account for resource type, size, age, frequency of use and other relevant characteristics where practical.
- Identify cached resources and their associated source information.
- Avoid deleting resources required by saved workspace materials, projects or other retained research.
- Handle interrupted or incomplete caching operations appropriately.
- Avoid treating a cached resource as permanently current when its external source may have changed.
- Communicate when cached resources are scheduled for automatic expiration or cleanup where appropriate.

### Design Guidance

Caching should improve performance and reduce unnecessary retrieval without creating an uncontrolled accumulation of scientific data.

Examples include cached search metadata, resource descriptions, quick-look previews and selected portions of larger datasets.

The application should make it clear when a user is viewing temporarily cached information rather than a newly retrieved resource.

Temporary cache management must not compromise saved research or deliberately retained datasets.

Retention preferences should allow routine temporary information to be managed automatically while preserving resources that users have deliberately saved.

## 4.9.3 Retained Datasets and Resource Libraries

### Core Requirements

- Allow users to deliberately retain selected datasets and external resources locally.
- Support reusable collections of previously acquired scientific resources.
- Allow retained resources to be searched and inspected.
- Preserve source identifiers, metadata, provenance and relevant quality information.
- Distinguish retained original data from derived or processed representations.
- Allow users to organize retained resources where appropriate.
- Identify when retained resources are associated with active projects or saved workspace materials.
- Allow users to remove retained resources when they are no longer needed, subject to dependency and project-preservation requirements.
- Support retention of reference resources that are useful across multiple investigations.
- Avoid requiring users to retrieve the same resource repeatedly when a suitable local copy already exists.
- Allow retained resources to remain available independently of temporary cache cleanup.
- Respect applicable licensing and provider restrictions when retaining external resources.

### Design Guidance

A local resource library can provide convenient access to datasets and reference information used regularly across research activities.

For example, a user may retain frequently used molecular reference data, observational datasets or catalogue records.

The application should make these resources discoverable and reusable without confusing them with formal research projects or temporary caches.

Deliberately retained resources should not be treated as temporary cache entries simply because they have not been accessed recently.

## 4.9.4 Local Resource Identification and Reuse

### Core Requirements

- Identify when a requested resource has already been acquired or retained locally.
- Allow users to inspect available local copies before initiating another retrieval.
- Identify relevant differences between local and externally available versions.
- Distinguish exact matches from related resources or different data releases.
- Allow users to choose whether to reuse an existing local resource or retrieve an updated version.
- Preserve original source identifiers and version information.
- Avoid silently substituting an outdated or different resource for the one requested.
- Support reuse of local resources across compatible workspaces and projects.
- Identify when a local resource is incomplete or unavailable for the intended operation.
- Identify whether an available local copy is temporary, deliberately retained or associated with saved research.
- Avoid unnecessary duplication when multiple research activities can safely reference the same underlying resource.

### Design Guidance

The application should avoid unnecessary retrieval when a suitable local resource already exists.

However, a local copy should not automatically be assumed equivalent to the currently available external resource.

For example, an archive may have released a newer calibrated version of an observation. The application should identify the difference and allow the user to decide whether the existing version remains appropriate.

Resource reuse should preserve the identity and history of the original resource rather than treating all locally available copies as interchangeable.

## 4.9.5 Storage Management and User Awareness

### Core Requirements

- Provide visibility into local resource storage and usage.
- Identify the approximate storage requirements of resources before substantial retrieval where information is available.
- Communicate when an operation may consume significant storage.
- Allow users to review temporary caches, retained datasets and other locally stored scientific resources.
- Support removal of unnecessary temporary or retained resources.
- Identify resources that are required by projects or saved research activities.
- Prevent accidental removal of resources that would invalidate or compromise saved research.
- Allow users to distinguish storage used by original data, derived data, caches and supporting resources.
- Provide useful information about incomplete or failed storage operations.
- Coordinate storage management with the broader storage controls established in Section 9.
- Provide sufficient information for users to understand the consequences of cleanup and retention operations.
- Make it possible to identify resources occupying substantial storage.

### Design Guidance

Astronomical data can require substantial storage, particularly when dealing with image collections, spectral cubes, time-series observations and large survey datasets.

Users should be able to understand the storage implications of their actions without having to inspect internal directories or manage application files manually.

Storage warnings and management controls should be proportionate to the size and importance of the affected resources.

Users should be able to understand which resources can be safely cleared, which are deliberately retained and which are required by saved research.

## 4.9.6 Resource Retention and Dependency Protection

### Core Requirements

- Distinguish resources that are temporary from those deliberately retained.
- Identify datasets referenced by saved workspace materials or research projects.
- Identify dependencies between stored resources and derived datasets, analyses or outputs.
- Warn users when removing a resource may affect other research materials.
- Prevent accidental deletion of required project resources.
- Allow users to remove temporary cached copies without removing independently retained or project-associated data.
- Support appropriate handling of shared resources used by multiple projects.
- Preserve research relationships when resources are moved or reorganized.
- Communicate when a resource cannot be removed safely without first addressing its dependencies.
- Avoid silently deleting dependent research materials when removing a local resource.
- Distinguish the removal of a temporary cached copy from the removal of the underlying retained resource.
- Ensure automatic cleanup follows the same dependency protections as manual cleanup.

### Design Guidance

A dataset may exist locally because it is temporarily cached, deliberately retained or required by a saved investigation.

These situations should not be treated identically.

For example, clearing a temporary preview cache should not delete the original dataset used by a project.

Likewise, removing a shared local resource should not silently invalidate several research activities that depend on it.

Dependency protection should apply regardless of whether cleanup is initiated manually or through an automatic retention policy.

## 4.9.7 Offline Access to Previously Acquired Resources

### Core Requirements

- Allow users to access suitable locally retained resources when external services are unavailable.
- Support inspection and analysis of previously acquired datasets without requiring an active external connection.
- Make available local resources discoverable through appropriate application workflows.
- Identify which functions require an external connection and which can operate using local resources.
- Communicate when a requested resource is unavailable locally and cannot currently be retrieved.
- Preserve access to locally stored metadata, source information and relevant research records.
- Avoid implying that externally hosted resources remain accessible offline when no suitable local copy exists.
- Support continued work with saved projects and locally available materials.
- Identify when an offline operation may require information that has not been retained locally.
- Preserve access to deliberately retained resources independently of temporary cache expiration.
- Allow offline work to continue without requiring users to repeatedly confirm that previously retained resources are available.

### Design Guidance

Offline access should allow users to continue meaningful research using previously acquired materials.

However, the application should distinguish between local functionality and operations that depend on external services.

For example, a user may be able to inspect and analyze a saved observation offline while being unable to retrieve a newly released dataset or query a live external archive.

The availability of local data should be clear enough that users can understand which research activities can continue without connectivity.

## 4.9.8 Offline Resource Awareness

### Core Requirements

- Make the current availability of local resources understandable.
- Identify when an external resource has not been cached or retained locally.
- Distinguish unavailable external resources from unavailable local files.
- Communicate when previously acquired data may be outdated relative to its external source.
- Preserve the original resource version used in previous research.
- Allow users to identify which external resources may require an active connection.
- Avoid silently treating an outdated cached resource as the latest available version.
- Provide useful information about the last known external retrieval or update where available.
- Identify when locally available resources are incomplete or only partially retrieved.
- Distinguish information available from local metadata and previews from information requiring access to the complete external resource.

### Design Guidance

Users should be able to understand what information is available locally and what remains dependent on external services.

The application should not require users to remember which resources they previously downloaded or whether a cached copy may have become outdated.

Resource availability and version information should be presented in a way that supports informed decisions without creating unnecessary interruptions.

## 4.9.9 Resource Updates and Synchronization Awareness

### Core Requirements

- Identify when external resources may have changed since their local retrieval.
- Support checking for updated resources where external services provide suitable mechanisms.
- Allow users to review available updates before incorporating them.
- Preserve previously acquired versions.
- Avoid silently replacing local resources with newer external versions.
- Communicate when a local resource may be outdated or superseded.
- Support appropriate updating of reference resources and other retained materials.
- Preserve relationships between original and updated versions.
- Identify potential effects of updates on existing analyses or research projects.
- Coordinate synchronization behavior with the broader requirements in Section 9.
- Avoid automatically updating project-associated resources when doing so could change the basis of existing research.
- Make the distinction between checking for an update and actually retrieving or applying that update clear.

### Design Guidance

Local resources should remain stable enough to support historical research and reproducibility.

An updated external dataset should be treated as a potentially new version rather than an automatic replacement for the resource previously used.

Users should be able to review changes and determine whether an update is appropriate for their research.

Checking for an update should not itself alter the locally retained resource.

## 4.9.10 Local Reference Resources

### Core Requirements

- Support local retention of scientific reference resources where permitted.
- Allow frequently used reference information to remain accessible without repeated external requests.
- Support appropriate caching or retention of molecular, atomic, stellar, planetary and other relevant scientific reference information.
- Preserve source identifiers, versions, metadata and attribution.
- Identify when reference resources may have been updated.
- Distinguish locally retained reference information from live external database results.
- Support reuse across compatible scientific workspaces.
- Respect applicable licensing, access and redistribution restrictions.
- Avoid assuming that every external reference database permits permanent local retention.
- Support appropriate retention preferences for reference resources, including different treatment of temporary and deliberately retained reference information.
- Preserve the version of reference information used in historical analyses where required for reproducibility.

### Design Guidance

Reference resources can be essential to repeated scientific workflows.

For example, users may repeatedly consult molecular spectral data, stellar parameters, planetary information or other specialized reference collections.

Local availability can improve research efficiency, but retention must respect the conditions imposed by the original provider.

Reference resources used in historical research should remain identifiable by their original source and version, even when newer reference information becomes available.

## 4.9.11 Cache Integrity and Resource Verification

### Core Requirements

- Maintain appropriate checks to identify incomplete or corrupted cached resources.
- Distinguish complete resources from interrupted or partial retrievals.
- Verify stored resources where technically practical.
- Preserve available information about retrieval and storage failures.
- Identify when a local file is missing, unreadable or unexpectedly modified.
- Avoid presenting incomplete or corrupted cached data as a verified complete resource.
- Support re-retrieval or recovery where appropriate.
- Preserve original source information when a resource is replaced or reacquired.
- Identify when a resource cannot be verified because the original source or verification information is unavailable.
- Apply appropriate integrity checks to both temporary cached resources and deliberately retained resources.
- Communicate when integrity verification is incomplete or unavailable rather than implying successful verification.

### Design Guidance

Local storage should not automatically be treated as evidence that a resource is complete or intact.

A download may be interrupted, a file may become corrupted or a resource may be modified outside the application.

The application should communicate relevant integrity problems and avoid silently using compromised data in scientific workflows.

## 4.9.12 Configurable Local Storage and Retention Preferences

### Core Requirements

- Allow users to configure preferences for temporary caching, local retention and automatic cleanup.
- Support different retention preferences for different resource categories where practical.
- Allow preferences to account for resource type, size, age, frequency of use and storage requirements where appropriate.
- Provide sensible default retention behavior that avoids unnecessary permanent storage.
- Allow users to establish how long suitable temporary resources should remain cached.
- Support automatic expiration or cleanup of temporary resources according to configured preferences.
- Allow users to identify which resource categories are subject to automatic cleanup.
- Provide appropriate control over whether frequently used resources should remain available locally.
- Allow users to retain selected resources independently of temporary cache policies.
- Ensure that automatic cleanup does not remove project-associated resources, independently saved workspace materials or other protected research dependencies.
- Make active retention preferences understandable.
- Allow users to change preferences without unintentionally deleting previously retained research materials.
- Avoid silently applying new retention preferences to existing resources in ways that could remove important data.
- Coordinate retention preferences with the acquisition and import requirements in Section 4.5.
- Preserve licensing and provider restrictions when applying retention preferences.

### Design Guidance

Users may have different storage requirements depending on the type and size of scientific data they work with.

For example, a user may prefer to keep small reference resources locally while allowing temporary previews and large exploratory downloads to expire automatically.

Another user may prefer to retain larger datasets because they are used frequently or because external retrieval is difficult.

The application should accommodate these differences without requiring users to manually manage every resource.

Automatic cleanup should apply only to resources eligible for removal under the active retention preferences and dependency protections.

Changing a retention preference should affect future storage behavior in a predictable way. Existing retained resources should not be silently deleted merely because a user changes a default preference.

The relationship between acquisition-time retention decisions and local storage behavior is established in Section 4.5.16. This subsection defines how those preferences should operate within local storage and cache management.

## General Principles

Local data, caching and offline resource access should:

- Reduce unnecessary external retrieval.
- Support deliberate local retention of scientific datasets and reference resources.
- Distinguish temporary caches, retained resources, saved workspace materials and project-associated data.
- Preserve metadata, source information and scientific relationships.
- Allow users to discover and reuse existing local resources.
- Make storage requirements and retention implications understandable.
- Support configurable retention preferences and automatic cleanup.
- Protect resources required by saved research.
- Support meaningful offline access to previously acquired materials.
- Communicate resource availability and potentially outdated information.
- Preserve historical versions when external resources change.
- Respect licensing and provider restrictions.
- Maintain the integrity of locally stored scientific resources.
- Avoid unnecessary duplication while preserving independent derived representations where required.

## General Principle

Scientific resources should remain accessible and reusable without requiring unnecessary dependence on external services.

Local storage and caching should improve research continuity while preserving user control, scientific provenance, historical stability and the integrity of saved research.

Automatic retention and cleanup should reduce storage-management effort without putting saved research, project dependencies or deliberately retained resources at risk.

## Implementation Boundary

This subsection establishes requirements for local resource retention, temporary caching, offline access, storage awareness, update awareness, configurable retention preferences and local resource integrity.

It does not prescribe specific storage technologies, cache architectures, synchronization protocols, directory structures, retention algorithms or implementation technologies.

Data retrieval and import are addressed in Section 4.5. Data lineage and processing history are addressed in Section 4.6. Source provenance and metadata are addressed in Section 4.7. Licensing and retention restrictions are addressed in Section 4.11. Broader platform storage, offline operation and synchronization requirements are addressed in Section 9. Project-level resource organization and shared-data relationships are addressed in Section 6.4.
