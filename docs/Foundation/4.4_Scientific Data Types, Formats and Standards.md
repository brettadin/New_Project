

# 4.4 — Scientific Data Types, Formats and Standards

## Purpose

The application should accommodate the wide variety of scientific data types, file formats and standards encountered in astronomical research.

Astronomical data is produced by different instruments, observatories, surveys, scientific software packages and research institutions. These sources may represent similar scientific measurements using different file formats, data structures, metadata conventions and measurement standards.

The application should support relevant established formats while remaining flexible enough to accommodate less common, specialized and unfamiliar data representations.

It should recognize that a file extension does not necessarily establish the scientific meaning or internal structure of its contents. Reliable interpretation requires consideration of the actual data, metadata, conventions and context.

The application should preserve original information, communicate uncertainty about interpretation and provide appropriate ways to make supported data usable across scientific capabilities.

## 4.4.1 Broad Scientific Data and Format Support

### Core Requirements

- Support a broad range of astronomical, scientific, observational, instrument-specific and general-purpose data formats.
- Accommodate common formats as well as less frequently encountered scientific formats.
- Support structured, semi-structured and unstructured files where meaningful scientific information can be identified.
- Accommodate both numerical and non-numerical scientific information.
- Support data represented in files, tables, arrays, multidimensional structures and other appropriate forms.
- Avoid restricting users to a small fixed collection of file extensions.
- Investigate additional format support as scientific requirements develop.
- Distinguish between a format being recognized, successfully parsed and scientifically interpreted.
- Communicate when a format is only partially supported or requires additional information.
- Preserve original files independently of any interpretation or conversion performed by the application.

### Design Guidance

Astronomical research frequently involves data from different generations of instruments, specialized software and external repositories.

The application should not assume that all useful data will arrive in a small number of standardized formats.

Broad format support should be treated as an ongoing capability rather than a permanently fixed list.

However, supporting a file extension or reading its contents does not automatically mean the application understands the scientific information represented within it.

## 4.4.2 Astronomical and Scientific File Formats

### Core Requirements

Consider and support relevant established formats, including but not limited to:

- **FITS:** Flexible Image Transport System, widely used for astronomical images, tables, spectra and multidimensional scientific data.
- **VOTable:** An XML-based format for representing and exchanging tabular astronomical data.
- **ECSV:** Enhanced Character Separated Values, supporting structured scientific tables and associated metadata.
- **CSV and TSV:** Common delimited text formats used for measurements, tables and exported scientific data.
- **ASCII and plain text:** Text-based scientific data, including instrument outputs and observational measurements.
- **HDF5:** A hierarchical format for storing large and complex scientific datasets.
- **ASDF:** Advanced Scientific Data Format, used for structured scientific data and metadata.
- **XML and JSON:** Structured formats used for scientific information, metadata and data exchange.
- **Specialized spectral and observational formats:** Formats associated with particular instruments, observatories, archives and scientific software.
- **Common image formats:** Formats such as TIFF, PNG and JPEG where appropriate for astronomical images, previews or related scientific material.

Support additional formats when justified by scientific relevance and practical feasibility.

Distinguish formats intended to preserve scientific measurements from formats primarily intended for visualization, presentation or general-purpose information exchange.

### Design Guidance

Different formats may represent similar scientific information while providing different levels of metadata, structure and precision.

For example, a scientific FITS file may preserve observational metadata and coordinate information that are absent from a simplified image export.

The application should retain access to the original representation and identify when a format has limitations for a particular scientific purpose.

The listed formats are examples of relevant candidates, not a requirement to implement every format simultaneously.

## 4.4.3 Scientific Data Types and Representations

### Core Requirements

Accommodate different scientific data types and representations, including:

- **Tabular data:** Measurements and associated metadata arranged in rows, columns or structured records.
- **Spectral data:** Measurements represented across wavelength, frequency, wavenumber or other relevant spectral coordinates.
- **Photometric data:** Fluxes, magnitudes, relative measurements and associated observational information.
- **Time-series data:** Measurements associated with observation times, temporal sampling and related metadata.
- **Image data:** Two-dimensional astronomical images and related spatial measurements.
- **Multidimensional data:** Data cubes and other representations involving multiple spatial, spectral, temporal or physical dimensions.
- **Coordinate and positional data:** Astronomical positions, reference frames, angular measurements and related information.
- **Event-based data:** Individual recorded events or detections, including specialized detector observations.
- **Catalogued data:** Object properties, classifications, measurements and associated identifiers.
- **Model and simulation outputs:** Calculated quantities, predicted measurements, parameter sets and simulation results.
- **Non-numerical scientific information:** Descriptions, classifications, observational notes and other contextual information.

Support relationships between different data representations where appropriate.

Allow scientific data to retain its original structure while providing suitable representations for compatible application capabilities.

### Design Guidance

Data types describe the scientific information being represented, whereas file formats describe how that information is stored or exchanged.

The same scientific quantity may appear in multiple formats, and a single file may contain several different types of scientific information.

The application should identify both dimensions rather than relying on file extensions alone.

## 4.4.4 File Recognition and Format Detection

### Core Requirements

- Attempt to identify file formats and internal structures automatically.
- Consider file contents, signatures, headers, metadata, encoding and structural characteristics.
- Use file extensions as supporting information rather than definitive proof of format.
- Identify discrepancies between a file extension and its actual contents.
- Recognize supported scientific structures even when files use unfamiliar or nonstandard extensions.
- Identify when a file contains multiple data structures or components.
- Communicate the confidence and limitations of automatic recognition where appropriate.
- Allow users to provide additional information when automatic recognition is insufficient.
- Distinguish successful file recognition from successful scientific interpretation.

### Design Guidance

Automatic format detection should help users work with diverse files without requiring them to know every technical detail.

However, the application must not assume that a file is valid simply because its extension appears familiar.

When recognition is uncertain, the application should communicate that uncertainty and provide appropriate inspection or manual interpretation options.

## 4.4.5 Internal Data Structures and Multidimensional Representations

### Core Requirements

- Accommodate scientific information stored as tables, arrays, images, data cubes and other structured representations.
- Support relevant dimensional information and relationships between data components.
- Preserve the organization of multidimensional datasets.
- Identify axes, dimensions and associated coordinate information where available.
- Support datasets containing multiple measurements, extensions, tables or data products.
- Accommodate relationships between measurements and their associated metadata.
- Preserve information about data ordering, indexing and structural organization.
- Identify unsupported or partially interpreted structures.
- Avoid flattening or simplifying complex data in ways that discard scientifically relevant information.

### Design Guidance

Astronomical datasets may contain much more than a single table or image.

A FITS file, for example, may contain multiple extensions, different data products and associated metadata.

The application should preserve these structures and make relevant components accessible without assuming that every file represents one simple measurement collection.

## 4.4.6 Metadata and Scientific Descriptions

### Core Requirements

Recognize, preserve and interpret relevant metadata associated with scientific data.

Where available, accommodate:

- Astronomical object names and identifiers.
- Observation dates and times.
- Observation locations and coordinates.
- Telescope, observatory and instrument information.
- Detector and instrument configurations.
- Measurement types and scientific quantities.
- Wavelength, frequency or energy information.
- Spatial and spectral coordinate information.
- Units and measurement conventions.
- Spectral and spatial resolution.
- Exposure times and observational conditions.
- Calibration and processing information.
- Uncertainty and quality information.
- Data acquisition and processing history.
- Relevant source and archive identifiers.
- Data product descriptions and version information.

Preserve metadata that cannot be interpreted automatically.

Distinguish original metadata from information inferred, assigned or supplied by the user.

Allow metadata to remain associated with its corresponding data components when data is transformed, extracted or converted.

### Design Guidance

Metadata provides essential scientific context.

A numerical array without information about its axes, units, measurement meaning or observational origin may be difficult or impossible to interpret reliably.

The application should therefore treat metadata as part of the scientific dataset rather than optional descriptive information.

## 4.4.7 Scientific Units and Measurement Conventions

### Core Requirements

- Recognize and accommodate relevant scientific units and measurement conventions.
- Support appropriate units for wavelength, frequency, wavenumber, time, distance, velocity, flux, intensity, energy, temperature and other relevant quantities.
- Accommodate commonly used astronomical units and conventions.
- Identify whether units are explicitly provided, inferred with sufficient evidence, user-assigned or unknown.
- Preserve original units and values.
- Support scientifically valid conversions where appropriate.
- Record relevant conversion methods and resulting representations.
- Distinguish between unit conversion and more complex scientific transformations.
- Avoid silently assigning units when the available information is insufficient.
- Communicate when inconsistent or ambiguous units may affect subsequent analysis.

### Design Guidance

Scientific values must be interpreted in the context of their units and measurement conventions.

Two numerical datasets should not be treated as directly comparable merely because their values have similar magnitudes or appear in equivalent columns.

Conversions should preserve traceability to original measurements and should not conceal differences in scientific meaning.

## 4.4.8 Coordinate Systems, Reference Frames and Time Standards

### Core Requirements

- Accommodate relevant astronomical coordinate systems and reference frames.
- Recognize and preserve coordinate information associated with observations and datasets.
- Support appropriate celestial coordinate representations.
- Preserve reference epochs and coordinate conventions.
- Accommodate relevant spatial coordinate transformations.
- Recognize relevant time systems and astronomical time conventions.
- Preserve observation timestamps and their associated time standards.
- Identify ambiguities involving coordinate systems, reference frames or time conventions.
- Support appropriate transformations where sufficient information is available.
- Communicate when required reference information is missing or uncertain.

### Design Guidance

Astronomical coordinates and observation times may use different reference systems and conventions.

For example, positional information may be expressed in different celestial coordinate systems or reference frames, while observation timestamps may use different time standards.

The application should preserve these distinctions and avoid assuming that values from different conventions are directly interchangeable.

## 4.4.9 Scientific Standards and Interoperability

### Core Requirements

- Support relevant established astronomical and scientific data standards.
- Consider standards used for data representation, metadata, coordinates, measurement descriptions and data exchange.
- Accommodate relevant standards developed through astronomical organizations and scientific collaborations.
- Support interoperability between compatible external resources and internal scientific capabilities.
- Preserve standard-defined metadata and relationships where possible.
- Identify unsupported or partially supported standard features.
- Avoid discarding meaningful information when converting between standards or representations.
- Monitor relevant changes to scientific standards as the application develops.

Potential areas of standards support include:

- FITS conventions and associated metadata conventions.
- International Virtual Observatory Alliance (IVOA) standards.
- Astronomical table and catalogue exchange standards.
- World Coordinate System (WCS) conventions.
- Scientific unit and quantity representations.
- Time and coordinate standards.
- Specialized instrument and mission data conventions.

### Design Guidance

Established standards improve interoperability and reduce the need for source-specific interpretation.

However, a format or standard may support optional features, specialized conventions or extensions that are not fully implemented by every application.

The application should communicate the extent of its support rather than claiming complete compatibility simply because it recognizes a standard.

## 4.4.10 Unfamiliar, Nonstandard and Partially Supported Formats

### Core Requirements

- Attempt to inspect unfamiliar files when their contents may contain useful scientific information.
- Avoid immediately rejecting files solely because their extensions or formats are not recognized.
- Investigate alternative methods of examining file structure and extracting usable information.
- Support manual interpretation when automatic recognition is insufficient.
- Identify portions that can be interpreted reliably and those that cannot.
- Preserve unrecognized content where practical.
- Communicate what was successfully recognized and what remains uncertain.
- Allow partially usable data to be examined where scientifically appropriate.
- Avoid treating unsupported or ambiguous information as verified scientific data.
- Provide a foundation for adding support for additional formats and structures.

### Design Guidance

The application should be flexible when encountering unfamiliar data, particularly because researchers may work with older instrument outputs, institution-specific formats or files produced by specialized scientific software.

However, flexibility must not become unsupported interpretation.

If the application can identify a numerical table but cannot determine what its columns represent, it should communicate that distinction and allow appropriate manual interpretation rather than assigning scientific meanings automatically.

## 4.4.11 Format Conversion and Data Representation

### Core Requirements

- Support appropriate conversion between compatible scientific formats and representations.
- Preserve relevant scientific information, metadata and structural relationships during conversion.
- Identify information that cannot be preserved in the destination format.
- Allow users to inspect conversion settings and outcomes where appropriate.
- Preserve the original file unchanged.
- Create separate converted or derived representations.
- Record the conversion method, relevant parameters and resulting format.
- Distinguish lossless conversion from conversion that may discard or approximate information.
- Communicate when a conversion changes precision, resolution, sampling or other scientifically relevant characteristics.
- Avoid presenting converted data as identical to the original when information has been altered or omitted.

### Design Guidance

Format conversion should improve interoperability without concealing changes to scientific information.

Some conversions may preserve the complete relevant data, while others may simplify metadata, reduce precision or discard specialized structures.

The application should communicate these differences and preserve access to the original representation.

## 4.4.12 Extensibility and Format Support Expansion

### Core Requirements

- Allow support for additional scientific formats and standards as requirements develop.
- Accommodate new instrument-specific and archive-specific data structures.
- Support improvements to existing format recognition and interpretation.
- Maintain documentation of supported formats and known limitations.
- Identify formats that are experimental, partially supported or no longer maintained.
- Evaluate new format support according to scientific relevance, user needs, technical feasibility and maintenance requirements.
- Avoid unnecessary duplication of format-handling functionality.
- Preserve compatibility with previously supported formats when changes are introduced.

### Design Guidance

Scientific data formats and standards continue to develop.

The application should be designed to expand its format support without requiring unnecessary redesign of unrelated scientific capabilities.

Format support should be evaluated according to actual scientific use cases rather than the number of extensions the application can recognize.

## General Principles

Scientific data types, formats and standards should:

- Accommodate a broad range of astronomical and scientific data representations.
- Avoid unnecessary restrictions based on file extensions.
- Distinguish file formats from scientific data types and meanings.
- Preserve original files and their internal structures.
- Recognize and retain relevant metadata and scientific conventions.
- Support appropriate units, coordinates, reference frames and time standards.
- Promote interoperability through established scientific standards.
- Accommodate unfamiliar and partially supported files without unsupported interpretation.
- Preserve traceability through conversions and transformations.
- Expand format support as scientific requirements develop.

## General Principle

The application should be flexible enough to work with the diverse data representations encountered in astronomical research while remaining rigorous about what it can reliably recognize and interpret.

Broad format support should increase accessibility to scientific information without compromising the meaning, integrity or traceability of the underlying data.

## Implementation Boundary

This subsection establishes the intended support for scientific data types, file formats, metadata conventions, standards and interoperability.

It does not prescribe specific parsing libraries, conversion software, internal data models or implementation technologies. It also does not require every listed format or standard to be supported during initial development.

External archive and database integrations are addressed in Section 4.2. Data relevance and compatibility assessment are addressed in Section 4.3. Data retrieval, local import and the handling of unfamiliar user-provided files are addressed in Section 4.5. General scientific data examination and preparation are addressed in Section 3.2.
