# 6.8 — Customization and User Preferences

## Purpose

This section establishes how users should be able to personalize the application's behaviour, appearance, defaults and working environment.

Section 6.5 established the visual identity and interface design principles. Section 6.6 addressed usability and accessibility. Section 6.7 covered customization of scientific data presentation.

Section 6.8 focuses on broader application-level customization: allowing users to configure how the application behaves and feels while maintaining consistency, scientific accuracy and usability.

The initial implementation should provide a manageable set of useful customization options, with opportunities for expansion as the application develops.

## 6.8.1 General Customization Principles

Customization should initially remain relatively limited, providing users with useful control over their application experience without introducing unnecessary complexity.

The system should be expandable as the application develops and user requirements become clearer.

**Core requirements**

- Provide basic application-level customization.
- Preserve user preferences between sessions.
- Support global preferences alongside workspace-specific and project-specific settings where appropriate.
- Allow users to override global preferences where necessary.
- Provide sensible defaults so users do not need to configure everything manually.
- Make important settings discoverable and understandable.
- Allow users to restore default settings.
- Avoid requiring users to configure the same preference repeatedly across different workspaces.
- Ensure customization does not compromise scientific accuracy, accessibility or application functionality.

**Future possibilities**

- More extensive application customization.
- Advanced preference categories and controls.
- Greater workspace-specific personalization.
- User-defined configuration profiles.
- More extensive control over application behaviour and presentation.

**Important considerations**

- Customization should expand in response to actual needs rather than introducing complexity prematurely.
- Global, workspace-specific and project-specific settings should have clearly defined relationships.
- Users should understand when one setting overrides another.
- Changes should not silently alter scientific data or invalidate previous analytical configurations.
- Users should be able to reverse unwanted preference changes or restore sensible defaults.

**Design principle:** Begin with a manageable set of useful customization options, retaining the flexibility to introduce more extensive personalization as the application matures.

## 6.8.2 Application Appearance and Themes

The application should initially provide a small selection of professionally designed themes, with additional customization introduced as the application develops.

**Core requirements**

- Provide a small selection of professionally designed application themes.
- Include dark and lighter appearance options.
- Provide limited accent-colour customization where appropriate.
- Allow interface text sizing to be adjusted where practical.
- Maintain consistent visual presentation across scientific workspaces.
- Provide a well-designed default theme reflecting the application's visual identity.
- Allow users to change themes without losing other application preferences.
- Ensure themes maintain readability, accessibility and appropriate contrast.

**Future possibilities**

- Additional professionally designed themes.
- More extensive theme customization.
- User-created themes.
- Additional background and accent-colour combinations.
- Greater control over interface contrast and visual density.
- Importing and sharing themes.

**Important considerations**

- Application themes must remain separate from scientific visualization colours and semantic status indicators, as established in Section 6.5.
- Changing themes must not alter scientific meaning, dataset identities or analytical presentation settings.
- Themes should be designed and tested for usability rather than simply offering arbitrary colour combinations.
- Appearance customization should complement the accessibility requirements established in Section 6.6.

**Design principle:** Begin with a small collection of polished, consistent themes and expand appearance customization as the application matures.

## 6.8.3 Workspace and Layout Preferences

The application should initially provide basic layout customization, allowing users to adjust their working environment without introducing unnecessary complexity.

**Core requirements**

- Allow basic panel resizing and repositioning.
- Allow users to show or hide selected panels and tools.
- Preserve preferred layouts between sessions.
- Provide sensible default layouts for different scientific workspaces.
- Allow users to restore the original workspace arrangement.
- Ensure layout customization does not interfere with essential navigation or functionality.

**Future possibilities**

- Multiple saved layouts.
- Workspace-specific layout profiles.
- Custom panel arrangements.
- User-created layout presets.
- Importing and exporting layouts.
- More extensive control over workspace organization.

**Important considerations**

- Initial customization should remain straightforward and intuitive.
- Essential navigation and functionality should remain accessible.
- Different scientific workspaces may require different default arrangements.
- Layout changes should not affect underlying research data or project organization.

**Design principle:** Provide basic layout flexibility from the beginning, with more extensive workspace customization introduced as the application's needs develop.

## 6.8.4 Scientific and Analytical Preferences

The application should allow users to establish global scientific and analytical preferences, reducing repetitive configuration while accommodating different research disciplines and investigations.

**Core requirements**

- Allow users to configure preferred scientific units and measurement conventions.
- Support preferences for wavelength units and representations, time and date conventions, and numerical formatting.
- Allow default numerical precision and display formatting to be configured.
- Provide default graph and table presentation preferences.
- Allow preferred scientific reference databases and resources to be configured where appropriate.
- Support global preferences alongside workspace-specific and project-specific overrides.
- Make active settings and overrides understandable.
- Ensure preferences do not silently modify original data or compromise scientific validity.

**Future possibilities**

- More extensive discipline-specific preferences.
- Advanced analytical configuration profiles.
- Additional control over default scientific methods and parameters.
- Reusable preference profiles for different research activities.

**Important considerations**

- A preferred unit or convention must not be assumed suitable for every dataset.
- Necessary conversions must remain traceable and preserve original values.
- Numerical display precision must not silently reduce the precision of stored scientific data.
- Default analytical settings must remain subject to scientific suitability and user control.
- Preferred reference databases should establish useful defaults, not unnecessarily restrict access to other scientific resources.
- Workspace and project overrides should not unexpectedly change global preferences.
- The application should make the origin of an active preference understandable.

**Design principle:** Provide useful global scientific defaults while allowing individual workspaces and projects to accommodate their own requirements.

## 6.8.5 Default Settings and User-Defined Configurations

The application should allow users to save and reuse preferred configurations for scientific tools and workflows, reducing repetitive setup and supporting consistent working practices.

**Core requirements**

- Allow users to save configurations for frequently used tools and operations.
- Support reusable configurations for spectroscopy, photometry, graphing, data processing, modelling and other scientific capabilities.
- Include saved import preferences where appropriate.
- Allow users to apply saved configurations to compatible datasets and workflows.
- Allow users to modify, duplicate and delete saved configurations.
- Provide sensible built-in defaults for common operations.
- Preserve configurations between sessions.
- Keep configurations associated with relevant projects or workspaces where appropriate.

**Future possibilities**

- More advanced configuration management.
- Configuration profiles for different research activities.
- Importing and exporting configurations.
- Sharing configurations between users.
- Community-created configuration libraries.

**Important considerations**

- Check compatibility before applying configurations to different datasets.
- Explain when a saved configuration is unsuitable or requires modification.
- Preserve the distinction between user-defined configurations and established scientific methods.
- Applying a configuration must not silently modify original data.
- Configurations used in scientific analyses must be recorded where necessary for traceability and reproducibility.
- Reusable tool configurations should complement, rather than duplicate, the complete analysis and workflow records established in Sections 5.3 and 5.5.
- Scientific presentation configurations should remain consistent with the requirements established in Section 6.7.

**Design principle:** Make common scientific operations easier to repeat while preserving flexibility, compatibility checks and scientific control.

## 6.8.6 Automation and Workflow Preferences

The application should allow users to configure how much automation they prefer, building on the four automation levels established in Section 5.2.

**Core requirements**

- Allow users to establish a global automation preference:
  - Manual
  - Guided
  - Balanced
  - Advanced automation
- Allow preferences to be overridden for individual workspaces, projects or tasks.
- Allow users to control which routine operations may execute automatically, within the boundaries of their selected automation level.
- Respect approval requirements for significant processing steps and analytical decisions.
- Preserve automation preferences between sessions.
- Make the active automation level and any overrides clear to the user.

**Future possibilities**

- More detailed automation profiles for different research activities.
- Reusable automation configurations.
- Additional control over individual automated operations.

**Important considerations**

- Automation preferences must remain consistent with Section 5.2.
- Global settings should not unexpectedly override project-specific requirements.
- Individual preferences must not bypass the restrictions of the selected automation level.
- Significant scientific decisions must remain transparent and appropriately controlled.
- Users must be able to change automation preferences without losing research progress.

**Design principle:** Make automation adaptable to individual working preferences without compromising scientific control or creating conflicting settings.

## 6.8.7 Notifications and Application Behaviour

The application should provide useful notifications while avoiding unnecessary interruptions or excessive customization.

**Core requirements**

- Provide notifications for important events, including completed operations, errors and significant warnings.
- Notify users about relevant background tasks, such as downloads, processing and modelling.
- Allow basic control over non-critical notifications.
- Keep important warnings and unresolved errors accessible until addressed.
- Distinguish informational notifications, warnings and critical errors.
- Avoid repetitive or unnecessary notifications.

**Future possibilities**

- More detailed notification preferences.
- Workspace-specific notification settings.
- Advanced notification filtering and grouping.

**Important considerations**

- Critical scientific warnings and errors must not be silently suppressed.
- Notification severity should remain consistent with the error and quality-control categories established in Section 5.6.
- Notifications should communicate useful information without interrupting workflows unnecessarily.
- Notification preferences should not remove underlying quality-control records, warnings or scientific validation findings.
- Keep customization straightforward.

**Design principle:** Notifications should inform users when necessary, not become another system they constantly have to manage.

## 6.8.8 Preference Management and Portability

The application should provide straightforward preference management, allowing users to retain, restore and transfer settings where appropriate.

**Core requirements**

- Preserve user preferences between sessions.
- Allow users to restore default application settings.
- Clearly distinguish global, workspace-specific and project-specific preferences.
- Preserve relevant project configurations during project export and transfer.
- Make it clear which settings belong to the user's application preferences and which belong to individual research projects.
- Avoid unintended changes to preferences when opening or importing projects.
- When saved exploratory workspace materials are transferred into a project, preserve their associated configurations where compatible and relevant, without automatically overriding the destination project's existing configurations.

**Future possibilities**

- Importing and exporting personal preference profiles.
- Synchronizing preferences between installations.
- Sharing selected configurations with other users.

**Important considerations**

- Preference management should remain straightforward.
- Project-specific scientific configurations should remain associated with their projects.
- Transferring preferences must not unintentionally overwrite existing settings.
- Project configuration portability should align with the project export and reproducibility requirements established in Sections 5.5 and 6.4.
- Personal application preferences should not automatically be imposed on another user's environment when opening a shared or transferred project.
- Any future preference synchronization or sharing should respect the application's privacy and security requirements.

**Design principle:** Preferences should be persistent, understandable and portable where useful, without introducing unnecessary management complexity.

## Overall Section 6.8 Principles

- Customization should improve usability without becoming unnecessarily complicated.
- Global preferences should coexist with appropriate workspace and project-specific overrides.
- User preferences should persist between sessions.
- Customization should remain consistent across the application.
- Scientific configurations must remain compatible with the data and methods to which they are applied.
- Application appearance must remain independent of scientific data colours and meanings.
- Automation and notification preferences must remain consistent with the wider application requirements.
- Customization must never silently compromise scientific integrity, accessibility or data provenance.
- Users should be able to restore defaults and understand the settings currently affecting their work.
- Additional customization should be introduced in response to actual needs as the application develops.

**Initial implementation priorities:** Basic application preferences, a small selection of themes, basic layout flexibility, global scientific conventions, reusable configurations, saved import preferences, four-level automation preferences, simple notification controls and preference persistence.

**Future expansion:** Advanced themes, layout profiles, detailed analytical preferences, reusable profiles, advanced notification controls, and preference synchronization or sharing.

**Scope boundaries and relationships**

- Section 6.5 establishes the visual identity and scientific interface presentation principles.
- Section 6.6 establishes general usability and accessibility requirements.
- Section 6.7 covers customization of individual scientific data presentations and visualization configurations.
- Section 5.2 establishes the scientific automation levels and safeguards.
- Sections 5.3 and 5.5 establish processing, analysis configuration, traceability and reproducibility requirements.
- Section 5.6 establishes scientific quality-control and warning requirements.
- Section 6.4 establishes project-specific organization, configuration and portability.

Section 6.8 should complement these requirements rather than duplicate their functionality or introduce conflicting preference systems.

**General principle:** The application should adapt to the user's working preferences without making the user manage the application instead of conducting research.
