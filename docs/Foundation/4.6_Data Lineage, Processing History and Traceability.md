

# 4.6 — Data Lineage, Processing History and Traceability

## Purpose

The application should maintain clear and traceable relationships between original scientific data, derived representations, processing operations and subsequent research outputs.

Scientific investigations frequently involve data being converted, extracted, calibrated, filtered, transformed, combined or otherwise modified before it is used in analysis.

These operations can produce multiple versions of the same underlying dataset, each serving a different research purpose. The application should preserve the relationships between these versions so users can understand how a particular representation was produced and how it contributes to subsequent results.

Data lineage and processing history should support scientific transparency, reproducibility and the ability to revisit or extend previous work without losing the connection to original materials.

## 4.6.1 Original and Derived Data Relationships

### Core Requirements

- Maintain a distinction between original scientific data and representations derived from it.
- Preserve relationships between original datasets and their derived versions.
- Allow multiple derived representations to originate from the same source dataset.
- Support derived datasets that combine information from multiple source datasets.
- Identify the source materials contributing to a derived representation.
- Preserve original data when creating modified or transformed versions.
- Avoid overwriting original scientific materials during processing.
- Allow users to identify whether a dataset is original, derived, imported as a new representation or otherwise modified.
- Maintain relationships when derived data is copied, moved or incorporated into other research activities.

### Design Guidance

Scientific research may involve several representations of the same underlying observation.

For example, a spectrum may be imported in its original form, converted to different units, calibrated, corrected and normalized before being used in an analysis.

These representations should remain distinguishable and connected rather than appearing as unrelated datasets.

The application should also accommodate analyses that combine multiple observations or reference datasets into a single derived result.

## 4.6.2 Processing and Transformation History

### Core Requirements

Maintain records of significant operations that modify, transform or produce scientific data.

Relevant operations may include:

- Unit and coordinate conversions.
- Format conversions.
- Data extraction and selection.
- Calibration and correction.
- Normalization and scaling.
- Baseline and background correction.
- Filtering and noise reduction.
- Resampling and interpolation.
- Alignment and registration.
- Data combination and aggregation.
- Mathematical transformations.
- Model-based transformations.
- Other scientific processing operations.

Where applicable, record:

- The input dataset or datasets.
- The resulting output or derived representation.
- The operation performed.
- Relevant parameters and configurations.
- The date and time of the operation.
- The scientific capability or tool used.
- Relevant warnings, assumptions and limitations.
- The relationship to previous processing operations.

Allow users to inspect the processing history associated with a derived dataset.

### Design Guidance

Processing history should explain how a particular representation was produced rather than merely indicating that it has been modified.

The level of detail recorded should reflect the scientific significance of the operation.

For example, a simple display adjustment may not require the same record as a calibration or mathematical transformation that affects subsequent measurements.

Where an operation can influence scientific results, sufficient information should be retained to understand and reproduce its effect.

## 4.6.3 Processing Sequences and Data Lineage

### Core Requirements

- Maintain the sequence of operations contributing to derived datasets and research outputs.
- Preserve dependencies between successive processing steps.
- Identify the inputs and outputs associated with individual operations.
- Support processing sequences involving multiple datasets.
- Represent relationships between source data, intermediate representations and final outputs.
- Allow users to inspect how a derived result was produced.
- Preserve lineage when processing sequences are extended or revised.
- Avoid losing earlier processing relationships when new operations are applied.
- Support branching processing sequences where users investigate alternative methods or parameters.

### Design Guidance

Data lineage should represent the development of scientific information over time.

A derived dataset may depend on several previous operations, each of which may depend on different source materials.

The application should preserve these relationships so users can follow the chain of operations from the original inputs to the resulting data.

For example, two independently processed versions of an observation may share the same original source but follow different correction or normalization procedures.

Both branches should remain identifiable without one silently replacing the other.

## 4.6.4 Multiple Processing Versions and Historical Preservation

### Core Requirements

- Support multiple versions of derived scientific data.
- Preserve previous versions when new processing operations produce modified results.
- Allow users to revisit earlier representations.
- Maintain relationships between successive versions.
- Identify significant differences between versions where practical.
- Allow users to create alternative processing branches.
- Avoid silently replacing historical results with newly processed versions.
- Preserve the configurations and processing information associated with each version.
- Allow users to identify which version was used in a particular analysis.

### Design Guidance

Scientific processing is often iterative.

Users may revise parameters, apply alternative corrections or investigate whether a different method produces a more appropriate result.

The application should support this without forcing users to discard previous work.

Historical versions should remain distinguishable from current versions, particularly when changes could affect scientific interpretation or conclusions.

## 4.6.5 Relationships Between Datasets, Analyses and Outputs

### Core Requirements

Maintain traceable relationships between scientific data and the research activities that use or produce it.

Support relationships such as:

- Original observations and imported representations.
- Datasets and their processed versions.
- Multiple input datasets and combined outputs.
- Reference datasets and analytical comparisons.
- Observational data and model inputs.
- Analytical inputs and calculated measurements.
- Processing operations and resulting datasets.
- Analyses and their outputs.
- Results and associated graphs, visualizations or reports.
- Intermediate data and subsequent analytical operations.

Allow users to identify which data contributed to a particular result.

Allow users to inspect which analyses and outputs depend on a particular dataset.

Maintain these relationships when research materials are reorganized or used across different workspaces and projects.

### Design Guidance

A scientific result should not become detached from the data and operations that produced it.

For example, a spectral comparison may depend on an imported observation, a processed version of that observation, several molecular reference datasets and a particular set of comparison parameters.

The application should retain the relationships between these materials and the resulting analysis.

This should support both forward tracing, from original data to results, and backward tracing, from a result to its contributing inputs.

## 4.6.6 Shared Data and Independent Processing

### Core Requirements

- Allow multiple analyses and projects to reference the same underlying scientific dataset.
- Support independent processing and analysis of shared source data.
- Preserve separate derived representations when different workflows modify the same source.
- Maintain relationships between shared source material and each derived representation.
- Prevent modifications in one research activity from unintentionally changing another activity's derived data.
- Avoid unnecessary duplication of large original datasets.
- Identify dependencies on shared resources.
- Communicate when a shared source becomes unavailable or changes in a way that may affect dependent work.

### Design Guidance

Sharing an original dataset should not mean sharing every subsequent modification made to it.

For example, two investigations may use the same astronomical observation but apply different calibration methods or processing parameters.

Each investigation should be able to maintain its own derived representations and processing history without compromising the other.

This should complement the shared-data and resource-management requirements established in Section 6.4.

## 4.6.7 Reproducibility of Data Transformations

### Core Requirements

Preserve sufficient information to understand and reproduce significant data transformations wherever technically possible.

This may include:

- Original input data or stable references to it.
- Processing methods and operation identifiers.
- Parameters and configuration values.
- Relevant units and measurement conventions.
- Required dependencies and external resources.
- Intermediate data where necessary.
- Software or capability versions where relevant.
- Assumptions and limitations.
- Resulting outputs.
- Relevant warnings and execution information.

Identify when a previous transformation cannot be reproduced exactly because required data, resources, software or configuration information is unavailable.

Distinguish between reproducing an operation and reproducing an identical numerical result when computational conditions or external dependencies have changed.

### Design Guidance

The application should preserve enough information to make scientific transformations understandable and repeatable.

Exact reproducibility may not always be possible, particularly when operations depend on external resources, changing software or unavailable historical data.

Such limitations should be identified rather than hidden.

Detailed analytical reproducibility and research-level records are further addressed in Section 5.5.

## 4.6.8 Data Lineage Across Workspaces and Projects

### Core Requirements

- Preserve data lineage when materials move between scientific workspaces.
- Maintain relationships between original and derived datasets when materials are incorporated into projects.
- Preserve processing history when research materials are reorganized.
- Support references to shared data without unnecessarily duplicating original resources.
- Maintain relationships between project materials and their contributing datasets.
- Preserve lineage when projects are duplicated or transferred.
- Identify missing dependencies when moving or exporting research materials.
- Avoid breaking scientific relationships when users change organizational structures.

### Design Guidance

Data lineage should remain independent of the visible organization of research materials.

Moving a processed dataset into a different folder, workspace or project should not disconnect it from its original source or processing history.

Likewise, a project should retain the relationships needed to understand how its datasets and results were produced, even when some underlying resources are shared with other projects.

## 4.6.9 Data Dependency Identification

### Core Requirements

- Identify datasets and outputs that depend on particular source materials or processing operations.
- Allow users to determine which research materials may be affected when a source dataset becomes unavailable or is replaced.
- Identify missing or inaccessible inputs required to revisit previous processing operations.
- Communicate when a change to a dependency may affect derived data or subsequent analyses.
- Preserve historical results when a dependency changes.
- Avoid automatically recalculating or replacing dependent outputs without appropriate user control.
- Support inspection of dependency relationships across multiple processing stages.

### Design Guidance

Changes to an original dataset or external resource may affect multiple derived representations and research activities.

The application should help users understand these relationships before they decide whether to update, reprocess or retain historical results.

A changed source should not silently invalidate previous research or cause historical outputs to be replaced.

## 4.6.10 Lineage Inspection and Historical Review

### Core Requirements

- Provide accessible ways to inspect the lineage of scientific datasets and outputs.
- Allow users to view relevant processing operations and their sequence.
- Identify original inputs, intermediate representations and resulting outputs.
- Allow users to inspect alternative processing branches and historical versions.
- Provide access to relevant parameters and configurations.
- Identify missing or unavailable dependencies.
- Support tracing research outputs back to their contributing datasets.
- Allow users to review previous processing decisions without requiring them to reconstruct the workflow manually.

### Design Guidance

Lineage information should be available at different levels of detail.

A user examining a dataset may only need to know which original observation it came from and what major processing operations were applied.

A user investigating a previous result may need to inspect the complete sequence of operations and contributing inputs.

The application should make this information accessible without requiring users to navigate complex technical records for routine tasks.

## General Principles

Data lineage, processing history and traceability should:

- Preserve relationships between original and derived scientific data.
- Record significant processing operations and transformations.
- Maintain the sequence and dependencies of processing activities.
- Support multiple versions and alternative processing branches.
- Connect datasets with the analyses and outputs that use them.
- Allow independent processing of shared source data.
- Preserve sufficient information for reproducibility.
- Maintain relationships across workspaces, projects and exports.
- Identify dependencies and potential impacts of changing resources.
- Allow users to inspect historical processing and data relationships.
- Avoid silently replacing original data or historical results.

## General Principle

Scientific data should remain traceable throughout its entire lifecycle.

Users should be able to understand where a derived representation came from, how it was produced, what information contributed to it and how it relates to subsequent research.

Data lineage should preserve the scientific relationships behind research materials independently of how those materials are organized or presented.

## Implementation Boundary

This subsection establishes requirements for data lineage, processing history, derived-data relationships, dependency tracking and transformation traceability.

It does not prescribe specific provenance graphs, database schemas, version-control systems, processing engines or implementation technologies.

Original source identification, metadata and attribution are addressed in Section 4.7. Detailed analytical records and reproducibility requirements are addressed in Section 5.5. Project-level organization and shared-resource management are addressed in Section 6.4.
