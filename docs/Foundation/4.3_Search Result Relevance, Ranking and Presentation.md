# 4.3 — Search Result Relevance, Ranking and Presentation

## Purpose

The application should present discovered scientific data and external resources in a way that helps users identify which results are relevant to their research.

Searches may return large numbers of datasets, observations, catalogue records and scientific resources with varying degrees of relevance to the user's intended investigation.

The application should help users understand what each result represents, why it may be relevant, where it originated and what information is available before deciding whether to investigate or retrieve it.

Search-result presentation should support both straightforward object searches and more complex research-oriented discovery without unnecessarily hiding potentially useful results.

## 4.3.1 Search Result Organization

### Core Requirements

- Present results in a consistent and understandable format across supported external resources.
- Organize results into meaningful categories where appropriate.
- Distinguish between different types of results, such as observations, datasets, catalogue entries, scientific references and external resources.
- Identify the source archive, database or provider associated with each result.
- Present important identifying information without requiring users to open every result individually.
- Support browsing and inspection of large result collections.
- Allow users to change how results are organized or ordered where appropriate.
- Preserve the distinction between individual results and groups of related resources.
- Avoid presenting fundamentally different resource types as though they are interchangeable.

### Design Guidance

Different searches may return different kinds of scientific information.

A search for an astronomical object, for example, may return observational datasets, catalogue records, publications and related reference resources.

These results should remain distinguishable while being accessible through a coherent search interface.

The application should provide enough structure to make large result collections manageable without imposing an identical presentation on every resource type.

## 4.3.2 Relevance Evaluation and Ranking

### Core Requirements

- Evaluate search results according to their relevance to the user's search criteria.
- Consider available identifiers, object names, scientific terminology, observation details and other relevant metadata.
- Account for the degree to which a result matches the user's specified requirements.
- Support ranking results by relevance where meaningful.
- Allow users to sort results using other useful criteria, such as observation date, resource type, source or other available metadata.
- Distinguish exact matches from approximate, partial or related matches.
- Communicate when a result is included because of a broader or indirect relationship to the search.
- Avoid presenting relevance ranking as a measure of scientific quality or authority.
- Avoid permanently excluding potentially useful results solely because they receive a lower relevance ranking.
- Keep the relevance-ranking approach adjustable as the application's scientific and search capabilities develop.
- Allow ranking criteria and methods to be revised or expanded without unnecessarily redesigning the broader discovery system.
- Document significant changes to ranking methods, criteria, configurations or behaviour.
- Preserve enough information about ranking changes to understand how search-result ordering may have been affected.

### Design Guidance

Relevance ranking should help users find useful information more efficiently, but it should not determine which scientific resources are inherently valuable.

A result may be highly relevant to the search terms while containing limited or unsuitable data. Conversely, a less directly matching result may contain information that becomes important during further investigation.

Ranking should therefore reflect the relationship between the search request and the available result information rather than attempting to assign a universal scientific value to each resource.

Ranking methods should be capable of evolving as the application supports additional resources, metadata and search requirements.

The application should distinguish between changing the ranking method and simply sorting an existing result collection by another available property. These operations serve different purposes and should remain understandable to users.

Where ranking methods or criteria change, the reasons and relevant effects should be documented. This is important because changes to ranking behaviour may alter which resources users encounter first, even when the underlying search results remain unchanged.

## 4.3.3 Search Result Summaries and Descriptive Information

### Core Requirements

Present useful descriptive information for each result where available.

Depending on the resource type, this may include:

- Dataset or resource name.
- Astronomical object or target.
- Observation identifier.
- Resource type.
- Source archive or provider.
- Instrument or observatory.
- Observation date or relevant time range.
- Wavelength range or observational band.
- Available data products.
- Relevant measurement or data categories.
- Dataset description or abstract.
- Publication or reference information.
- Availability or access status.
- Important limitations or warnings.

Allow users to inspect additional information without requiring immediate retrieval of the complete resource.

Distinguish information supplied by the original provider from descriptions or summaries generated by the application.

### Design Guidance

Search-result summaries should prioritize information that helps users decide whether a result deserves further investigation.

The information displayed should depend on the type of resource. An observational dataset may need instrument and observation details, while a scientific reference entry may need authorship, publication information and a description of its subject.

Avoid displaying empty fields or overwhelming users with metadata that is not useful at the current stage of discovery.

## 4.3.4 Result Comparisons and Differentiation

### Core Requirements

- Allow users to compare relevant information across multiple search results.
- Make meaningful differences between datasets and resources identifiable.
- Present comparable metadata consistently where possible.
- Identify differences in source, observation, instrument, date, data product and other relevant characteristics.
- Allow users to distinguish multiple observations of the same astronomical object.
- Support comparison of related results obtained from different archives or providers.
- Preserve source-specific information when comparing results from different resources.
- Avoid implying that results are directly comparable when their underlying characteristics differ.

### Design Guidance

Researchers may need to examine several observations or resources before deciding which ones are appropriate for an investigation.

For example, a search may return multiple observations of the same exoplanet obtained using different instruments, wavelength ranges or observing programs.

The application should make these distinctions understandable without requiring users to retrieve every dataset first.

More detailed scientific compatibility and measurement comparisons are addressed in Section 3.2.

## 4.3.5 Relevance Beyond Exact Matches

### Core Requirements

- Allow relevant results to remain discoverable when they do not exactly match the original search terms.
- Support related object identifiers, alternative names, scientific classifications and associated resources.
- Identify related observations and datasets where relationships can be established.
- Allow broader results to be distinguished from exact matches.
- Explain relevant relationships when a result is included through an indirect match.
- Allow users to narrow or broaden their search after reviewing the results.
- Avoid silently substituting a related resource for the exact resource requested.
- Preserve the ability to inspect results with lower relevance where appropriate.

### Design Guidance

Astronomical research frequently involves alternative object names, catalogue identifiers and relationships between astronomical systems.

A search for a particular object may reasonably return observations associated with its host star, related system components or other scientifically relevant records.

These relationships can improve discovery, but they should remain understandable.

The application should make clear whether a result directly matches the search or is included because of a broader scientific relationship.

## 4.3.6 Result Filtering and Refinement

### Core Requirements

Allow users to refine result collections using available information.

Potential filtering criteria include:

- Resource or data type.
- Astronomical object or target.
- Archive or provider.
- Instrument or observatory.
- Observation date or time range.
- Wavelength range or observational band.
- Available data products.
- Observation or processing status.
- Availability and access conditions.
- Other relevant source-specific metadata.

Allow multiple filters to be combined where appropriate.

Provide a clear indication of which filters are currently active.

Allow users to remove or modify filters without unnecessarily restarting the entire discovery process.

Make it possible to broaden a search when filtering becomes too restrictive.

### Design Guidance

Filtering should help users narrow large result collections without requiring them to understand every technical detail of an external resource.

The available filters should reflect the metadata actually supplied by each provider.

The application should not imply that a filter is universally available when the underlying resource does not provide the required information.

Detailed data selection and scientific compatibility assessment remain separate from search-result filtering.

## 4.3.7 Result Limitations and Uncertainty

### Core Requirements

- Communicate when result descriptions or metadata are incomplete.
- Identify when important information is unavailable from the original source.
- Distinguish missing information from information that has been confirmed not to apply.
- Communicate relevant access restrictions or retrieval limitations where known.
- Identify when a result represents a preview, summary or partial record rather than a complete dataset.
- Preserve provider warnings and relevant limitations.
- Avoid presenting incomplete descriptions as though they represent the full scientific content of a resource.
- Distinguish search relevance from data quality, reliability and scientific suitability.

### Design Guidance

Search results are often based on limited metadata rather than a complete inspection of the underlying scientific data.

The application should avoid implying that a result has been fully evaluated simply because it appears in a search collection.

For example, a result may match an object identifier and wavelength range while lacking information about calibration or measurement uncertainty.

Such limitations should be communicated when known, while leaving detailed quality assessment to the appropriate stages of the research workflow.

## 4.3.8 Result Selection and Further Investigation

### Core Requirements

- Allow users to select individual search results for further inspection.
- Support opening relevant dataset or resource details.
- Allow users to investigate multiple results without losing their search context.
- Provide access to available previews and additional metadata.
- Allow selected results to proceed to the appropriate retrieval or acquisition workflow.
- Preserve the identity and source information of selected results.
- Avoid automatically downloading or permanently retaining selected resources.
- Avoid automatically adding discovered results to research projects.
- Allow users to return to their previous result collection after inspecting an individual resource.

### Design Guidance

Search-result selection should provide a transition from discovery to investigation, not an automatic commitment to acquire or retain data.

Users should be able to examine promising results, compare alternatives and decide which resources are worth retrieving.

The discovery process should remain useful even when a user ultimately decides not to acquire any of the results.

## 4.3.9 Search Result Persistence and History

### Core Requirements

- Allow users to revisit recent search-result collections where practical.
- Preserve relevant search criteria and filtering selections.
- Maintain references to the original sources and result identifiers.
- Identify when previously discovered resources may no longer be available.
- Distinguish saved search information from permanently retained datasets.
- Allow users to revisit a result without assuming that its underlying resource remains unchanged.
- Support useful search-history organization without requiring every search to become part of a research project.

### Design Guidance

Search history can help users revisit earlier discoveries and continue research without repeating unnecessary searches.

However, saving a search or its results should not automatically download or permanently retain the underlying scientific datasets.

Search history, locally cached resources and project-associated research materials serve different purposes and should remain distinguishable.

## General Principles

Search-result relevance, ranking and presentation should:

- Make large collections of scientific search results understandable.
- Distinguish different resource types and their original providers.
- Rank results according to their relevance to the search rather than assumed scientific quality.
- Keep ranking methods and criteria adjustable as search capabilities develop.
- Document significant changes to ranking methods, criteria and behaviour.
- Present useful identifying information and descriptive metadata.
- Support comparison of related observations and resources.
- Preserve relevant results beyond exact search matches.
- Allow progressive filtering and search refinement.
- Communicate missing information and relevant limitations.
- Distinguish search summaries and previews from complete scientific datasets.
- Allow users to investigate results without automatically acquiring or retaining them.
- Preserve useful search context and history.

## General Principle

Search results should help users understand what scientific information is available and why individual resources may be relevant to their research.

The application should make discovery efficient without hiding useful alternatives, confusing relevance with scientific quality or encouraging users to treat search results as already validated research data.

## Implementation Boundary

This subsection establishes requirements for the organization, relevance evaluation, ranking, filtering, comparison and presentation of scientific search results.

It does not prescribe specific search algorithms, ranking models, interface components or implementation technologies.
