

# 5.3 — Data Processing and Transformation Safeguards

## Purpose

The application should provide scientific data processing capabilities while preserving the integrity, meaning and traceability of the underlying information.

Scientific research frequently requires data to be calibrated, filtered, normalized, transformed, corrected, resampled or otherwise prepared before meaningful analysis can take place.

These operations may be necessary, but they can also introduce assumptions, remove information, alter measurements or affect subsequent interpretations.

The application must therefore distinguish original observations from processed and derived data, preserve the ability to revisit previous states and communicate the methods and parameters applied during processing.

Processing should remain scientifically appropriate, transparent and reversible where practical. Users should retain control over consequential transformations, while automated operations must follow the same safeguards as manually performed procedures.

## 5.3.1 Original Data Preservation

### Core Requirements

- Preserve original imported and retrieved scientific datasets.
- Avoid silently overwriting or destructively modifying original observations.
- Maintain a clear distinction between original data and processed or derived representations.
- Preserve original files and source information wherever technically and legally possible.
- Ensure that processing operations create appropriately identified outputs rather than silently replacing source data.
- Allow users to revisit original datasets after processing.
- Preserve relevant original metadata, units, measurement conventions and uncertainty information.
- Identify when an operation cannot preserve all original information.
- Communicate when an operation may result in information loss.
- Prevent automated processing from silently modifying original research materials.

### Design Guidance

Original scientific data should serve as the preserved reference point for subsequent research activities.

For example, applying a baseline correction to an infrared spectrum should produce a derived representation while retaining access to the original measured spectrum.

This allows users to compare the original and corrected data, reconsider processing choices and investigate whether an apparent scientific feature was introduced or affected by the transformation.

## 5.3.2 Derived Data and Processing Outputs

### Core Requirements

- Support the creation of derived datasets through scientific processing operations.
- Identify derived data separately from original source data.
- Preserve relationships between derived datasets and their source materials.
- Allow multiple derived versions to originate from the same original dataset.
- Preserve relevant processing parameters and configurations associated with each derived version.
- Support further processing of previously derived datasets where scientifically appropriate.
- Maintain the ability to identify the sequence of transformations applied to a dataset.
- Distinguish intermediate processing outputs from finalized analytical results.
- Avoid automatically treating derived data as equivalent to original observations.
- Support inspection and comparison of original and derived representations.

### Design Guidance

Scientific processing is often iterative.

A user may create several versions of a dataset using different normalization methods, calibration assumptions or filtering parameters.

The application should accommodate these different processing paths without requiring the user to overwrite previous results or duplicate original source files unnecessarily.

Derived datasets should remain independently identifiable while retaining their relationships to the original observations.

## 5.3.3 Processing Method Identification and Transparency

### Core Requirements

- Identify the processing method applied to a dataset.
- Record relevant operations performed during data preparation and transformation.
- Preserve the parameters and assumptions associated with each operation.
- Distinguish established scientific methods from experimental or user-defined procedures.
- Identify when a method uses approximations or known limitations.
- Make relevant processing information accessible when inspecting derived datasets.
- Communicate when an operation may alter the scientific interpretation of the data.
- Avoid presenting transformed data without identifying significant processing that has been applied.
- Preserve information about the software or external tool used when relevant.
- Support appropriate documentation of manual and automated processing.

### Design Guidance

Users should be able to understand how a dataset reached its current state.

For example, a processed astronomical image may have undergone bias subtraction, dark-frame correction, flat-field correction, background subtraction and image alignment.

The resulting image should retain sufficient information to identify these operations and understand their contribution to the final representation.

## 5.3.4 Scientific Compatibility and Processing Suitability

### Core Requirements

- Evaluate whether a processing operation is appropriate for the selected dataset.
- Consider data type, measurement conventions, units, metadata, uncertainty and scientific context.
- Identify missing information that may prevent reliable processing.
- Detect incompatible input structures or measurement types.
- Communicate when an operation requires assumptions that cannot be verified from available information.
- Avoid applying processing methods solely because a dataset has a recognizable file format or extension.
- Distinguish technical compatibility from scientific suitability.
- Support appropriate alternatives when a selected operation is unsuitable.
- Allow users to inspect relevant compatibility information before consequential processing.
- Avoid silently forcing incompatible data into a processing workflow.

### Design Guidance

A processing operation may be technically executable without being scientifically appropriate.

For example, normalization procedures suitable for one type of spectrum may not be appropriate for another measurement type or research objective.

The application should consider the scientific meaning of the data rather than relying exclusively on its numerical structure.

## 5.3.5 Units, Conventions and Scientific Transformations

### Core Requirements

- Preserve known units and measurement conventions throughout processing.
- Identify when an operation changes the representation or units of a dataset.
- Support scientifically appropriate unit conversions.
- Preserve original values or source representations when conversions are performed.
- Record conversion methods and relevant parameters where necessary.
- Avoid silently assigning units to measurements when they are unknown.
- Distinguish converted values from original measurements.
- Preserve relevant coordinate systems, reference frames and time conventions.
- Identify when transformations require assumptions about units or conventions.
- Communicate when a conversion or transformation may affect scientific interpretation.

### Design Guidance

Scientific transformations frequently involve more than changing numerical values.

For example, converting spectral data between wavelength, frequency and wavenumber requires careful handling of the relationship between the variables and their associated units.

Likewise, changing coordinate systems or time standards can affect the interpretation of astronomical observations.

The application should preserve the scientific context of these transformations and make relevant conversions traceable.

## 5.3.6 Calibration and Correction Procedures

### Core Requirements

- Support scientifically appropriate calibration and correction operations.
- Identify the calibration or correction method applied.
- Preserve relevant calibration data, reference information and parameters where available.
- Distinguish calibrated measurements from uncalibrated observations.
- Identify when calibration information is missing or incomplete.
- Communicate assumptions and limitations associated with correction procedures.
- Preserve original observations alongside calibrated or corrected representations.
- Support comparison between original and corrected datasets.
- Avoid presenting unverified corrections as established measurements.
- Identify when a calibration procedure may be unsuitable for the available data.

### Design Guidance

Calibration and correction procedures are often essential to observational astronomy, but their validity depends on the instrument, observational conditions and scientific context.

Examples include wavelength calibration, photometric calibration, detector corrections, background subtraction, instrumental response correction and atmospheric corrections.

The application should not assume that every dataset requires the same calibration procedures or that a successful correction automatically produces scientifically reliable measurements.

## 5.3.7 Filtering, Cleaning and Data Exclusion

### Core Requirements

- Support appropriate filtering, cleaning and exclusion operations.
- Preserve information about excluded, masked or modified data points.
- Distinguish invalid measurements from valid but unusual observations.
- Identify the criteria used to remove or exclude data.
- Allow users to inspect excluded information where appropriate.
- Avoid silently deleting observations because they differ from expected patterns.
- Support comparison between original and filtered datasets.
- Preserve relevant uncertainty and quality information.
- Communicate when filtering may introduce bias or affect scientific conclusions.
- Allow users to reconsider or modify exclusion criteria.

### Design Guidance

Removing data points may be necessary to address known instrumental errors, corrupted measurements or other identifiable problems.

However, unusual measurements may also represent genuine scientific phenomena.

For example, an unexpectedly high signal in an astronomical time series could be an instrumental artifact, a transient event or a genuine flare.

The application should preserve excluded information and make the reason for exclusion understandable rather than automatically treating statistical unusualness as evidence of invalidity.

## 5.3.8 Resampling, Interpolation and Resolution Changes

### Core Requirements

- Support scientifically appropriate resampling and interpolation operations.
- Identify when new values are calculated rather than directly measured.
- Preserve information about the original sampling and resolution.
- Record relevant interpolation methods and parameters.
- Identify when resampling changes the effective resolution or sampling characteristics of a dataset.
- Communicate limitations introduced by interpolation or extrapolation.
- Distinguish measured values from interpolated or extrapolated values.
- Avoid implying that increasing the number of data points increases the underlying observational information.
- Preserve original datasets for comparison.
- Identify when resampling may affect subsequent analysis.

### Design Guidance

Resampling and interpolation can make datasets easier to compare or process, but they do not create new observational evidence.

For example, interpolating a sparsely sampled spectrum onto a finer wavelength grid may produce a smoother representation without increasing the instrument's spectral resolution.

The application should communicate this distinction and preserve the original sampling characteristics.

## 5.3.9 Normalization, Scaling and Mathematical Transformations

### Core Requirements

- Support appropriate normalization, scaling and mathematical transformations.
- Identify the transformation applied and its purpose.
- Preserve relevant original measurement values.
- Record normalization references, scaling factors and other relevant parameters.
- Distinguish absolute measurements from normalized or relative representations.
- Identify when a transformation changes the physical interpretation of a quantity.
- Avoid comparing differently transformed datasets as though they share identical measurement conventions.
- Communicate when transformations may remove meaningful absolute information.
- Support inspection and comparison of original and transformed representations.
- Preserve sufficient information to reproduce the transformation.

### Design Guidance

Normalization and scaling can make comparisons easier, but they can also remove information that is scientifically important.

For example, normalizing two spectra to their respective maximum intensities may allow comparison of spectral shapes while removing differences in absolute signal strength.

The application should make clear what information is retained and what information is no longer represented directly.

## 5.3.10 Processing Configurations and Reusable Procedures

### Core Requirements

- Allow users to save and reuse appropriate processing configurations.
- Preserve relevant parameters and methodological assumptions.
- Support modification and duplication of existing configurations.
- Allow configurations to be associated with relevant projects or workspaces.
- Identify the processing methods and operations contained in a configuration.
- Check compatibility before applying configurations to different datasets.
- Communicate when a configuration requires missing or incompatible information.
- Preserve configuration history when changes may affect scientific results.
- Distinguish user-defined configurations from established scientific procedures.
- Avoid automatically applying configurations to unsuitable datasets.

### Design Guidance

Reusable configurations can improve efficiency and consistency across repeated research activities.

For example, a user may save a processing configuration for a particular type of spectroscopic observation and apply it to other compatible datasets.

However, identical parameters do not necessarily produce scientifically equivalent results when datasets differ in instrument characteristics, measurement conventions or observational conditions.

The application should therefore evaluate compatibility rather than assuming that a saved configuration is universally applicable.

## 5.3.11 Automated Processing Safeguards

### Core Requirements

- Apply the same scientific processing safeguards to automated and manually initiated operations.
- Identify significant operations performed automatically.
- Preserve the parameters, assumptions and sequence of automated processing steps.
- Prevent automation from silently overwriting original datasets.
- Identify when automated processing encounters missing, ambiguous or incompatible information.
- Request user input when consequential methodological decisions cannot be made reliably.
- Communicate significant processing warnings and failures.
- Allow users to inspect automated processing results.
- Preserve completed work when subsequent operations fail where practical.
- Avoid treating successful automated execution as proof of scientific validity.

### Design Guidance

Automation should make processing more efficient without concealing how data was transformed.

For example, an automated workflow may apply a recognized calibration procedure to compatible observations. However, when required calibration information is missing or ambiguous, the application should request appropriate intervention rather than silently substituting unsupported values or assumptions.

These requirements should remain consistent with the four automation levels established in Section 5.2.

## 5.3.12 Processing Errors, Reversal and Recovery

### Core Requirements

- Identify processing errors and unsuccessful operations.
- Distinguish incomplete operations from successfully completed transformations.
- Preserve original and previously valid derived datasets when processing fails.
- Support undoing or reversing supported operations where practical.
- Allow users to return to previous processing states.
- Identify when an operation cannot be fully reversed.
- Preserve relevant information about failed or interrupted operations.
- Avoid silently retaining incomplete outputs as though they were valid.
- Support recovery from interrupted multi-step processing workflows.
- Communicate when recovery may require repeating an operation or retrieving missing resources.

### Design Guidance

Processing errors should not leave users uncertain about the condition of their research data.

Where practical, operations should preserve previous valid states so users can recover without losing their original observations or earlier work.

Some transformations may not be mathematically reversible, particularly when they involve information removal or lossy conversion. These limitations should be identified before or during the operation.

## 5.3.13 Processing History and Data Relationships

### Core Requirements

- Maintain relationships between original datasets, derived versions and subsequent processing operations.
- Record the sequence of transformations applied to derived data.
- Identify which source datasets contributed to a particular output.
- Preserve relevant processing parameters and configurations.
- Support branching processing workflows from common source datasets.
- Allow users to inspect and compare different processing paths.
- Identify dependencies between processing operations and their outputs.
- Preserve relationships when datasets are reorganized or moved between workspaces and projects.
- Avoid breaking research relationships when derived datasets are copied or transferred.
- Coordinate processing history with the analysis-level reproducibility requirements in Section 5.5.

### Design Guidance

Scientific processing should support iterative investigation without losing the history of previous decisions.

For example, a user may create two derived spectra from the same observation, applying different baseline correction methods to investigate their effects.

Both processing paths should remain identifiable and connected to the same original observation.

The application should preserve these relationships without requiring unnecessary duplication of the original source data.

## General Principles

Data processing and transformation safeguards should:

- Preserve original scientific observations and source materials.
- Maintain clear distinctions between original, processed and derived datasets.
- Identify processing methods, parameters and assumptions.
- Evaluate scientific compatibility before applying transformations.
- Preserve units, measurement conventions and uncertainty information.
- Make calibration, correction, filtering and normalization operations transparent.
- Identify when transformations introduce calculated values or remove information.
- Preserve excluded or modified observations where practical.
- Support reusable configurations with appropriate compatibility checks.
- Apply consistent safeguards to manual and automated processing.
- Support recovery and access to previous valid processing states.
- Maintain traceable relationships between source data and derived outputs.

## General Principle

Scientific processing should improve the usability and analytical value of data without obscuring its origin, altering its meaning without justification or destroying the ability to evaluate previous research decisions.

Every significant transformation should remain understandable, appropriately qualified and traceable to its source.

## Implementation Boundary
