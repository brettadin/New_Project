# 4.5 — Data Retrieval, Import and Acquisition

## Purpose

The application should provide flexible and reliable ways to acquire scientific data from external resources and import user-provided files.

Research may involve retrieving observations from astronomical archives, downloading scientific datasets, importing files produced by instruments or external software, and incorporating previously collected research materials.

The application should accommodate these different acquisition methods without unnecessarily restricting users to particular providers, file formats or predefined workflows.

Data acquisition should balance convenience with scientific reliability. Users should be able to inspect and validate data when necessary while retaining the option to perform straightforward or large-scale imports without excessive manual intervention.

The acquisition process should support exploratory research without requiring users to create a permanent project or retain every resource they investigate.

Original files must remain unchanged. Retrieved and imported data should retain their source information, metadata and relevant relationships, while any interpretation, conversion or preparation should remain identifiable and traceable.

## 4.5.1 External Data Retrieval

### Core Requirements

- Allow users to retrieve scientific data from supported external archives, databases and other resources.
- Support retrieval of observations, datasets, measurements, catalogue records and other relevant scientific products.
- Allow users to select individual resources or multiple resources for retrieval.
- Support retrieval through available provider interfaces, APIs, download services and other appropriate access methods.
- Identify the external source and relevant resource identifiers.
- Provide information about the data products available before retrieval where practical.
- Allow users to inspect relevant metadata and descriptions before deciding whether to retrieve a resource.
- Support retrieval of selected data products rather than requiring users to download entire collections unnecessarily.
- Accommodate resources that provide direct downloads as well as those requiring external access.
- Communicate access restrictions, unavailable resources and retrieval limitations.
- Allow retrieved resources to be directed into an appropriate scientific workspace or other suitable working environment.
- Preserve the distinction between retrieving a resource for examination and deliberately retaining it for longer-term use.

### Design Guidance

Data discovery and data retrieval should remain separate actions.

Finding a potentially useful dataset should not automatically download it, add it to a project or permanently retain it.

Users should be able to investigate available resources and decide which ones they actually need.

The application should also distinguish between retrieving an original observation, a processed data product, a catalogue record and other forms of scientific information.

## 4.5.2 User-Provided Data and File Import

### Core Requirements

- Support importing a wide range of user-provided scientific and astronomical data.
- Accommodate recognized formats, less common formats and unfamiliar files that may contain useful scientific information.
- Support data originating from instruments, observatories, external scientific software, research institutions and other sources.
- Allow users to import individual files and collections of files.
- Avoid restricting users to a small fixed list of file extensions.
- Attempt to identify file types, structures, encodings, metadata and scientific content automatically.
- Recognize potentially useful data structures even when files do not match a known format exactly.
- Attempt alternative approaches to inspect or extract usable information when direct format support is unavailable.
- Explain what was successfully recognized, what could not be interpreted and whether additional information or user intervention is required.
- Preserve original files unchanged.
- Create separate representations when conversion, extraction or interpretation is necessary.
- Allow partially interpretable files to provide usable information while clearly identifying unsupported portions.
- Support expansion to additional formats and data structures as requirements develop.

### Design Guidance

The application should avoid unnecessarily restricting users based on file extensions or a fixed list of supported formats.

Researchers may work with older instrument outputs, specialized software exports, institution-specific files and other data representations that cannot always be recognized automatically.

The application should attempt to make useful information accessible without pretending to understand scientific content it cannot reliably interpret.

Recognizing a file or extracting numerical values does not necessarily establish what those values represent.

## 4.5.3 File Recognition and Import Inspection

### Core Requirements

During import, attempt to identify and inspect:

- File format and relevant internal structures.
- File encoding and organization.
- Available headers and metadata.
- Data tables, columns, fields and channels.
- Numerical and non-numerical content.
- Measurement types and scientific quantities where identifiable.
- Available units and measurement conventions.
- Astronomical objects and associated identifiers where available.
- Instrument, telescope and observational information.
- Observation dates, times and other relevant conditions.
- Available uncertainty and quality information.
- Unsupported, unrecognized or potentially problematic portions.

Distinguish between information that is:

- Explicitly present in the original file.
- Automatically identified with sufficient confidence.
- Inferred from available information.
- Supplied or corrected by the user.
- Unknown or not reliably interpretable.

Allow users to inspect the results of automatic recognition before accepting an interpretation where appropriate.

### Design Guidance

Import inspection should establish what the application can reliably determine about a file.

The application should not silently assign scientific meanings to columns, units or measurements based on assumptions that cannot be justified.

Where recognition is incomplete, users should be able to provide additional information through the manual mapping process described below.

## 4.5.4 Manual Data Mapping and Unfamiliar Formats

### Core Requirements

When automatic recognition cannot reliably identify the structure or scientific meaning of imported data, provide a manual data-mapping interface.

Allow users to:

- Assign scientific meanings to columns, fields or data channels.
- Identify measurement types such as wavelength, intensity, flux, time, uncertainty and other relevant quantities.
- Specify or correct units and measurement conventions.
- Identify headers, metadata and relevant data regions.
- Resolve ambiguities when multiple interpretations are possible.
- Identify relationships between different data components where necessary.
- Preview the interpreted data before accepting the mapping.

Allow user-defined mappings to make otherwise unsupported or unfamiliar data usable within appropriate scientific capabilities.

Support inspection and, where practical, saving mappings for reuse with similar files or formats.

Maintain a distinction between original metadata and interpretations supplied by the user.

Communicate uncertainty when a mapping cannot be established confidently.

### Design Guidance

Manual mapping should provide a practical alternative when automatic interpretation is insufficient.

For example, a user may import a text file containing two numerical columns but no recognizable headers. The application may identify the structure as tabular data without knowing whether the columns represent wavelength, intensity, time, flux or another measurement.

The user should be able to assign the appropriate meanings and units, inspect the resulting interpretation and decide whether it is suitable for further use.

Saved mappings should be treated as reusable interpretation configurations rather than proof that every file with a similar structure has identical scientific meaning.

The original file must remain unchanged, and the application should preserve the distinction between supplied information and user-defined interpretation.

## 4.5.5 Guided Import and Validation

### Core Requirements

Provide a guided import workflow that allows users to review an import preview and validation report before accepting imported data.

Where possible, identify:

- Recognized file formats and data structures.
- Detected measurements, columns and metadata.
- Missing or incomplete metadata.
- Potential formatting problems.
- Invalid or non-numerical values where relevant.
- Potential data-quality concerns.
- Compatibility problems that may affect subsequent analysis.
- Unrecognized or unsupported portions.
- Information requiring user interpretation or correction.

Allow users to:

- Review the proposed interpretation.
- Correct data mappings.
- Supply missing information.
- Resolve identifiable problems.
- Inspect relevant warnings.
- Accept the import when satisfied with the available information.

Preserve unresolved warnings and limitations with the imported data.

### Design Guidance

Guided import should provide sufficient information for users to understand what they are bringing into the application.

It should be particularly useful when importing unfamiliar files, important research datasets or data intended for quantitative analysis.

Validation should help identify problems without implying that a successful import establishes the scientific validity of the data.

## 4.5.6 Streamlined Import and Background Validation

### Core Requirements

Provide a streamlined import workflow that allows users to import files directly into the appropriate working environment without individually reviewing every file or completing a detailed validation process.

Support streamlined importing for routine operations and larger collections of files.

Continue performing appropriate background recognition and validation checks.

Allow users to review detected problems after importing.

Keep files that cannot be interpreted reliably identifiable as requiring attention.

Avoid unnecessarily preventing imports because of non-critical warnings or incomplete metadata.

Communicate failures and significant problems without silently treating unsupported or invalid data as fully interpreted scientific information.

Allow users to inspect and resolve outstanding import issues later.

### Design Guidance

Detailed validation is valuable, but requiring every user to complete the same review process for every file would make routine data acquisition unnecessarily tedious.

The application should balance scientific reliability with practical usability.

Users should be able to choose between detailed guided review and streamlined importing while retaining access to the relevant validation information.

Streamlined importing must not bypass essential safeguards or falsely imply that every imported file is ready for scientific analysis.

## 4.5.7 Batch Import and Multiple Data Sources

### Core Requirements

- Support importing multiple files together.
- Accommodate collections containing different formats and different types of scientific data.
- Support both guided and streamlined batch-import workflows.
- Allow users to inspect selected files before starting a batch operation where appropriate.
- Provide an overview of the files being processed.
- Identify successfully imported files, warnings, partial imports and failures.
- Allow individual files to be investigated without requiring the entire batch to be repeated.
- Preserve the identity and source information of each file.
- Avoid treating every file in a batch as though it has the same scientific structure or interpretation.
- Support appropriate reporting of incomplete or unsuccessful batch operations.

### Design Guidance

Batch importing should reduce repetitive work without removing the ability to handle individual files appropriately.

For example, a user may import several spectra from one observation session alongside a collection of images and associated measurement tables.

The application should recognize that these files may have different formats, structures and scientific purposes.

A problem with one file should not unnecessarily prevent unrelated files in the same batch from being imported successfully.

## 4.5.8 Retrieval and Import Progress Management

### Core Requirements

- Provide information about ongoing retrieval and import operations.
- Communicate relevant progress and completion status.
- Identify failed, interrupted or incomplete operations.
- Provide useful information about the cause of failures where available.
- Support cancellation of ongoing operations where technically possible.
- Accommodate large downloads and imports that may require extended processing.
- Support appropriate recovery or resumption of interrupted operations where the external service and data format permit.
- Avoid presenting partially retrieved or imported data as complete.
- Preserve successfully completed work when unrelated operations fail.
- Allow users to review the status of multiple simultaneous operations.
- Communicate relevant information about retrieval size, estimated storage requirements and progress where available.

### Design Guidance

Retrieval and import operations may vary substantially in size and duration.

A small catalogue query may complete quickly, while a large observational dataset or collection of instrument files may require considerably more time.

The application should communicate the state of these operations without unnecessarily interrupting the user's research workflow.

Where an operation cannot be resumed safely, the application should explain what remains incomplete and what would be required to retry it.

## 4.5.9 Automatic Data Organization

### Core Requirements

Where the application can identify meaningful relationships between imported or retrieved files, it should offer to organize them into logical groups.

Potential grouping criteria include:

- Astronomical object or target.
- Observation session or observation date.
- Instrument or telescope.
- Data type or measurement technique.
- Research source or archive.
- Related observations or datasets.
- Other identifiable scientific relationships.

Allow users to:

- Review and modify automatically suggested groupings.
- Manually organize files when automatic grouping is unavailable or incorrect.
- Move files between groups.
- Combine or separate groups as needed.
- Leave files ungrouped when appropriate.
- Decline suggested organization.

Base automatic organization on available metadata and identifiable relationships rather than unsupported assumptions.

Preserve original files, metadata and provenance regardless of how files are grouped.

### Design Guidance

Automatic organization should reduce the effort required to manage research materials without restricting the user's preferred organizational approach.

For example, multiple spectra of the same astronomical object could be suggested for grouping, as could observations from the same instrument or files belonging to a common observation session.

However, files should not be grouped solely because their names appear similar when the underlying scientific relationship cannot be established reliably.

The user should remain in control of accepting, modifying or rejecting suggested groupings.

Project organization and persistent research-material management are addressed in Section 6.

## 4.5.10 Original Data Preservation and Derived Representations

### Core Requirements

- Preserve original user-provided files and externally retrieved source files unchanged.
- Avoid overwriting original files during import, conversion, interpretation or preparation.
- Create separate representations for converted, extracted, mapped or otherwise transformed data.
- Maintain relationships between original files and their derived representations.
- Record relevant transformations, interpretation decisions and processing parameters.
- Preserve original metadata alongside additional user-supplied or application-generated information.
- Identify when information has been omitted, altered or approximated during conversion.
- Allow users to identify which representation is original and which has been modified.
- Support recovery or retrieval of the original source where technically possible.

### Design Guidance

Importing data should not compromise the integrity of the original scientific material.

The application may need to interpret, restructure or convert data before it can be used by scientific capabilities, but these operations should produce identifiable derived representations.

A user-defined mapping, for example, should not alter the original file. It should establish an additional interpretation that can be inspected, revised and reused.

## 4.5.11 Retrieval and Import History

### Core Requirements

- Maintain appropriate records of significant retrieval and import operations.
- Identify the original source or user-provided file.
- Record relevant retrieval or import dates.
- Preserve source identifiers and available version information.
- Record the files and data products successfully acquired.
- Identify warnings, failures and incomplete operations.
- Preserve relevant manual mappings and interpretation decisions.
- Record significant conversions or transformations performed during acquisition.
- Allow users to revisit relevant retrieval and import information.
- Support searching and filtering retrieval and import history using available information, such as source, object, resource type, date, operation status and data type.
- Allow users to inspect the outcome of previous retrieval operations without assuming the resource remains available externally.
- Maintain relationships between acquired data and the research materials that subsequently use it.

### Design Guidance

Retrieval and import history should help users understand where research data came from, how it entered the application and what happened during acquisition.

Searchable and filterable history is particularly useful when users have acquired many resources over an extended period.

These records should complement the broader provenance and analysis-history requirements established elsewhere rather than creating a disconnected duplicate record system.

Retrieval history should also remain distinct from a permanent local resource library or project history. Recording an acquisition does not necessarily mean that the underlying data must be retained indefinitely.

## 4.5.12 Import Configuration and Reusable Mappings

### Core Requirements

- Allow users to save suitable import configurations.
- Support reuse of manual mappings for similar files and data structures.
- Allow saved mappings to be inspected, modified and deleted.
- Preserve the distinction between original file metadata and user-defined interpretations.
- Identify when a saved mapping may not be suitable for a new file.
- Check structural and scientific compatibility before applying a saved mapping.
- Allow users to choose whether to reuse a suggested mapping.
- Preserve relevant mapping information with imported data.
- Avoid automatically applying saved mappings when their suitability cannot be established.

### Design Guidance

Reusable import configurations can reduce repetitive work, particularly when users regularly handle files produced by the same instrument or software.

However, similar file structures do not guarantee identical measurement meanings or units.

The application should identify potentially suitable mappings and allow users to confirm their application rather than assuming that a previous interpretation is always correct.

## 4.5.13 Retrieval and Import Error Handling

### Core Requirements

- Identify and communicate retrieval and import failures.
- Distinguish between external service failures, access restrictions, incomplete downloads, unsupported formats, invalid structures and interpretation problems.
- Preserve successfully acquired information when an unrelated part of an operation fails.
- Avoid silently discarding partially retrieved or interpreted data.
- Provide useful information about the cause of a failure where available.
- Identify whether the problem may be resolved through retrying, providing additional information, changing access settings or using another method.
- Preserve relevant error and warning information.
- Allow users to review unresolved problems later.
- Avoid repeatedly attempting operations that are known to be unsupported or unsuitable without a meaningful change in conditions.

### Design Guidance

Not every unsuccessful retrieval or import represents a problem with the scientific data itself.

External services may be temporarily unavailable, credentials may be missing, file structures may be unsupported or data may be incomplete.

The application should identify the nature of the problem as accurately as possible and help users determine an appropriate next step.

## 4.5.14 Large Dataset and Selective Retrieval

### Core Requirements

- Accommodate scientific resources that are too large or inefficient to retrieve in their entirety for routine inspection.
- Support metadata-first inspection where providers make sufficient descriptive information available.
- Allow users to examine available resource descriptions, data products and previews before retrieving substantial amounts of data.
- Support selective retrieval of relevant observations, files, data products, wavelength ranges, time ranges, spatial regions or other available subsets.
- Support progressive or staged retrieval where the provider and resource permit it.
- Consider remote access or partial-data access when retrieving an entire resource is unnecessary or impractical.
- Communicate estimated resource size and storage requirements before substantial retrieval where information is available.
- Clearly distinguish retrieved portions from complete datasets.
- Identify when an analysis requires data that has not yet been retrieved.
- Preserve the relationship between selectively retrieved portions and their original source resource.
- Allow users to retrieve additional portions or the complete resource later when needed.
- Preserve retrieval progress and identify incomplete or interrupted operations.

### Design Guidance

Astronomical observations can contain substantial amounts of information, particularly for image collections, spectral cubes, time-series observations and large survey products.

The application should not assume that users must download every available data product before they can determine whether a resource is useful.

Where possible, users should be able to inspect metadata and previews, retrieve selected portions, and expand the retrieval as their investigation develops.

For example, a user may initially need only a particular wavelength range or observation product to determine whether a dataset is suitable for further analysis.

Selective retrieval must not imply that a partial dataset is equivalent to the complete original resource. The application should communicate the scope and limitations of the retrieved material.

## 4.5.15 Exploratory Workspaces and Transfer to Projects

### Core Requirements

- Allow retrieved and imported resources to be examined in an appropriate scientific workspace before users decide whether to retain them for longer-term research.
- Support exploratory work without requiring users to create a formal research project first.
- Allow users to use a workspace temporarily for inspection, comparison and preliminary analysis.
- Support saving an exploratory workspace independently of a research project where appropriate.
- Preserve the relationship between an exploratory workspace and the resources, configurations, visualizations, annotations and notes associated with it.
- Allow users to explicitly retain selected resources and exploratory work in a research project.
- Support transferring selected datasets, observations and relevant workspace materials into an existing or newly created project.
- Preserve available metadata, provenance, source information, processing history, configurations, graphs, annotations, notes and relationships during transfer.
- Allow users to choose which materials are transferred rather than requiring the entire exploratory workspace to be retained.
- Preserve original source data and distinguish it from workspace-specific or project-specific derived materials.
- Avoid duplicating large underlying datasets unnecessarily when multiple projects or workspaces reference the same resource.
- Ensure that transferring materials into a project does not unexpectedly alter or invalidate the original exploratory workspace.
- Maintain clear distinctions between temporary workspace materials, independently saved workspace materials and project-associated research materials.

### Design Guidance

The application should support a natural progression from discovery to investigation and, where appropriate, persistent research.

A user may retrieve an observation, examine its contents, compare it with reference data and perform preliminary analysis without yet deciding whether it belongs in a formal project.

The user should be able to continue exploring without being forced to create a project or permanently retain every resource.

When an investigation becomes worth preserving, the user should be able to transfer the relevant materials into a project while retaining their scientific context and relationships.

For example, a user may inspect several observations of an astronomical target, compare their available wavelength coverage and identify one dataset suitable for further analysis. They should be able to retain that dataset and its relevant exploratory work without automatically retaining every resource examined during the search.

Workspace saving, project organization and persistent research management are addressed further in Section 6.4.

## 4.5.16 Configurable Retrieval and Retention Preferences

### Core Requirements

- Allow users to establish preferences governing how retrieved and imported resources are handled after acquisition.
- Support configurable retention behavior for different resource types and acquisition categories.
- Allow users to distinguish between temporary retrieval, temporary caching, deliberate local retention and project-associated resources.
- Support automatic retention preferences where appropriate, without requiring every resource to be retained indefinitely.
- Allow retention behavior to be configured according to relevant characteristics, such as data type, resource type, source or size where practical.
- Provide sensible default behavior that avoids unnecessary permanent storage.
- Make the active retention behavior understandable before or during acquisition where appropriate.
- Allow users to change retention preferences without unintentionally deleting previously retained research materials.
- Ensure project-associated resources and independently saved workspace materials are protected from automatic cleanup.
- Avoid silently changing the retention status of previously acquired resources when global preferences are modified.
- Identify when a resource is retained because it is associated with a project or another saved research activity.
- Coordinate retention preferences with local storage and cache-management requirements in Section 4.9.

### Design Guidance

Users may have different preferences for different types of scientific resources.

For example, a user may prefer to retain small reference datasets automatically while treating large observational datasets as temporary until they have been examined.

The application should support such distinctions without requiring users to manually manage every acquisition.

Automatic retention should remain understandable and controllable. It must not silently convert temporary resources into permanent research materials or remove resources that have become part of a saved investigation.

Changing a future retention preference should not automatically rewrite the historical retention decisions associated with existing resources.

## General Principles

Data retrieval, import and acquisition should:

- Support both external data retrieval and user-provided scientific files.
- Accommodate diverse formats, structures and sources.
- Avoid unnecessary restrictions based on file extensions.
- Attempt useful interpretation of unfamiliar data without inventing scientific meaning.
- Provide manual mapping when automatic interpretation is insufficient.
- Offer guided and streamlined import workflows.
- Support mixed-format batch importing.
- Perform appropriate validation and communicate unresolved issues.
- Offer automatic organization without removing user control.
- Preserve original files and maintain traceable derived representations.
- Support reusable import configurations and mappings.
- Maintain searchable and filterable retrieval and import history.
- Accommodate large datasets through metadata-first inspection, selective retrieval and progressive access where possible.
- Support exploratory research without requiring immediate project creation.
- Allow selected exploratory work and resources to be transferred into persistent projects.
- Preserve scientific context and relationships during acquisition and transfer.
- Support configurable retention preferences while protecting saved research.
- Communicate failures, limitations and incomplete operations clearly.

## General Principle

Data acquisition should be flexible enough to accommodate the diverse ways researchers obtain scientific information while preserving the integrity and traceability of the underlying material.

Users should be able to discover, retrieve, inspect and use scientific resources efficiently without being forced into unnecessary project creation, permanent storage or repetitive validation procedures.

Convenience must never depend on pretending that unfamiliar or insufficiently understood data is scientifically verified, or on silently losing the context and relationships needed to understand acquired research materials.
