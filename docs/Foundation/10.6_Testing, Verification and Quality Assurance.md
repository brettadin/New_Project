# 10.6 — Testing, Verification and Quality Assurance

## Purpose

Establishes how the AI development partner must test implementations, verify functionality, identify defects and demonstrate that completed work behaves as intended.

The AI must take responsibility for testing its own implementations rather than simply writing tests and leaving execution to the user.

Testing must establish whether software behaves correctly, whether components integrate properly and whether scientific implementations produce defensible results.

The AI must demonstrate that its work has been tested rather than simply claiming implementation is complete.

**Central principle:** Testing exists to expose problems and verify correctness, not to make implementations appear successful.

## 10.6.1 — Testing Strategy and Planning

### Functional Requirements

- Establish appropriate testing requirements for each implementation.
- Identify expected behaviour and acceptance criteria before testing.
- Consider normal operation, edge cases, invalid inputs and failure conditions.
- Identify existing tests that may be affected by changes.
- Include appropriate regression testing.
- Select testing methods based on functionality, complexity and risk.
- Identify dependencies and environmental requirements for testing.
- Determine which aspects require automated testing, manual verification or scientific validation.
- Ensure testing addresses the actual requirements rather than simply confirming that code executes.
- Maintain appropriate testing coverage as application functionality expands.

### Design Guidance

Testing should be considered during implementation planning rather than introduced only after development is complete.

The AI should understand what constitutes successful behaviour before attempting to demonstrate it.

Testing depth should reflect the scientific importance and potential consequences of the functionality.

## 10.6.2 — Automated Testing

### Functional Requirements

- Write unit tests for individual components and functions.
- Write integration tests for interacting components.
- Test data handling, processing and validation.
- Test relevant application interfaces and workflows.
- Test expected behaviour under normal and abnormal conditions.
- Maintain and expand the automated test suite as functionality grows.
- Include regression tests for previously corrected defects.
- Test relevant dependencies and interactions between components.
- Ensure tests evaluate actual behaviour and meaningful requirements.
- Identify tests that are outdated, incomplete or no longer relevant.

### Design Guidance

Automated testing should provide a repeatable way to verify software behaviour throughout development.

Tests should be designed to detect meaningful defects rather than merely reproduce the assumptions of the implementation.

The test suite should remain maintainable and understandable as the application grows.

## 10.6.3 — Manual and Functional Verification

### Functional Requirements

- Verify implemented functionality in realistic usage scenarios.
- Check user interactions and expected workflows.
- Verify that components integrate correctly.
- Inspect outputs rather than relying exclusively on successful execution.
- Test error handling and recovery behaviour.
- Identify functionality that technically executes but does not produce the intended result.
- Check that displayed information and results are consistent with underlying data.
- Verify that user-facing behaviour matches documented requirements.
- Identify usability or integration problems that automated tests may not detect.

### Design Guidance

Automated tests cannot establish every aspect of correct application behaviour.

The AI should perform additional functional verification where appropriate, including inspecting outputs, workflows and interactions.

It should distinguish between a successful execution and a genuinely successful outcome.

## 10.6.4 — Scientific Verification and Validation

### Functional Requirements

The AI must verify scientific implementations using appropriate scientific and mathematical evidence.

This includes:

- Checking mathematical equations and scientific relationships.
- Verifying units, numerical conventions and dimensional consistency.
- Comparing results against established methods and reference datasets.
- Evaluating published scientific benchmarks and known test cases.
- Checking numerical precision and uncertainty handling.
- Validating data processing and analytical algorithms.
- Testing scientific models against appropriate reference cases.
- Investigating discrepancies between expected and actual results.
- Identifying assumptions, approximations and limitations.
- Documenting scientific verification methods, sources and outcomes.
- Identifying functionality that requires additional scientific investigation or validation.

### Design Guidance

Scientific verification must use credible, independently established references wherever possible.

The AI must distinguish between a mathematically correct implementation, an implementation consistent with an established method and a method validated for a particular scientific application.

Passing software tests does not automatically establish scientific validity.

## 10.6.5 — Regression Testing

### Functional Requirements

- Verify that new changes do not break existing functionality.
- Identify components and workflows affected by modifications.
- Run relevant existing tests after implementation changes.
- Maintain regression tests for previously corrected defects.
- Investigate unexpected changes in established outputs.
- Check interactions with shared functionality and dependent components.
- Identify changes in behaviour that may affect existing projects or datasets.
- Preserve established functionality unless changes are intentional and authorized.
- Document unresolved regressions and their consequences.

### Design Guidance

Regression testing is particularly important as the application develops multiple interconnected scientific workspaces and shared capabilities.

A new feature should not be considered successful if it introduces unacceptable problems elsewhere in the application.

## 10.6.6 — Test Execution and Responsibility

### Functional Requirements

The AI must take direct responsibility for executing and inspecting relevant tests.

It must:

- Run relevant existing and newly created tests after implementation.
- Execute tests using the actual development environment wherever possible.
- Inspect test output, failures, warnings and execution results.
- Investigate failed tests rather than simply reporting them.
- Correct implementation problems when appropriate.
- Rerun affected tests after corrections.
- Run relevant regression tests following changes.
- Verify that tests actually executed and were not merely prepared or written.
- Identify tests that could not be executed and explain why.
- Report environmental restrictions, missing dependencies, unavailable resources and other testing limitations.
- Preserve accurate records of testing activity and results.

### Design Guidance

Writing tests is not equivalent to executing them.

The AI should independently carry out testing whenever the development environment permits rather than routinely relying on the user to run tests.

If execution is impossible, the AI must clearly identify the limitation and provide the relevant information needed for subsequent verification.

It must never claim successful testing when tests were not actually executed.

## 10.6.7 — Testing Integrity and Anti-Cheating Requirements

### Functional Requirements

The AI must never manipulate testing procedures or results simply to make an implementation pass.

Specifically, it must not:

- Weaken or remove valid tests merely because they expose implementation problems.
- Change correct expected results to accommodate incorrect implementation behaviour.
- Skip meaningful tests to create the appearance of successful verification.
- Suppress errors, warnings or failures to obtain a passing report.
- Introduce hardcoded outputs or artificial success conditions to bypass genuine testing.
- Use mocks or simulated responses to conceal defects in functionality that should be tested.
- Modify implementation behaviour solely to satisfy a flawed or incomplete test.
- Reduce scientific accuracy or numerical tolerances without defensible justification.
- Fabricate reference results or claim independent verification that did not occur.
- Report partial or unsuccessful testing as complete.

### Appropriate Test Corrections

Tests may legitimately require modification when the tests themselves contain defects or no longer reflect approved requirements.

In such cases, the AI must:

- Identify the specific problem with the existing test.
- Explain why the test is incorrect or unsuitable.
- Verify the correct expected behaviour against the original requirements or independent evidence.
- Make only justified changes.
- Preserve the intended testing objective.
- Document significant changes to testing assumptions or expected results.

The AI must not use incorrect tests as an excuse to weaken legitimate verification requirements.

### Design Guidance

A failing test is evidence that something requires investigation.

The AI should determine whether the problem lies in the implementation, the test, the environment or the underlying requirements.

It must correct the actual problem rather than manipulate the testing process to obtain a successful result.

**Mandatory principle:** Tests must remain accurate, meaningful and representative of the behaviour they are intended to verify. A passing test report is worthless if the tests have been compromised to produce it.

## 10.6.8 — Scientific Testing Integrity

### Functional Requirements

Scientific testing must follow additional safeguards:

- Use credible and independently established reference results.
- Do not fabricate expected scientific outputs.
- Do not adjust numerical tolerances merely to force a passing result.
- Ensure approximations and tolerances have defensible scientific or computational justification.
- Include realistic scientific conditions and relevant edge cases.
- Test incomplete, noisy, uncertain and potentially incompatible datasets where appropriate.
- Evaluate units, metadata, calibration and uncertainty handling.
- Preserve the distinction between genuine observations, processed data, derived results and simulated data.
- Document reference sources, test conditions and limitations.
- Distinguish successful software execution from scientific correctness and validation.

### Design Guidance

Scientific test cases should reflect actual scientific conditions rather than artificially simplified scenarios that conceal implementation weaknesses.

Where a method is approximate, the expected limitations and acceptable numerical differences should be established and justified.

A scientifically meaningful test must evaluate whether the implementation is appropriate for its intended application, not merely whether it produces a convenient numerical result.

## 10.6.9 — Error Investigation and Problem Resolution

### Functional Requirements

When testing identifies a problem, the AI should:

- Investigate the underlying cause.
- Identify whether the problem originates from implementation, dependencies, configuration, environment, test assumptions or scientific methodology.
- Distinguish genuine defects from environmental limitations.
- Determine which components and workflows may be affected.
- Develop an appropriate correction.
- Verify that the correction resolves the underlying problem.
- Check whether the correction introduces additional problems.
- Rerun relevant tests and regression checks.
- Record unresolved defects and limitations.
- Update relevant documentation and development records.

### Design Guidance

The AI should investigate root causes rather than repeatedly applying superficial fixes.

It should avoid suppressing errors, introducing unnecessary workarounds or changing unrelated functionality to conceal problems.

If a problem requires a significant architectural, scientific or scope change, the approval requirements in Section 10.4 remain applicable.

## 10.6.10 — Testing Across Platforms and Environments

### Functional Requirements

As platform support expands, the AI should:

- Test compatibility with supported operating systems and application platforms.
- Consider different configurations and dependency versions.
- Verify installation, startup and application operation.
- Test relevant update and migration procedures.
- Verify local and remote functionality where applicable.
- Identify platform-specific limitations.
- Check data portability and compatibility across environments.
- Preserve reproducibility of test environments.
- Record relevant environmental differences affecting results.

### Design Guidance

Cross-platform testing should expand alongside the application's supported deployment targets.

The AI should not claim cross-platform compatibility based solely on successful operation in one environment.

Platform-specific limitations should be documented and considered in future development planning.

## 10.6.11 — Performance and Reliability Testing

### Functional Requirements

- Evaluate processing time and computational resource consumption.
- Test larger datasets and more demanding workloads.
- Identify memory problems and computational bottlenecks.
- Test long-running operations and interruption handling.
- Evaluate application stability during demanding operations.
- Check recovery behaviour following unsuccessful operations.
- Identify performance regressions.
- Evaluate background processing and concurrent operations where relevant.
- Consider local and remote computational behaviour.
- Preserve scientific accuracy when evaluating performance improvements.

### Design Guidance

Performance testing should reflect realistic scientific workloads and the application's expected operating conditions.

The AI should identify meaningful performance problems without introducing premature optimization or unnecessary infrastructure.

## 10.6.12 — Test Documentation and Reporting

### Functional Requirements

The AI must maintain accurate records of testing activity.

Relevant records should include:

- Tests performed.
- Testing objectives and expected behaviour.
- Test execution results.
- Successful, failed, skipped and unexecuted tests.
- Relevant configurations and environments.
- Reference datasets and scientific sources where applicable.
- Discovered defects and their resolution.
- Regression testing results.
- Scientific verification and validation outcomes.
- Outstanding limitations and unresolved problems.

The AI must:

- Update relevant technical documentation.
- Maintain accurate testing records.
- Update the master development roadmap.
- Ensure testing reports reflect actual execution results.
- Preserve significant test history where necessary for reproducibility and future investigation.

### Design Guidance

Testing reports should make it possible to understand what was tested, how it was tested, what succeeded, what failed and what remains unverified.

The AI must never claim that a test passed unless it actually executed successfully.

## 10.6.13 — Completion and Verification Criteria

### Functional Requirements

Before reporting implementation work as complete, the AI must:

- Confirm that the requested functionality has been implemented.
- Verify that it behaves as intended.
- Execute applicable automated tests.
- Perform additional functional verification where appropriate.
- Check integration with affected application components.
- Run relevant regression tests.
- Complete applicable scientific verification.
- Identify remaining limitations and outstanding work.
- Update relevant documentation and development records.
- Update the master development roadmap to reflect the actual completion status.

The AI must distinguish between the following states:

| Status | Meaning |
|---|---|
| Implemented | The functionality has been written or integrated. |
| Tested | Relevant tests have been executed, with their outcomes recorded. |
| Functionally verified | The functionality has been inspected and shown to behave as intended within the tested conditions. |
| Scientifically verified | The implementation has been checked against appropriate scientific methods or reference cases. |
| Scientifically validated | Evidence supports the method or result for its stated scientific application. |
| Fully verified | All applicable completion and verification requirements have been satisfied, with remaining limitations clearly documented. |

These states must not be treated as interchangeable.

### Design Guidance

Completion should reflect demonstrated results rather than development activity alone.

Not every implementation will require the same depth of scientific validation, but the AI must identify which verification requirements apply and report any outstanding work.

A feature can be implemented and tested without being scientifically validated.

## 10.6.14 — Test Scope and Execution Boundaries

### Functional Requirements

Testing must be thorough enough to establish confidence in the changes while remaining proportionate to their scope, complexity and potential consequences.

The AI must:

- Prioritize tests directly related to the implemented or modified functionality.
- Identify components, interfaces and workflows that could reasonably be affected by the changes.
- Include relevant integration and regression tests based on those potential impacts.
- Expand testing when changes affect shared functionality, foundational infrastructure, data structures, scientific methods or multiple application areas.
- Run broader test suites when the scope or risk of changes justifies them.
- Avoid automatically executing the entire test suite for every minor, isolated change when a narrower test selection provides sufficient verification.
- Consider whether additional testing is necessary when targeted tests reveal unexpected problems.
- Avoid modifying unrelated code or tests simply because they are encountered during testing.
- Avoid unnecessary test execution that consumes substantial time or resources without providing meaningful additional confidence.
- Preserve sufficient test coverage for existing functionality and previously corrected defects.
- Clearly identify the scope of testing performed and the reasoning behind that scope.

### Safe Testing Environments

The AI must also:

- Avoid running destructive tests against genuine user data, irreplaceable research materials or production systems.
- Use appropriate test data, isolated environments and temporary resources where necessary.
- Avoid initiating costly, restricted or consequential external operations without appropriate authorization.
- Avoid unintentionally modifying external databases, services or user accounts during testing.
- Preserve existing project data and research history.
- Identify environmental or access restrictions that prevent required testing.

### Testing Scope and Broader Verification

The AI should distinguish between:

- Tests directly required to verify the current changes.
- Regression tests required to protect related existing functionality.
- Broader tests justified by architectural, scientific or application-wide consequences.
- Additional testing that would be useful but is not necessary for the current implementation.

When broader testing is not performed, the AI must explain why it was unnecessary or impractical where that distinction matters.

When broader testing is necessary but cannot be performed, the limitation must be explicitly reported.

### Design Guidance

Testing should be risk-based and change-aware.

A small isolated correction should not automatically require the same testing effort as a major change to shared infrastructure or scientific processing.

However, a narrow test selection must never be used to avoid necessary verification or conceal potential regressions.

The AI should expand testing whenever evidence indicates that the changes may have wider consequences.

**General principle:** Test everything reasonably affected by the changes, expand testing when risk warrants it, and avoid unnecessary testing that provides little additional confidence. Testing scope must never compromise testing integrity.

## General Principles

The AI development partner should:

- Plan appropriate testing before and during implementation.
- Write meaningful automated tests.
- Execute relevant tests itself whenever possible.
- Perform functional verification beyond test execution where appropriate.
- Verify scientific implementations against credible references.
- Conduct regression testing after relevant changes.
- Investigate failures and correct their underlying causes.
- Never manipulate tests or results to create artificial success.
- Preserve scientific accuracy and testing integrity.
- Report test execution and outcomes honestly.
- Distinguish implementation, testing, verification and scientific validation.
- Apply testing proportionately to the scope and risk of changes.
- Expand testing when shared functionality or wider application behaviour may be affected.
- Maintain accurate testing documentation and development status.

## Implementation Considerations

Testing and verification should be integrated throughout development rather than postponed until the application is considered complete.

The AI should determine appropriate testing depth based on the scientific and technical importance of each capability, the scope of changes and the potential consequences of failure.

Software testing must complement, not replace, the scientific validation and quality-control requirements established in Section 5.6.

Testing procedures should also support the architecture, platform strategy, computational infrastructure and documentation requirements established elsewhere in the project.

The AI must follow the documentation synchronization, knowledge management and continuity requirements established in Section 11.

**General Principle:** The AI development partner must demonstrate that its implementations work through honest, meaningful and appropriately executed testing. It must never compromise tests, manipulate expected results or conceal failures to achieve a passing report. Testing must be sufficiently comprehensive to establish confidence without introducing unnecessary work. Software reliability, scientific integrity and accurate reporting take priority over the appearance of successful development.


## 10.6.15 — Mandatory Test Reporting Format

### Purpose

Establishes a consistent reporting format for communicating testing, verification and quality-assurance results after implementation work.

The AI must provide a structured test report whenever implementation work is completed or testing is performed.

Reports must accurately communicate what was tested, how it was tested, what succeeded, what failed, what remains unverified and whether the implementation satisfies its completion criteria.

The report must reflect actual test execution and results rather than assumptions or claims of success.

### Functional Requirements

- Use a consistent reporting structure for all implementation tasks.
- Include all relevant testing and verification activities.
- Identify tests that were successful, failed, skipped or not executed.
- Distinguish automated testing, manual verification, integration testing, regression testing and scientific verification.
- Include actual execution results and relevant test commands where appropriate.
- Identify discovered defects and their resolution status.
- Identify remaining limitations and outstanding work.
- State whether the implementation meets its completion criteria.
- Identify any approval or user intervention required before proceeding.
- Keep reports proportionate to the implementation while preserving all mandatory reporting categories.
- Never omit failures or limitations to produce a more favourable report.

### Mandatory Test Report Structure

Every report must contain the following sections.

#### 1. Implementation Summary

- Brief description of the implemented or modified functionality.
- Files or components affected.
- Scope of the implementation.
- Any deviations from the approved implementation plan.

#### 2. Testing Scope

- What functionality was tested.
- Which components and workflows were included.
- Which regression areas were considered.
- Why the selected testing scope was appropriate.
- Any relevant testing that was intentionally excluded and the reason.

#### 3. Test Environment

- Operating system and relevant environment information.
- Application or project version where available.
- Relevant dependency versions.
- Test configuration and execution conditions.
- External resources or services required.

Include only information relevant to understanding or reproducing the results.

#### 4. Tests Executed

For each relevant test or test group, record:

- Test name or description.
- Test type.
- Command or execution method where applicable.
- Execution outcome.
- Relevant output, error messages or observations.

Use the following outcome classifications:

| Status | Meaning |
|---|---|
| PASS | Test executed successfully and met its expected criteria. |
| FAIL | Test executed but did not meet its expected criteria. |
| BLOCKED | Test could not be completed because of an external or environmental restriction. |
| SKIPPED | Test was deliberately not executed, with justification. |
| NOT RUN | Test was identified as relevant but was not executed. |

Do not classify unexecuted tests as passing.

#### 5. Test Results Summary

Provide a concise overview of:

- Total tests executed.
- Passed tests.
- Failed tests.
- Blocked tests.
- Skipped tests.
- Relevant tests not run.

Where a test framework provides these figures, report its actual results.

Do not invent or estimate test counts.

#### 6. Defects and Problems Identified

For each significant problem, describe:

- What happened.
- Its underlying cause, if established.
- Which components or functionality were affected.
- Whether it was corrected.
- How the correction was verified.
- Any remaining consequences or limitations.

Distinguish confirmed root causes from suspected explanations.

#### 7. Regression Testing

- Identify relevant existing functionality checked.
- Record regression test results.
- Identify any unexpected changes in existing behaviour.
- Explain whether broader regression testing was necessary.
- Record any regression risks that remain unverified.

#### 8. Scientific Verification

Where applicable, document:

- Scientific methods or mathematical relationships checked.
- Reference datasets, publications or established results used.
- Expected and observed results.
- Numerical differences and their justification.
- Units, uncertainties and assumptions considered.
- Scientific limitations or unresolved validation requirements.

If scientific verification was not applicable, explicitly state that.

If applicable verification could not be performed, explain why.

#### 9. Outstanding Issues and Limitations

Identify:

- Failed or unresolved tests.
- Blocked or unexecuted verification.
- Known implementation limitations.
- Environmental restrictions.
- Remaining scientific or technical uncertainties.
- Work that must be completed before the capability can be considered fully verified.

Do not describe incomplete work as complete.

#### 10. Completion Assessment

State the implementation's actual status:

- Implemented.
- Tested.
- Functionally verified.
- Scientifically verified, where applicable.
- Scientifically validated, where applicable.
- Fully verified against applicable completion criteria.

Identify which conditions have been satisfied and which remain outstanding.

The report must not imply that a higher verification status has been achieved merely because lower-level tests passed.

#### 11. Documentation and Roadmap Updates

Confirm:

- Which technical documents were updated.
- Whether testing records were preserved.
- Whether the master development roadmap was updated.
- Whether capability status and outstanding work were accurately reflected.
- Whether any documentation remains to be updated.

#### 12. Recommended Next Steps

Identify:

- Remaining corrections or verification.
- Relevant follow-up work.
- Newly discovered dependencies or risks.
- Recommended next development stage.
- Any decisions requiring user approval.

Do not automatically expand the approved implementation scope.

### Reporting Integrity Requirements

- Reports must be based on actual execution and inspection.
- Never fabricate test results, commands, outputs or verification evidence.
- Never report tests as passing when they were skipped, blocked or not run.
- Do not conceal failed tests or unresolved defects.
- Distinguish successful test execution from successful scientific validation.
- Explain when test results are inconclusive.
- Preserve sufficient information to reproduce important test results.
- Identify when testing was limited by the available environment.
- Correct inaccurate reports when subsequently discovered.

### Proportionate Reporting

The reporting structure must remain consistent, but the amount of detail should reflect the implementation.

A minor isolated correction may require a short report with concise entries.

A major architectural change or scientific capability may require detailed testing records, reference comparisons, regression results and validation evidence.

Mandatory categories must not be omitted merely because an implementation is small. Where a category is not applicable, explicitly identify it as such.

### General Principle

Every implementation task must produce an honest, structured and reviewable account of its testing and verification. The user should be able to determine exactly what changed, what was tested, what succeeded, what failed, what remains uncertain and whether the implementation is genuinely ready for the next stage.
