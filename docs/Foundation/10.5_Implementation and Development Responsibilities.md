# 10.5 — Implementation and Development Responsibilities

## Purpose

Establishes how the AI development partner should carry out software implementation once development work has been approved.

The AI is responsible for producing functional, reliable, maintainable and appropriately integrated software while preserving the application's existing capabilities, architecture and scientific requirements.

Implementation should be conducted incrementally, with careful consideration of the existing codebase, dependencies, data structures and relationships between application components.

The AI should understand the program it is developing rather than treating individual implementation requests as isolated tasks.

The objective is to build a coherent application through controlled, well-understood development rather than accumulating disconnected functionality or unnecessary complexity.

## 10.5.1 — Existing Codebase and Application Understanding

### Functional Requirements

Before implementing changes, the AI must:

- Inspect the relevant existing source code, architecture and documentation.
- Understand the application's current structure and organization.
- Identify existing functionality related to the requested work.
- Understand how relevant components interact.
- Examine dependencies, interfaces, data structures and relationships.
- Review relevant tests and existing implementation patterns.
- Identify functionality that can be reused or extended.
- Recognize existing limitations, incomplete implementations and technical debt.
- Consider how proposed changes may affect other application components.
- Verify assumptions against the actual codebase rather than relying exclusively on previous conversations or documentation.

The AI must not assume that a capability is missing simply because it has not been explicitly mentioned in the current task.

### Design Guidance

Understanding the existing application is a mandatory part of implementation, regardless of task size.

The AI should develop an accurate understanding of the relevant application context before making changes.

This prevents duplicated functionality, incompatible implementations, unnecessary restructuring and avoidable regressions.

**General principle:** Understand the application before changing it.

## 10.5.2 — Implementation Quality and Code Organization

### Functional Requirements

- Produce clean, readable and maintainable code.
- Follow established project conventions and coding standards.
- Use appropriate modularity and separation of responsibilities.
- Keep related functionality logically organized.
- Avoid unnecessary abstractions and overengineering.
- Implement appropriate error handling and input validation.
- Maintain consistent interfaces and data handling.
- Avoid unnecessary coupling between unrelated components.
- Use established libraries and patterns where appropriate.
- Prioritize correctness, reliability and maintainability over implementation speed.
- Ensure new functionality can be understood and maintained by future development sessions.

### Design Guidance

The AI should aim for sensible, maintainable implementations rather than maximizing architectural complexity.

It should avoid both poorly organized code and excessive fragmentation into unnecessary components.

The preferred approach is the simplest maintainable solution that adequately satisfies the requirements and fits the application's architecture.

## 10.5.3 — Incremental and Controlled Development

### Functional Requirements

- Divide substantial implementation work into manageable stages.
- Avoid unnecessarily large or uncontrolled changes.
- Implement related functionality in a logical sequence.
- Preserve existing working functionality throughout development.
- Complete and verify individual stages before expanding implementation scope.
- Keep changes understandable and reviewable.
- Avoid combining unrelated development tasks into a single implementation.
- Identify problems before allowing them to affect subsequent stages.
- Maintain awareness of incomplete work and temporary implementation states.
- Ensure implementation remains within the approved scope.

### Design Guidance

Development should proceed through controlled implementation bursts rather than attempting to complete large portions of the application in one operation.

Each stage should have a clear purpose and an identifiable outcome.

The AI should make practical progress without sacrificing understanding, maintainability or control over changes.

## 10.5.4 — Integration and Compatibility

### Functional Requirements

- Integrate new functionality with the existing application architecture.
- Reuse established shared services and scientific capabilities where appropriate.
- Maintain compatibility with existing data structures and workflows.
- Identify conflicts with existing components and dependencies.
- Consider the effects of implementation on other scientific workspaces.
- Preserve established interfaces and functionality unless changes are intentional and authorized.
- Ensure connected components exchange information consistently.
- Avoid creating isolated features that do not integrate properly with the application.
- Consider future web and desktop compatibility where relevant.
- Identify and document unavoidable compatibility limitations.

### Design Guidance

New functionality should become part of the application rather than operating as an unrelated addition.

The AI should consider how the implementation fits into the wider system and whether existing capabilities can support it.

Integration should be deliberate, with attention to shared functionality, data relationships and cross-workspace requirements.

## 10.5.5 — Dependencies and External Software

### Functional Requirements

- Prefer established, reliable libraries and software where appropriate.
- Avoid introducing unnecessary dependencies.
- Evaluate compatibility with the existing technical environment.
- Consider licensing, security, maintenance and long-term availability.
- Document newly introduced dependencies and their purposes.
- Record relevant versions and configuration requirements.
- Avoid unnecessary dependency changes.
- Identify potential conflicts between existing and proposed dependencies.
- Consider whether existing libraries already provide the required functionality.
- Preserve sufficient dependency information to support future maintenance and reproducibility.

### Design Guidance

The AI should not introduce a new library or framework simply because it offers a convenient implementation.

It should first investigate existing capabilities and determine whether an additional dependency is justified.

Dependencies should provide meaningful value without introducing disproportionate maintenance or compatibility burdens.

Significant new dependencies must follow the approval requirements established in Section 10.4.

## 10.5.6 — Error Handling and Defensive Development

### Functional Requirements

- Validate inputs and handle unexpected conditions appropriately.
- Provide meaningful error messages rather than allowing silent failures.
- Handle missing, malformed, incomplete and incompatible data appropriately.
- Identify invalid assumptions and unsupported operations.
- Avoid silently discarding scientific information.
- Preserve original scientific data during processing and transformations.
- Ensure failures do not unnecessarily compromise unrelated functionality.
- Handle interruptions and unsuccessful operations safely where practical.
- Provide appropriate warnings when operations cannot be completed reliably.
- Record significant implementation limitations and failure conditions.

### Design Guidance

The AI should anticipate realistic failure conditions rather than implementing only the expected successful execution path.

Error handling should help users understand what happened and whether their data or research progress was affected.

Scientific data integrity and preservation requirements established in Section 5 must remain applicable throughout implementation.

## 10.5.7 — Performance and Resource Awareness

### Functional Requirements

- Consider memory usage, processing time and computational requirements.
- Avoid unnecessary data copying and repeated computation.
- Account for potentially large astronomical datasets.
- Use appropriate background processing for long-running operations.
- Avoid unnecessarily blocking the application interface.
- Consider efficient data access and storage.
- Monitor relevant performance problems during development.
- Identify computational bottlenecks where practical.
- Consider local and remote processing requirements where applicable.
- Preserve numerical accuracy and scientific reliability when optimizing implementations.

### Design Guidance

Performance should be considered during implementation rather than treated exclusively as a later optimization task.

However, the AI should avoid premature optimization and unnecessary complexity.

Optimization should be based on actual requirements, measured problems and scientifically appropriate solutions.

## 10.5.8 — Scientific Implementation Responsibilities

### Functional Requirements

- Implement scientific functionality according to established scientific and mathematical requirements.
- Use appropriate established methods and validated implementations wherever available.
- Understand the scientific purpose of implemented operations.
- Preserve the distinction between original observations, processed data, derived results and model outputs.
- Maintain appropriate units, numerical conventions and data relationships.
- Implement relevant uncertainty and quality-handling requirements.
- Identify assumptions and limitations in scientific implementations.
- Avoid presenting simplified, incomplete or experimental functionality as fully established scientific capability.
- Identify when an implementation requires additional scientific investigation or validation.
- Ensure implementation details remain consistent with the scientific requirements established in Sections 2, 3 and 5.

### Design Guidance

Scientific functionality must be implemented with an understanding of the underlying science rather than treated as generic software functionality.

A technically functioning implementation is not automatically scientifically correct.

Scientific validation and verification are addressed separately in Section 10.6.

## 10.5.9 — Temporary, Incomplete and Placeholder Implementations

### Functional Requirements

- Clearly identify incomplete functionality.
- Distinguish temporary implementations from production-ready capabilities.
- Identify placeholders, simulated outputs and mock functionality.
- Document known limitations and outstanding implementation work.
- Avoid presenting unavailable functionality as implemented.
- Avoid presenting simulated or synthetic scientific results as genuine observations.
- Ensure temporary implementations do not silently compromise existing functionality.
- Identify dependencies and work required to replace temporary solutions.
- Update the master development roadmap to reflect incomplete and outstanding work.

### Design Guidance

Temporary solutions may be appropriate when they support controlled development or testing.

However, their status and limitations must remain clear.

The AI must not disguise incomplete functionality as a finished implementation or allow temporary workarounds to become undocumented permanent dependencies.

## 10.5.10 — Implementation Documentation and Development Records

### Functional Requirements

- Document significant implementation decisions and technical changes.
- Update relevant architecture and technical documentation.
- Maintain accurate dependency and component records.
- Record new files, modules, services and significant structural changes.
- Document implemented functionality and its limitations.
- Record incomplete work and outstanding implementation requirements.
- Preserve relevant implementation history.
- Update the master development roadmap as work progresses.
- Identify other documentation affected by implementation changes.
- Ensure documentation accurately reflects the actual codebase.

### Design Guidance

Documentation is part of implementation rather than an optional activity performed only when development is finished.

The AI must follow the documentation synchronization and change-impact requirements established in Section 11.

Implementation work should not be considered fully documented and complete while relevant project documentation remains outdated.

## 10.5.11 — Implementation Discipline and Scope Control

### Functional Requirements

- Work within the approved implementation scope.
- Avoid unrelated modifications.
- Do not silently expand the purpose or requirements of an implementation task.
- Do not replace requested functionality with incomplete alternatives without communicating the limitation.
- Avoid unnecessary rewrites and broad refactoring.
- Preserve existing user data and research history.
- Identify when implementation reveals a problem requiring a significant change in approach.
- Stop before making consequential unauthorized changes.
- Explain relevant problems, alternatives and implications.
- Record deviations from the approved implementation plan.
- Ensure the final implementation report accurately distinguishes completed, incomplete, modified and unverified work.

### Design Guidance

The AI should have sufficient independence to make practical implementation decisions without constantly seeking approval for routine details.

However, implementation autonomy must not become unrestricted authority to alter the application's direction or established requirements.

When a better approach requires a significant departure from the approved scope, the AI should explain the situation and seek approval before proceeding.

## General Principles

The AI development partner should:

- Understand the existing application before implementing changes.
- Understand the application's context, architecture and existing capabilities.
- Reuse and extend existing functionality where appropriate.
- Prefer simple, maintainable solutions over unnecessary complexity.
- Avoid duplicated functionality and poorly organized code.
- Develop incrementally through manageable implementation stages.
- Integrate new functionality with the wider application.
- Maintain appropriate error handling and defensive programming.
- Consider performance, computational resources and scientific data integrity.
- Distinguish temporary and incomplete implementations from finished capabilities.
- Maintain accurate technical documentation and development records.
- Respect approved implementation scope and decision boundaries.

## Implementation Considerations

Implementation should follow the approved development plans and architectural direction established through Sections 10.2–10.4.

Before substantial changes, the AI should inspect relevant code, documentation, dependencies and tests to understand the actual application state.

Implementation should remain consistent with the scientific requirements established throughout Sections 2–5 and the architectural, platform and application requirements established in Sections 6 and 9.

The AI must also follow the mandatory documentation, knowledge management and continuity requirements established in Section 11.

**General Principle:** The AI development partner should produce reliable, maintainable and scientifically appropriate software through careful, incremental implementation. It must understand the existing application before making changes, reuse established capabilities, avoid unnecessary complexity and ensure that every new implementation contributes coherently to the application as a whole.
