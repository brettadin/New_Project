

# 4.12 — Resource Evaluation, Expansion and User Contributions

## Purpose

The application should maintain an adaptable catalogue of external scientific resources and provide a structured approach for evaluating, introducing, maintaining and retiring them.

Astronomical research depends on a changing ecosystem of archives, catalogues, databases, scientific software, services and reference resources. New resources become available, existing services change and previously useful integrations may become outdated or unsuitable.

The application should therefore support ongoing resource evaluation rather than treating its initial collection of integrations as permanent or exhaustive.

Users should also be able to suggest resources that may improve the application. These suggestions should provide a meaningful route for identifying useful additions without automatically treating every submission as an approved integration.

Resource expansion should remain guided by scientific value, reliability, accessibility, maintainability and relevance to the application's overall purpose.

## 4.12.1 External Resource Catalogue

### Core Requirements

- Maintain an organized catalogue of known external scientific resources.
- Include relevant archives, databases, catalogues, surveys, reference collections, scientific software, APIs, services and other research tools.
- Preserve resource names, descriptions, providers and relevant identifiers.
- Organize resources by scientific discipline, resource type, intended purpose and other useful categories.
- Allow resources to be associated with multiple scientific disciplines and research activities.
- Support searching, filtering and browsing the resource catalogue.
- Distinguish resources that are actively integrated from those that are documented, recommended, under evaluation or unavailable.
- Preserve relevant links to official resource websites, documentation and access points.
- Maintain information about supported functionality and known limitations.
- Allow the catalogue to expand without requiring every listed resource to be directly integrated into the application.

### Design Guidance

The resource catalogue should serve as an organized reference for the external scientific ecosystem relevant to the application.

Not every listed resource needs to provide an automated integration. Some may be valuable as independently accessible databases, specialized software or scientific reference sources.

The catalogue should distinguish these roles clearly rather than implying that every listed resource is equally integrated or supported.

## 4.12.2 Resource Evaluation Criteria

### Core Requirements

Evaluate potential resources according to relevant criteria, including:

- Scientific relevance to the application's subject areas and research capabilities.
- Authority and credibility of the provider.
- Scientific quality and reliability of the available information.
- Coverage of relevant astronomical objects, observations or research subjects.
- Data availability, completeness and documentation.
- Metadata quality and compatibility with scientific workflows.
- Supported formats, standards, APIs and integration methods.
- Accessibility and applicable usage restrictions.
- Licensing, attribution and redistribution conditions.
- Privacy and security considerations.
- Service availability and operational reliability.
- Maintenance status and long-term sustainability.
- Compatibility with existing application capabilities.
- Implementation and maintenance complexity.
- Potential overlap with existing resources.
- Additional scientific value provided by the resource.

### Design Guidance

Resource evaluation should consider the overall value of an integration rather than relying on a single measure of popularity, convenience or technical accessibility.

A scientifically authoritative resource may still be unsuitable for direct integration if its access restrictions, maintenance requirements or technical limitations outweigh its practical value.

Likewise, a specialized resource may be valuable even if it serves a relatively narrow research area.

## 4.12.3 Resource Catalogue Status and Classification

### Core Requirements

- Maintain understandable status information for catalogued resources.
- Support distinctions such as:
  - Identified.
  - Under evaluation.
  - Planned.
  - Integrated.
  - Partially supported.
  - Available externally but not integrated.
  - Temporarily unavailable.
  - Deprecated.
  - Discontinued.
- Identify the capabilities provided by each integrated resource.
- Identify known limitations and unsupported functionality.
- Preserve relevant evaluation and maintenance information.
- Distinguish current availability from integration status.
- Allow resource status to change as evaluation and maintenance progress.
- Avoid presenting planned or partially supported integrations as fully operational.

### Design Guidance

Resource status should communicate what users can realistically expect from a resource.

For example, a database may be fully documented in the catalogue while supporting only limited automated retrieval. Another resource may be fully integrated but temporarily unavailable because its external service is offline.

These situations should remain distinguishable.

## 4.12.4 Resource Discovery and Catalogue Maintenance

### Core Requirements

- Support ongoing identification of relevant external scientific resources.
- Allow resources to be added to the catalogue when discovered through research, development or user suggestions.
- Preserve the source of resource recommendations where appropriate.
- Support periodic review of catalogued resources.
- Identify resources that have become outdated, inaccessible, duplicated or superseded.
- Maintain relevant descriptions, links, documentation and integration status.
- Allow outdated catalogue entries to be revised or retired.
- Preserve historical information about significant resource changes.
- Avoid removing a resource from historical research records merely because it is no longer actively supported.
- Maintain consistency between catalogue information and actual integration capabilities.

### Design Guidance

The resource catalogue should be maintained as the external scientific ecosystem evolves.

Catalogue maintenance should not require every resource to be continuously monitored in real time. Review frequency and monitoring depth should be proportionate to the importance, reliability requirements and practical maintenance costs of each resource.

## 4.12.5 User-Suggested External Resources

### Core Requirements

- Allow users to suggest external scientific resources for consideration.
- Support suggestions for archives, databases, catalogues, surveys, scientific software, APIs, reference collections and other relevant tools.
- Allow users to provide a resource name, description and official website or documentation link.
- Allow users to explain the scientific purpose and potential value of a suggested resource.
- Support optional supporting information, such as relevant disciplines, research applications or examples of useful data.
- Allow suggestions to be reviewed and evaluated before being added to the supported resource catalogue.
- Preserve the distinction between a user suggestion and an officially evaluated or integrated resource.
- Communicate the status of suggestions where appropriate.
- Avoid automatically connecting to or executing suggested external resources.
- Allow the application to consider suggestions from different users without requiring every suggestion to be adopted.

### Design Guidance

Users may encounter valuable scientific resources through their own research that are not already represented in the application.

A suggestion mechanism should make it possible to communicate these discoveries without requiring users to understand the application's technical integration requirements.

Submissions should be treated as proposals for evaluation, not as automatic authorization to connect to external services or incorporate their software.

## 4.12.6 Evaluation of User Suggestions

### Core Requirements

- Review suggested resources according to the established evaluation criteria.
- Determine whether a suggestion is relevant to the application's scientific purpose.
- Identify whether the resource duplicates existing catalogue entries or provides additional capabilities.
- Evaluate scientific credibility, documentation, availability, access conditions and maintenance requirements.
- Assess potential integration approaches where direct integration is justified.
- Identify licensing, privacy, security or other concerns.
- Record whether a suggestion is accepted for further investigation, planned, declined or deferred.
- Provide a reasonable explanation for significant decisions where appropriate.
- Preserve the ability to reconsider previously declined or deferred suggestions when circumstances change.
- Avoid treating suggestion frequency or popularity as sufficient evidence of scientific value.

### Design Guidance

Suggestions should receive proportionate evaluation.

A resource that is unsuitable for direct integration may still be worth including as an independently accessible reference.

Likewise, a resource may be scientifically valuable but impractical to integrate until its API, documentation or access conditions improve.

The application should distinguish these outcomes rather than reducing every decision to accepted or rejected.

## 4.12.7 Resource Integration Planning and Prioritization

### Core Requirements

- Prioritize potential integrations according to scientific value and practical feasibility.
- Consider how an integration supports existing research capabilities and scientific disciplines.
- Identify dependencies and prerequisites before planning implementation.
- Evaluate the likely development, testing and ongoing maintenance effort.
- Consider whether an integration provides functionality that should instead be developed natively.
- Identify whether multiple resources can complement one another.
- Support incremental integration rather than requiring complete functionality immediately.
- Document significant integration decisions and their rationale.
- Reassess priorities as application requirements and external resources evolve.
- Avoid allowing low-value integrations to create unnecessary architectural or maintenance complexity.

### Design Guidance

Integration priority should reflect the value delivered to users relative to the resources required to implement and maintain the integration.

An initial integration may support only a limited set of useful operations, with additional functionality considered later.

The application should favor meaningful, reliable integrations over a large catalogue of poorly maintained connections.

## 4.12.8 Resource Maintenance and Review

### Core Requirements

- Establish a process for reviewing the condition of supported resources and integrations.
- Identify significant changes to external services, APIs, software, documentation and access conditions.
- Review whether integrations remain scientifically useful and technically functional.
- Identify resources that have become unreliable, outdated or unsupported.
- Track known integration limitations and unresolved issues.
- Reassess resources when major changes affect their suitability.
- Support updating, replacing, restricting or retiring integrations where appropriate.
- Preserve relevant historical records when resource status changes.
- Identify potential effects on existing research workflows and saved projects.
- Avoid silently changing the resource or method used by historical research.

### Design Guidance

Maintenance requirements will differ between resource types.

An external archive with a frequently changing API may require more active monitoring than a stable scientific reference publication.

Review efforts should reflect the resource's importance, expected change frequency and potential impact on scientific work.

## 4.12.9 Resource Deprecation and Discontinuation

### Core Requirements

- Support identifying resources and integrations that are deprecated, discontinued or no longer suitable.
- Communicate when a resource is approaching the end of its supported lifecycle where information is available.
- Identify alternative resources where scientifically appropriate.
- Distinguish a discontinued external service from an integration that the application no longer supports.
- Preserve previously acquired datasets and relevant research records.
- Preserve attribution, provenance and historical integration information.
- Identify affected projects, workflows and dependencies where possible.
- Avoid automatically replacing discontinued resources with alternatives that may produce different scientific results.
- Allow users to review potential migration options.
- Maintain access to previously generated outputs wherever technically and legally possible.

### Design Guidance

Discontinuing an integration should not erase the scientific work previously performed with it.

For example, if an external modelling service becomes unavailable, previously generated results and their associated records should remain accessible even if new calculations can no longer be performed through that service.

Alternatives should be evaluated for scientific equivalence rather than assumed interchangeable.

## 4.12.10 Resource Documentation and Decision Records

### Core Requirements

- Maintain documentation for significant resource evaluation and integration decisions.
- Record why a resource was selected, rejected, deferred or retired.
- Preserve relevant information about scientific value, technical feasibility, access conditions and known limitations.
- Identify the source of important resource information.
- Record significant changes to resource status and supported functionality.
- Maintain links to relevant provider documentation and integration references.
- Preserve information about unsuccessful integration attempts where the findings may inform future decisions.
- Distinguish verified information from assumptions and unresolved questions.
- Make relevant resource documentation accessible to future maintenance and development work.

### Design Guidance

Resource decisions should remain understandable over time.

A previously rejected integration may become viable when an API improves or access restrictions change. Documenting the original evaluation prevents unnecessary repetition and helps future development understand the reasoning behind earlier decisions.

## General Principles

Resource evaluation, expansion and user contributions should:

- Maintain an organized and adaptable catalogue of scientific resources.
- Evaluate resources according to scientific value, credibility, accessibility and sustainability.
- Distinguish catalogue entries from actively supported integrations.
- Preserve clear integration status and known limitations.
- Support user suggestions without automatically accepting or executing them.
- Evaluate suggested resources consistently and transparently.
- Prioritize integrations according to scientific value and practical feasibility.
- Maintain supported resources as external services and software evolve.
- Preserve historical research when integrations are changed or discontinued.
- Document significant resource decisions and their rationale.
- Avoid unnecessary duplication, complexity and maintenance burdens.
- Allow the external resource ecosystem to expand as the application develops.

## General Principle

The application's external resource ecosystem should develop through deliberate evaluation, meaningful scientific contribution and ongoing maintenance.

A useful resource catalogue is not defined by the number of entries it contains, but by the relevance, reliability, accessibility and practical value of the resources it provides.

## Implementation Boundary

This subsection establishes requirements for external resource catalogues, resource evaluation, user suggestions, integration prioritization, maintenance and lifecycle management.

It does not prescribe a particular catalogue database, submission system, review workflow, monitoring service or integration management technology.
