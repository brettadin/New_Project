

# 5.6 — Validation, Error Detection and Quality Control

## Purpose

The application should provide comprehensive capabilities for assessing data quality, identifying errors, evaluating scientific and computational reliability, and validating analytical methods and outputs.

Quality control should operate throughout the scientific workflow, from data retrieval and import through processing, modelling, analysis and interpretation.

The application should help users identify potential problems, understand their consequences and determine whether data or results are suitable for a particular research purpose.

Quality assessment must account for scientific context. A dataset may contain missing information, instrumental artifacts or unusual measurements while remaining useful for certain investigations.

The application should therefore distinguish between confirmed problems, potential concerns, incomplete information and observations that require further investigation. It should preserve user authority over scientific judgments while providing reliable automated checks and validation tools.

## 5.6.1 Data Quality Assessment

### Core Requirements

- Perform appropriate initial quality assessments when datasets are imported or retrieved.
- Perform additional task-specific checks when users select analytical workflows.
- Account for data type, observational characteristics and intended scientific application when assessing quality.
- Detect or identify potential issues, including:
  - Missing or invalid values.
  - Duplicate measurements or records.
  - Outliers and unusual observations.
  - Excessive noise or background interference.
  - Gaps and incomplete coverage.
  - Inconsistent sampling or discontinuities.
  - Malformed or inconsistent data structures.
  - Missing uncertainty measurements.
  - Missing or questionable metadata.
  - Potentially insufficient resolution or sensitivity.
- Distinguish critical errors, warnings and informational observations.
- Explain detected problems and their potential scientific consequences.
- Identify which datasets, measurements or analytical operations are affected.
- Avoid automatically rejecting datasets simply because they contain quality issues.
- Preserve the user's ability to inspect questionable data and determine whether it remains useful.
- Avoid treating every statistically unusual observation as an error.

### Design Guidance

Quality assessment should consider the intended use of a dataset rather than applying a single universal standard.

For example, an observation with limited spectral coverage may be unsuitable for one type of molecular identification but remain useful for another investigation.

The application should communicate relevant limitations without unnecessarily restricting scientific exploration.

## 5.6.2 Metadata, Units and Calibration Validation

### Metadata Validation

**Core Requirements**

- Read available metadata from files, archive records and associated documentation.
- Identify missing, inconsistent, malformed or potentially unreliable metadata.
- Never fabricate missing information or silently assume scientific values.
- Allow incomplete datasets to be imported and used where scientifically appropriate.
- Request additional information only when genuinely necessary for an operation.
- Explain how missing or questionable metadata affects analytical suitability.
- Preserve the origin and classification of metadata throughout subsequent analysis.

Maintain four distinguishable metadata classifications:

1. **Verified metadata:** Explicitly supplied by a reliable source.
2. **User-supplied metadata:** Added or corrected by the user.
3. **Inferred metadata:** Derived through a documented, defensible process.
4. **Unknown metadata:** Not available or not reliably established.

These classifications must remain distinguishable throughout analysis, project records, exports and reports. Inferred information must never be presented as verified source information.

### Unit Validation

**Core Requirements**

- Identify measurement units and coordinate conventions where available.
- Detect incompatible units when datasets are compared, combined or processed.
- Support scientifically valid unit conversions.
- Record conversions and preserve original values.
- Never silently assume an unknown unit.
- Flag ambiguous or incompatible measurements before potentially invalid comparisons.
- Identify when unit information is incomplete or insufficient for a particular operation.

### Calibration Validation

**Core Requirements**

- Identify available calibration information and processing status.
- Distinguish raw, partially calibrated and calibrated observations where possible.
- Check whether calibration information is appropriate for the intended analysis.
- Identify missing, inconsistent or potentially outdated calibration information.
- Warn when calibration limitations could affect scientific conclusions.
- Avoid assuming that all instruments or observational methods require identical calibration procedures.
- Preserve calibration provenance and processing history.
- Identify when calibration status cannot be established reliably.

### Design Guidance

The application must distinguish between data that is unusable for a particular operation, data that is usable with limitations and data that is suitable for the intended analysis.

Missing metadata should not automatically make a dataset unusable. However, the application must not silently substitute assumptions for information that is scientifically necessary.

## 5.6.3 Instrument and Observational Quality Control

### Core Requirements

- Maintain an expandable collection of known instrument characteristics, specifications, limitations and potential artifacts.
- Use instrument-specific information when the instrument can be reliably identified and the information is relevant.
- Do not automatically apply instrument-specific corrections, assumptions or quality rules if they could introduce errors or compromise the analysis.
- Distinguish confirmed instrument problems from suspected issues.
- Identify potential instrumental noise, detector artifacts, saturation, signal clipping, instrumental drift and calibration problems where detectable.
- Account for observational conditions, including atmospheric interference and background contamination where relevant.
- Identify differences between instruments when comparing observations.
- Explain potential effects on data quality and scientific interpretation.
- Record the reference information and methods used in quality assessments.
- Allow users to inspect quality-control assessments and override appropriate assessments with relevant warnings.

### Future Possibilities

- Expand the instrument information collection as new instruments and reference information become available.
- Incorporate instrument-specific quality-control procedures and validated correction methods.
- Compare observations against known instrument performance characteristics.
- Support more detailed observational-condition assessments.

### Design Guidance

Instrument-specific information must only be applied when its relevance and suitability are established.

Having a known instrument profile does not automatically make every associated correction or assumption appropriate. Instrument characteristics should inform quality assessment without replacing evaluation of the actual observation.

## 5.6.4 Processing and Transformation Validation

### Core Requirements

- Provide users with tools to inspect and validate processing results.
- Identify potential processing errors and unexpected outputs where detectable.
- Evaluate whether transformations are appropriate for the data type and intended scientific objective.
- Help users identify excessive smoothing, filtering artifacts, distorted signals and information loss.
- Allow comparison between original and processed datasets.
- Make changes to uncertainties and measurement properties inspectable.
- Warn about transformations that could compromise subsequent analyses.
- Allow users to validate processing workflows before reusing them.
- Preserve the user's authority to accept, reject or revise processing decisions.
- Identify when processing results cannot be validated reliably with the available information.

### Future Possibilities

- More advanced automated diagnostic checks.
- Additional processing-quality indicators.
- Guided validation procedures for complex workflows.
- Reusable validation configurations for compatible processing procedures.

### Design Guidance

Detecting a potential problem is not the same as validating a scientific result.

The application should provide diagnostic information and supporting evidence while allowing users to evaluate whether a processing operation is appropriate for their research.

These requirements should remain consistent with the original data preservation and processing safeguards established in Section 5.3.

## 5.6.5 Model and Analytical Output Validation

### Core Requirements

- Detect numerical instability, convergence failures and computational errors where possible.
- Identify physically implausible or mathematically invalid outputs.
- Check model assumptions and input compatibility.
- Support independent validation against established reference datasets, published results and benchmark cases.
- Compare outputs against known results and identify discrepancies.
- Identify poor fits, residual patterns and unexplained differences.
- Distinguish successful computation from scientifically validated results.
- Communicate model limitations and conditions under which outputs may be unreliable.
- Record validation methods, reference sources, configurations and results.
- Allow users to inspect validation evidence and make their own scientific judgments.
- Identify when reference comparisons are incomplete or unsuitable for establishing reliability.

### Design Guidance

Model validation should consider both computational behavior and scientific suitability.

For example, a model may complete successfully and produce a numerical result while failing to represent the available observations adequately.

Agreement with a reference result supports confidence but does not automatically prove that a model or analytical result is correct. Reference datasets and benchmark cases must also have documented limitations and provenance.

## 5.6.6 Scientific Method Validation and Benchmarking

### Core Requirements

- Prefer established, scientifically accepted methods where suitable.
- Verify implementations against published methodologies, equations and reference cases.
- Compare implementations against independent software or libraries where practical.
- Test methods using known datasets and benchmark problems.
- Identify differences between theoretical expectations and actual implementation results.
- Document method assumptions, applicable conditions, limitations and known failure cases.
- Distinguish established methods from experimental or less extensively validated approaches.
- Preserve validation records, references, test configurations and outcomes.
- Reassess methods when significant errors, scientific developments or implementation changes are identified.
- Identify the extent to which a method has been independently validated.

### Future Possibilities

- Expandable benchmark libraries for different scientific disciplines.
- Community-contributed reference cases and independent validation results.
- Automated regression testing against established scientific benchmarks.
- Broader comparison of alternative implementations of established scientific methods.

### Design Guidance

Scientific methods should be evaluated against appropriate references and established expectations wherever possible.

A method should not be treated as validated simply because it produces plausible results or agrees with a small number of selected examples.

Validation records should identify what was tested, which references were used, what limitations remain and which conditions have not yet been evaluated.

## 5.6.7 Warnings, Errors and Quality Reporting

### Core Requirements

- Provide a consistent system for communicating scientific and technical problems.
- Distinguish critical errors, warnings and informational notices.
- Explain what was detected, why it matters and which data or results are affected.
- Identify whether an issue prevents an operation, limits reliability or simply warrants attention.
- Link warnings to affected datasets, processing operations, models and analyses.
- Preserve significant quality-control findings in project records.
- Allow users to inspect historical warnings and determine whether previously identified problems have been addressed.
- Avoid overwhelming users with repetitive or irrelevant notifications.
- Never silently dismiss scientifically significant problems.
- Distinguish automatically detected problems from issues confirmed through user evaluation or independent validation.

### Comprehensive Quality-Assessment Reports

Users should be able to generate quality-assessment reports for individual datasets and broader investigations.

Reports should document:

- Dataset identification and relevant provenance.
- Quality checks performed.
- Detected errors, warnings and informational observations.
- Missing or questionable metadata.
- Instrumental and observational limitations.
- Processing and calibration concerns.
- Validation checks and their outcomes.
- Known uncertainties and limitations.
- Issues that have been resolved and how they were addressed.
- Outstanding issues and their potential consequences.
- Relevant references and supporting information.
- Any limitations affecting the completeness of the assessment.

Reports should be retainable within projects and exportable.

### Future Possibilities

- Customizable warning thresholds and notification preferences.
- More advanced quality-assessment reporting.
- Cross-project quality monitoring.
- Comparison of quality assessments across related datasets or observations.

### Design Guidance

Warnings and reports should communicate useful information rather than simply listing technical problems.

Users should be able to understand the significance of an issue, determine which research materials are affected and identify whether further investigation is necessary.

## 5.6.8 Validation Across Scientific Workflows

### Core Requirements

- Apply appropriate validation at relevant stages of scientific workflows.
- Perform initial checks during data retrieval and import.
- Perform additional checks before or during processing when relevant.
- Evaluate the suitability of inputs for selected analytical methods.
- Support validation of model configurations and computational execution.
- Evaluate analytical outputs and their supporting evidence.
- Identify when problems introduced at an earlier stage may affect subsequent results.
- Preserve relationships between validation findings and affected workflow components.
- Avoid assuming that passing an earlier validation stage guarantees the validity of later results.
- Allow users to inspect relevant validation information throughout an investigation.

### Design Guidance

Quality control should not be treated as a single inspection performed when data first enters the application.

A dataset may pass initial structural checks but still be unsuitable for a particular analysis. Likewise, a processing operation may introduce new problems that were not present in the original observations.

Validation should therefore remain connected to the scientific workflow and be appropriate to the operation being performed.

## 5.6.9 Quality Assessment History and Issue Resolution

### Core Requirements

- Preserve significant quality assessments and validation findings.
- Record when assessments were performed and which methods or checks were used.
- Identify the datasets, operations and outputs examined.
- Allow users to document how identified issues were investigated or resolved.
- Distinguish resolved issues from unresolved, accepted or partially addressed concerns.
- Preserve previous findings when new assessments produce different results.
- Identify when a previously accepted dataset or result requires reassessment.
- Maintain links between quality-control records and relevant analysis history.
- Avoid silently removing historical warnings when underlying data or methods change.
- Support inspection of quality-assessment history over the course of an investigation.

### Design Guidance

Quality assessments may change as users obtain additional information, correct metadata, apply calibration or revise analytical methods.

The application should preserve previous findings and document why the assessment changed rather than replacing the historical record with only the latest status.

## 5.6.10 User Review and Scientific Judgment

### Core Requirements

- Allow users to inspect detected problems and supporting information.
- Allow users to determine whether questionable data remains suitable for a particular purpose.
- Support documented user decisions concerning warnings and quality-control findings.
- Allow appropriate overrides of automated assessments.
- Communicate when overriding a warning may affect scientific reliability.
- Preserve the reason for significant user overrides where appropriate.
- Distinguish user acceptance of a limitation from proof that the underlying issue has been resolved.
- Avoid automatically rejecting scientifically unusual or incomplete observations.
- Avoid allowing users to silently erase significant quality-control findings.
- Preserve the evidence supporting automated assessments and user decisions.

### Design Guidance

The application should provide meaningful quality-control assistance without assuming that automated checks can resolve every scientific judgment.

A user may reasonably choose to analyze incomplete or questionable data when the limitations are understood and appropriate to the research question.

The application should support that decision while preserving the relevant warnings and research context.

## 5.6.11 Validation Limitations and Incomplete Evidence

### Core Requirements

- Identify when a quality assessment cannot be completed.
- Communicate when required reference information, metadata or validation resources are unavailable.
- Distinguish checks that passed, failed, were inconclusive or were not performed.
- Identify when an assessment relies on incomplete or indirect evidence.
- Avoid presenting an incomplete validation as a comprehensive assessment.
- Preserve information about unavailable or unsupported checks.
- Allow users to inspect the scope and limitations of an assessment.
- Identify when a validation method is not applicable to the selected data or operation.
- Communicate when scientific correctness cannot be established automatically.
- Preserve unresolved validation concerns in relevant research records.

### Design Guidance

Not every scientific result can be independently validated by the application.

Some observations lack suitable reference datasets, some analytical methods have no definitive benchmark and some scientific interpretations require expert evaluation.

The application should communicate these limitations rather than implying that every result has received the same level of validation.

## General Principles

Validation, error detection and quality control should:

- Operate throughout scientific workflows rather than only during data import.
- Account for data type, scientific context and intended research use.
- Distinguish confirmed errors, potential problems, warnings and informational observations.
- Preserve incomplete and unusual datasets when they remain scientifically useful.
- Never fabricate metadata or silently assume missing scientific information.
- Maintain distinguishable metadata classifications.
- Apply instrument-specific information only when appropriate.
- Make processing and analytical results inspectable.
- Distinguish computational success from scientific validity.
- Support independent validation against appropriate references and benchmarks.
- Preserve validation findings, limitations and user decisions.
- Communicate the scope and limitations of quality assessments.
- Maintain user authority over scientific judgments.

## Acceptance Criteria

The implementation must demonstrate that:

1. Imported and retrieved datasets receive appropriate initial quality assessments.
2. Task-specific checks identify problems relevant to the selected analytical workflow.
3. Missing, invalid and questionable data are identified without automatically rejecting otherwise useful datasets.
4. Metadata classifications remain distinguishable throughout the application.
5. Missing metadata is never fabricated or silently assumed.
6. Unit conversions and calibration handling preserve original values and provenance.
7. Instrument-specific quality checks are applied only when appropriate.
8. Processing results can be inspected and compared against original data, with validation decisions remaining user-controlled.
9. Model and analytical outputs can be checked against independent scientific references and benchmark cases.
10. Scientific methods are tested against established methodologies and reference cases.
11. Warnings and errors clearly communicate their severity, consequences and affected components.
12. Quality-assessment reports accurately document checks, findings, limitations and resolutions.
13. Quality-control information remains accessible and traceable within projects and exported records.
14. Incomplete, inconclusive and unperformed validation checks are clearly distinguished from successful checks.
15. Significant quality-control findings and user decisions remain accessible in historical analysis records.

Acceptance testing should include normal datasets, incomplete datasets, noisy observations, incompatible units, ambiguous metadata, unsuitable inputs, instrumental artifacts and known benchmark cases.

Scientific correctness must be assessed independently of basic software functionality. A successful test execution or plausible-looking output does not establish scientific validity.

## General Principle

Quality control should help users understand the reliability and limitations of scientific data and results without creating false confidence or unnecessarily restricting legitimate research.

The application should identify what it can verify, explain what it cannot establish and preserve the evidence needed for users to make informed scientific judgments.

## Implementation Boundary

This subsection establishes requirements for data quality assessment, metadata and calibration validation, instrument-specific checks, processing validation, scientific method benchmarking, error reporting and quality-control history.

It does not prescribe specific validation algorithms, instrument database technologies, benchmark frameworks, quality-scoring systems or implementation technologies.

Scientific integrity is established in Section 5.1. Automation and user control are addressed in Section 5.2. Data processing safeguards are addressed in Section 5.3. Scientific interpretation and uncertainty are addressed in Section 5.4. Analysis reproducibility and traceability are addressed in Section 5.5. AI-assisted scientific analysis and interpretation are addressed in Section 5.7.
