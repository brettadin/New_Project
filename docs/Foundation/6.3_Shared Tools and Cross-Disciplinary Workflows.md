# 6.3 — Shared Tools and Cross-Disciplinary Workflows

## Purpose

Establish how scientific tools, shared capabilities, resources and workflows operate across the application's different scientific disciplines and workspaces.

The application should avoid unnecessary duplication of functionality while allowing tools to adapt to the scientific requirements of different areas.

Users should be able to access common capabilities independently or within relevant scientific workspaces, combine capabilities across disciplines, and introduce external resources where necessary.

The overall system should remain expandable as new scientific areas, tools, methods and research requirements are introduced.

This subsection distinguishes between:

1. Functional Requirements — capabilities the application should provide.
2. Future Functional Possibilities — additional capabilities that may be developed later.
3. Design Guidance — principles that should inform implementation without prescribing exact solutions.
4. Implementation Status — the priority and maturity of the requirements.

---

## 1. Functional Requirements

### 1.1 Shared Scientific Tools and Capabilities

The application should provide shared scientific tools and capabilities that can be accessed wherever they are relevant.

Shared tools must be accessible in two ways:

- Independently, through an application-wide tools area or equivalent access point.
- Within relevant scientific workspaces, allowing users to access tools without unnecessarily leaving their current research environment.

Requirements:

- Reuse common underlying implementations wherever practical rather than creating unnecessary duplicate tools.
- Make shared functionality available across scientific disciplines where appropriate.
- Allow tools to expose specialized functionality depending on the active workspace, research activity or data being handled.
- Maintain consistency in fundamental tool behaviour while accommodating discipline-specific requirements.
- Allow tools to be extended when additional scientific requirements emerge.
- Avoid forcing unrelated functionality into workspaces where it is not relevant.
- Maintain relationships between shared tools and the workspaces that use them.

### 1.2 Context-Aware Tool Behaviour

Shared tools should adapt intelligently to their scientific context while retaining user control.

Requirements:

- Recognize the active scientific workspace, research activity and relevant data type.
- Automatically present appropriate controls, methods and settings.
- Apply scientifically appropriate defaults for the current context.
- Allow users to modify settings, access advanced functionality and override automatic choices.
- Explain significant automatic selections, recommendations or configuration changes.
- Avoid assuming that a method or configuration is appropriate simply because of the active workspace.
- Preserve user-selected configurations where appropriate, including when switching between workspaces or revisiting an analysis.
- Ensure contextual adaptation does not prevent users from accessing functionality needed for less conventional investigations.

The application should provide intelligent assistance without restricting scientific control.

### 1.3 Shared Capability Inventory

Maintain a comprehensive inventory of shared tools and scientific capabilities.

The inventory must document:

- Each tool or capability available within the application.
- Which scientific workspaces and disciplines use it.
- What it does within each scientific context.
- Its scientific purpose, role and rationale.
- Which functionality is shared and which is discipline-specific.
- Relevant inputs, outputs and supported data types.
- Dependencies and relationships with other tools and capabilities.
- Relevant methods, configurations and scientific requirements.
- Known limitations and compatibility considerations.
- Opportunities for extending the capability into additional scientific areas.

The inventory must:

- Be updated when capabilities are introduced, modified, expanded or deprecated.
- Identify opportunities to extend existing functionality rather than unnecessarily duplicating it.
- Record when an extension to a shared capability may benefit other workspaces.
- Remain consistent with the application's technical and scientific documentation.

The inventory should help maintain an understanding of the application as a connected system rather than a collection of unrelated tools.

### 1.4 Shared Scientific Capabilities

The following are initial examples of capabilities that should be considered for shared infrastructure:

- Data importing, inspection and management.
- Graphing and scientific visualization.
- Statistical analysis and numerical computation.
- Scientific databases and reference libraries.
- Spectral analysis and signal processing.
- Photometry and time-series analysis.
- Mathematical modelling and simulations.
- Dataset comparison and correlation.
- Unit conversion and scientific data standardization.
- Reporting, documentation and scientific export.
- Uncertainty and error analysis.
- Data quality assessment and validation.

This list is expandable and should be refined through scientific research and architectural planning.

Not every capability needs to be available in every workspace. Shared infrastructure should support specialized functionality where necessary.

For example, spectroscopy and photometry may use common numerical analysis, plotting and uncertainty infrastructure while retaining their own specialized analytical methods.

### 1.5 Cross-Disciplinary Workflows

Users must be able to construct workflows that combine tools, methods, datasets and capabilities from different scientific disciplines.

For example, an investigation could involve:

- Stellar characterization.
- Exoplanet transit photometry.
- Atmospheric spectroscopy.
- Atmospheric modelling.
- Comparison between observations and theoretical predictions.

Requirements:

- Allow workflows to move between scientific workspaces and shared tools.
- Support combining capabilities from different disciplines where scientifically appropriate.
- Clearly identify which scientific workspace or discipline each workflow stage belongs to.
- Make transitions between workspaces and shared tools visible and understandable.
- Identify the tools, methods and datasets used at each stage.
- Preserve relationships between inputs, intermediate results and final outputs.
- Explain the scientific purpose of methods and capabilities used within the workflow.
- Identify compatibility requirements and potential limitations when moving between disciplines.
- Preserve the origin and scientific context of data throughout the workflow.
- Allow complete workflows to be inspected, revisited and understood.
- Support sharing workflows while retaining their full structure and scientific context.

A cross-disciplinary workflow should not conceal the fact that it uses methods and capabilities from multiple scientific areas.

### 1.6 Data and Method Compatibility

The application must assess compatibility when users connect datasets, methods or workflow stages.

Compatibility checks should consider relevant properties, including:

- Data formats and structures.
- Units and measurement conventions.
- Wavelength coverage and spectral resolution.
- Time systems and sampling conventions.
- Instrument characteristics and calibration.
- Observational conditions.
- Data quality and uncertainty.
- Processing methods and assumptions.
- Metadata completeness and reliability.
- Scientific suitability for the intended analysis.

Requirements:

- Automatically assess compatibility when datasets, methods or workflow stages are connected.
- Identify incompatible, missing or potentially problematic properties.
- Classify issues according to their severity.
- Explain why identified differences matter scientifically.
- Explain the potential consequences for subsequent analysis and interpretation.
- Recommend valid conversions, corrections or alternative approaches where appropriate.
- Allow users to inspect compatibility findings before proceeding.
- Permit users to proceed with documented limitations where scientifically reasonable.
- Preserve compatibility-check results, user decisions and subsequent transformations in the workflow history.
- Never silently force incompatible datasets or methods into a common format.
- Never silently modify original data to resolve compatibility problems.

Compatibility assessment should distinguish between technically compatible data and data that are scientifically suitable for a particular investigation.

### 1.7 Workflow Continuity

Users must be able to move between shared tools and scientific workspaces without unnecessarily losing research context or workflow information.

Requirements:

- Allow datasets, outputs and results to be transferred between relevant tools and workspaces.
- Preserve relevant research context when moving between tools.
- Retain intermediate results and relationships between workflow stages.
- Allow users to revisit, inspect, modify and rerun individual workflow stages.
- Identify downstream stages affected by changes to earlier stages.
- Provide ways to rerun affected stages without unnecessarily repeating an entire workflow.
- Preserve processing histories, configurations, dependencies and provenance.
- Support saving, reopening, duplicating and modifying workflows.
- Maintain clear distinctions between original data, intermediate results, processed data and final outputs.
- Preserve relationships between workflow stages when investigations are saved, exported or shared.

Changes to one stage must not silently overwrite or invalidate previously generated results.

### 1.8 Shared Scientific Resources

Maintain shared access to scientific resources that may be relevant across multiple workspaces.

Examples include:

- Scientific databases and catalogues.
- Molecular and atomic reference databases.
- Spectral line lists.
- Scientific reference libraries.
- Physical and mathematical models.
- Instrument reference information.
- Other relevant scientific datasets and resources.

Requirements:

- Make relevant resources accessible across appropriate scientific workspaces.
- Track resource origins, versions, limitations and compatibility.
- Allow resources introduced for one discipline to be evaluated for use in other disciplines.
- Avoid unnecessary duplication of shared reference resources.
- Preserve resource references and versions within analyses and workflows.
- Identify when a resource is unavailable, outdated, incompatible or otherwise unsuitable.
- Maintain clear distinctions between application-provided and externally supplied resources.

Resources must not be treated as scientifically reliable merely because they are accessible or integrated.

### 1.9 User-Managed External Resources and Integrations

Users must not be restricted to scientific resources already integrated by the application developers.

The application should support the introduction and use of external scientific resources, including resources that its built-in searches cannot access.

Examples include:

- Institutional databases.
- Private or locally maintained spectral reference libraries.
- Specialized databases without public APIs.
- Collections of published reference measurements.
- Custom scientific datasets and reference materials.
- External scientific models and computational resources.

Requirements:

- Allow users to introduce external scientific resources not already included in the application's resource catalogue.
- Support user-provided reference databases and libraries where technically feasible.
- Support connections through appropriate interfaces, APIs, local files or other integration methods.
- Allow users to import data from resources that cannot be directly connected.
- Make compatible user-provided resources available to relevant scientific tools and workflows.
- Allow users to manage, update, replace and remove their own resource integrations.
- Preserve source information, metadata, licensing information and provenance.
- Clearly distinguish built-in, externally connected and user-provided resources.
- Communicate integration limitations and unsupported functionality.
- Avoid assuming that externally supplied resources are scientifically reliable without appropriate assessment.

Where direct integration is not possible, alternative approaches such as importing compatible data should be considered.

### 1.10 Dependencies and Tool Relationships

Maintain explicit relationships between shared tools, scientific capabilities and their dependencies.

For example, a spectral analysis capability may depend on:

- Data import and interpretation.
- Wavelength calibration.
- Numerical processing.
- Scientific reference databases.
- Graphing and visualization.
- Uncertainty analysis.

Requirements:

- Document dependencies between tools and capabilities.
- Identify required inputs, supporting resources and prerequisites.
- Detect missing requirements where practical.
- Identify when a capability depends on another tool, resource or scientific method.
- Assess the effects of changes to shared tools on other workspaces and workflows.
- Avoid introducing changes that unexpectedly break dependent capabilities.
- Keep dependency information consistent with the capability inventory and technical documentation.

### 1.11 Extensibility Across Scientific Areas

The shared capability system must accommodate new scientific disciplines, tools and research requirements.

When introducing or extending a capability, consider:

- Whether it belongs in one scientific workspace or multiple workspaces.
- Whether existing shared functionality can support it.
- Whether it introduces new dependencies.
- Whether it could benefit additional scientific areas.
- Whether it requires modifications to existing workflows or resources.
- Whether it introduces new scientific, technical or compatibility requirements.

New capabilities should be evaluated in the context of the wider application rather than developed as isolated additions.

## 2. Future Functional Possibilities

The following capabilities are worth considering but are not initial development priorities.

### 2.1 Advanced Capability Management

- Automatically identify opportunities to reuse capabilities across disciplines.
- Detect overlapping functionality and opportunities for consolidation.
- Maintain an interactive dependency and relationship map between tools.
- Track capability maturity, implementation status, scientific validation status and known limitations.
- Identify when changes to shared capabilities may affect other workspaces.
- Recommend improvements to the shared capability system as the application expands.

### 2.2 Advanced Workflow Management

- Workflow branching and comparison.
- Reusable cross-disciplinary workflow templates.
- Automated identification of affected downstream stages.
- Advanced workflow optimization.
- Recommendations for alternative tools or methods.
- More sophisticated workflow dependency management.

### 2.3 Shared Resource Discovery

- Automatically identify useful scientific resources across disciplines.
- Recommend resources based on the current research context.
- Expand reference libraries through community contributions.
- Allow compatible user-provided reference libraries to be searched alongside built-in resources.

### 2.4 Advanced User Integrations and Extensions

Consider introducing a modular extension system that allows users to develop, install and manage their own scientific tools and analytical methods.

Potential functionality:

- User-created scientific tools.
- Custom analytical methods and algorithms.
- Specialized data-processing procedures.
- Custom database connectors and resource adapters.
- User-defined scientific models.
- Extensions that integrate with existing shared capabilities.
- User-defined data mappings for unfamiliar database structures or formats.

Such a system would require research into:

- Security and permissions.
- Compatibility with the application's architecture.
- Scientific validation and reliability.
- Documentation of methods, assumptions and limitations.
- Versioning and dependencies.
- Attribution and licensing.
- Integration into relevant workspaces and workflows.
- Safe installation, execution, updating and removal.

This is a future possibility rather than an initial requirement.

### 2.5 Sharing User-Created Tools and Extensions

Consider allowing users to share custom scientific tools, analytical methods and extensions with other users.

Potential functionality:

- Share custom tools independently or alongside workflows that use them.
- Allow recipients to obtain required tools when importing a shared workflow.
- Identify missing, unavailable or incompatible tools.
- Include documentation explaining purpose, methodology, inputs, outputs, assumptions and limitations.
- Preserve creator attribution, version history and licensing information.
- Allow users to inspect and evaluate tools before installing or using them.
- Distinguish community-created tools from independently tested or scientifically validated tools.
- Allow creators to publish updates while preserving compatibility with existing workflows where possible.
- Provide appropriate security checks before installing or executing externally created functionality.

**Important safeguard:** Sharing a workflow must not automatically install or execute unfamiliar tools. Users must be able to inspect and approve required components before using them.

## 3. Design Guidance

The following principles should guide architecture, interface and workflow design without prescribing exact layouts or implementations.

### 3.1 Shared Functionality

- Prefer common underlying implementations where practical.
- Avoid unnecessary duplication of tools and functionality.
- Allow shared tools to adapt to different scientific contexts.
- Maintain consistent fundamental behaviour across workspaces.
- Avoid forcing every workspace to expose every available capability.
- Keep specialized functionality accessible where scientifically appropriate.

### 3.2 Contextual Adaptation

- Tools should intelligently recognize their scientific context.
- Automatic configurations should remain understandable and adjustable.
- Advanced functionality should remain accessible.
- Contextual defaults should never replace scientific judgement.
- Users should retain control over consequential analytical choices.

### 3.3 Cross-Disciplinary Integration

- Make transitions between scientific areas understandable.
- Preserve scientific context when moving between tools and workspaces.
- Avoid concealing methodological or disciplinary differences.
- Prioritize scientific compatibility over convenience.
- Avoid combining unrelated capabilities simply to create the appearance of integration.

### 3.4 Capability and Dependency Management

The capability inventory should form part of the application's technical and scientific documentation.

It should help answer:

- What capabilities exist?
- Where are they used?
- What do they do in each scientific area?
- Why are they implemented that way?
- What depends on them?
- Where else could they be useful?
- What would be required to extend or reuse them?
- What other parts of the application could be affected by changes?

The inventory should remain maintainable and useful as the application grows.

### 3.5 External Resources and Extensions

- Clearly distinguish application-provided, externally connected and user-provided resources.
- Preserve provenance and attribution.
- Make limitations and compatibility requirements understandable.
- Avoid assuming that external integrations are reliable or scientifically validated.
- Prioritize security when introducing external functionality.
- Keep user-created and community-provided tools distinguishable from established and independently validated methods.

### 3.6 Long-Term Flexibility

- Do not prescribe a permanent list of shared capabilities.
- Allow existing tools to evolve as scientific requirements change.
- Reassess opportunities for reuse when new disciplines or workflows are introduced.
- Avoid rigid dependency structures that prevent future expansion.
- Evaluate shared functionality in the context of the wider application architecture.

## 4. Implementation Status

### Core Functional Requirements

The initial application should establish:

1. Shared scientific tools accessible independently and within relevant workspaces.
2. Context-aware tool behaviour with user-adjustable configurations.
3. A maintained capability and integration inventory.
4. Shared underlying capabilities where appropriate.
5. Cross-disciplinary workflows with clearly identifiable transitions and stages.
6. Automatic data and method compatibility assessment.
7. Workflow continuity and preservation of research context.
8. Shared scientific resources and reference libraries.
9. User-managed external resources through supported integrations or imports.
10. Documented dependencies and relationships between capabilities.
11. An extensible shared capability structure that accommodates additional scientific areas.

### Future Functional Possibilities

Not initial priorities:

- Advanced automated capability and dependency management.
- Advanced workflow branching, templates and optimization.
- Automated cross-disciplinary resource recommendations.
- User-created scientific tools, analytical methods and extensions.
- A modular extension or plugin ecosystem.
- Community sharing of user-created tools and extensions.
- Sharing custom tools alongside workflows that depend on them.

### Design Guidance

Exact tool layouts, navigation arrangements, integration mechanisms, dependency implementations and extension architectures remain open for later research and technical planning.

The implementation should be determined by scientific requirements, usability, technical feasibility, security, maintainability and the wider application architecture.

---

## General Principle

Shared tools and capabilities should make the application function as a connected scientific environment rather than a collection of isolated disciplinary applications.

Users should be able to access common functionality wherever it is relevant, adapt tools to their scientific context, combine capabilities across disciplines and introduce external resources when necessary.

All integrations and workflows must preserve scientific context, compatibility information, provenance and user control.

The system should remain expandable, allowing capabilities developed for one scientific area to benefit others where appropriate, without compromising scientific validity or unnecessarily complicating the application.

The ultimate objective is to support coherent, traceable and scientifically appropriate research workflows across the entire application.
