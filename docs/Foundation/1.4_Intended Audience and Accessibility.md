# 1.4 — Intended Audience and Accessibility

## Purpose

Establish the intended audience of the application and define the expectation that its scientific capabilities should remain accessible to a broad range of users.

The application should accommodate beginners, amateur astronomers, students, educators and experienced researchers. Differences in scientific knowledge or technical experience should influence how functionality is presented and supported, but should not unnecessarily restrict what users can accomplish.

Accessibility should be achieved through thoughtful interface design, understandable explanations, appropriate guidance and flexible workflows without sacrificing scientific depth, methodological accuracy or professional capability.

## 1.4.1 Intended User Groups

The application should support a diverse audience with different interests, objectives and levels of experience.

**Primary intended user groups include:**

- **Beginners:** Individuals developing an interest in astronomy or learning how to use scientific tools and investigate astronomical subjects.
- **Amateur astronomers:** Individuals conducting independent observations, research, analysis and exploration outside formal professional research environments.
- **Students:** Individuals studying astronomy, astrophysics, planetary science or related scientific disciplines.
- **Educators:** Individuals using the application to demonstrate scientific concepts, support instruction and develop educational activities.
- **Experienced researchers:** Individuals conducting more advanced scientific investigations using observational data, analytical methods, modelling and computational tools.
- **Interdisciplinary users:** Individuals whose research combines astronomy with other scientific disciplines or methods.

**Core requirements**

- Accommodate users across these different groups.
- Avoid designing the application exclusively around professional researchers or complete beginners.
- Recognize that users may have substantial knowledge in one scientific area while being unfamiliar with another.
- Allow users to develop their capabilities as their scientific knowledge and experience increase.
- Avoid unnecessary distinctions between users based solely on their experience level.

## 1.4.2 Accessibility Without Sacrificing Scientific Depth

The application should make advanced scientific capabilities approachable without reducing their underlying complexity or scientific validity.

**Core requirements**

- Provide understandable explanations of scientific tools, methods and terminology.
- Make common operations approachable for users with limited technical experience.
- Provide access to advanced functionality without requiring users to navigate unnecessarily simplified versions of scientific tools.
- Explain important parameters, assumptions, limitations and methodological choices.
- Distinguish between simplified educational explanations and scientifically complete analytical methods.
- Allow users to explore advanced capabilities as their knowledge develops.
- Avoid concealing important scientific information merely to simplify the interface.
- Preserve access to detailed results, metadata and methodological information where relevant.

**Design guidance**

A beginner-friendly experience should help users understand and use scientific capabilities, not replace those capabilities with oversimplified demonstrations.

Advanced users should be able to access the information and controls they require without being forced through introductory explanations or unnecessary guidance.

## 1.4.3 Flexible Levels of Guidance

Users should be able to receive an appropriate amount of assistance depending on their experience, the task being performed and the complexity of the scientific operation.

**Core requirements**

- Provide contextual explanations and guidance where useful.
- Explain unfamiliar scientific terminology and concepts.
- Offer assistance with complex workflows and analytical operations.
- Make relevant documentation and educational resources accessible from appropriate contexts.
- Avoid overwhelming experienced users with unnecessary introductory material.
- Allow users to seek additional explanation when needed.
- Clearly communicate when guidance is simplified, incomplete or intended for educational purposes.
- Ensure guidance does not substitute for appropriate scientific validation or methodological judgment.

**Design guidance**

Guidance should be available when it is useful rather than imposed uniformly across the application.

Different tasks may require different levels of explanation, even for the same user.

## 1.4.4 Scientific and Technical Experience

The application should recognize that scientific knowledge, mathematical ability, programming experience and familiarity with software are separate dimensions of user experience.

**Core requirements**

- Avoid assuming that users possess advanced programming skills.
- Avoid assuming that familiarity with the interface implies scientific expertise.
- Provide appropriate support for mathematical and scientific concepts.
- Make relevant technical requirements understandable.
- Allow users to access advanced controls and methods when they have the necessary knowledge.
- Support workflows that do not require programming where practical.
- Preserve opportunities for more advanced computational and programmatic approaches.
- Clearly communicate when a task requires specialized scientific knowledge, external software or technical preparation.

**Design guidance**

The application should not treat every user as having the same background.

A user may be an experienced observational astronomer but a beginner in spectroscopy, or an advanced student who is unfamiliar with computational modelling. The application should accommodate these differences without imposing a single fixed user level.

## 1.4.5 Accessibility and Usability

The application should be designed to remain usable across a range of user needs and working conditions.

**Core requirements**

- Maintain readable text, understandable terminology and clear interface organization.
- Use appropriate visual contrast and distinguishable interface elements.
- Avoid relying exclusively on colour to communicate important information.
- Support appropriate keyboard interaction and navigation.
- Provide clear feedback for important actions, operations and errors.
- Make complex information understandable through suitable presentation and organization.
- Avoid unnecessary interface clutter and interaction complexity.
- Consider accessibility requirements throughout design and development rather than treating them as optional additions.

**Future considerations**

- Additional accessibility preferences and interface adjustments.
- Expanded support for assistive technologies.
- Alternative presentation methods for complex scientific information.
- Further user-controlled display and interaction options.

Accessibility requirements should be evaluated against established standards and practical user needs during interface research and development.

## 1.4.6 Learning and Progression

The application should support users as they develop scientific knowledge and become more comfortable with its capabilities.

**Core requirements**

- Provide access to educational resources relevant to the application's scientific subjects.
- Support progression from introductory concepts to more advanced scientific material.
- Connect explanations and learning resources to relevant tools and research activities.
- Allow users to explore unfamiliar scientific areas without requiring prior expertise in every discipline.
- Support independent learning and experimentation.
- Avoid permanently restricting functionality based on a user's presumed experience level.
- Allow users to access more detailed information and advanced controls as appropriate.

**Design guidance**

The application should help users grow into its capabilities.

A beginner should be able to start with understandable guidance and gradually undertake more advanced investigations without needing to move to an entirely different application.

## 1.4.7 User Flexibility and Personal Working Preferences

Users should be able to work in ways that suit their individual needs and research experience.

**Core requirements**

- Support different levels of interface guidance and detail where appropriate.
- Allow users to configure relevant preferences without compromising essential functionality.
- Avoid forcing all users into identical workflows.
- Support both guided and independent approaches to scientific activities.
- Preserve access to advanced controls and information regardless of introductory guidance preferences.
- Ensure personal preferences do not silently alter scientific methods or data.

Detailed customization requirements are established in Section 6.8.

## General Principles

- The application should accommodate beginners and experienced researchers.
- Scientific depth must not be sacrificed for accessibility.
- Advanced functionality should not be unnecessarily restricted by introductory design.
- Scientific knowledge, mathematical experience and programming ability should not be treated as interchangeable.
- Guidance should be contextual, useful and appropriate to the task.
- Users should be able to develop their knowledge and capabilities over time.
- Accessibility should be considered throughout application design and development.
- Different users should be able to approach scientific work in ways suited to their experience and objectives.
- The application should remain approachable without becoming scientifically superficial.

**General principle:** The application should make serious astronomy research approachable to a broad audience while preserving the scientific depth, flexibility and methodological rigor required by advanced users.

## Implementation Boundary

This subsection establishes the intended audience and general accessibility expectations.

It does not prescribe specific interface layouts, accessibility technologies, educational curricula, user account categories or detailed customization controls.

These requirements are developed further in Sections 6 and 7 and should be evaluated through appropriate usability, accessibility and educational research.
