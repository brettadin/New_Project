# 3.7 — Scientific Modelling, Simulation and Prediction

## Purpose

The application should provide capabilities for applying, examining and evaluating scientific models relevant to astronomical research.

Scientific models allow researchers to investigate physical processes, estimate otherwise inaccessible properties, test hypotheses and compare theoretical predictions with observational evidence.

The application should support established scientific models as well as configurable modelling approaches that can be adapted to different research questions.

Modelling capabilities should accommodate both relatively straightforward calculations and more advanced computational simulations, depending on the scientific requirements and available resources.

The initial modelling priority should be planetary and exoplanet atmospheric characterization. The broader framework should remain extensible to other astronomical and planetary modelling disciplines as the application develops.

Users should be able to examine model inputs, assumptions, parameters, outputs and limitations. Model results should remain distinguishable from direct observations and should not be presented as established scientific conclusions without appropriate evaluation.

## 3.7.1 General Modelling Framework

### Core Requirements

- Support the application and evaluation of scientific models across relevant astronomical disciplines.
- Accommodate analytical, numerical and computational modelling approaches.
- Support both predefined scientific models and configurable model parameters.
- Allow models to use observational data, reference information and user-supplied inputs where appropriate.
- Preserve the distinction between model inputs, assumptions, calculated outputs and observational measurements.
- Allow users to examine the methods and parameters used by a model.
- Support comparison between different models addressing similar research questions.
- Allow modelling capabilities to integrate with other scientific tools and workflows.
- Accommodate additional modelling approaches as scientific requirements develop.

### Design Guidance

The application should provide a common foundation for scientific modelling without forcing every discipline to use the same mathematical or computational approach.

Different models may have fundamentally different assumptions, inputs, computational requirements and interpretations.

Shared functionality should improve usability and consistency while preserving the specialized requirements of individual scientific models.

## 3.7.2 Model Selection and Applicability

### Core Requirements

- Allow users to identify and select models appropriate to their research objectives.
- Provide information about the scientific purpose and intended application of available models.
- Identify relevant input requirements and assumptions.
- Communicate limitations and known restrictions.
- Evaluate whether supplied data and parameters are suitable for a selected model.
- Distinguish between models intended for exploratory investigation and those suitable for quantitative scientific analysis.
- Support comparison of alternative models where appropriate.
- Avoid automatically treating a model as suitable simply because it can accept the available inputs.
- Identify relevant dependencies, external resources and computational requirements.
- Make clear when a model is experimental, incompletely validated or unsuitable for a particular scientific application.

### Design Guidance

Model selection should be guided by scientific suitability rather than convenience alone.

A model may produce numerical outputs even when its assumptions are not satisfied by the available observations.

The application should help users understand when a model is appropriate, when additional information is required and when alternative approaches should be considered.

## 3.7.3 Model Parameters and Configuration

### Core Requirements

- Allow users to inspect and configure relevant model parameters.
- Support appropriate parameter units, ranges and constraints.
- Identify default, user-supplied, measured, estimated and assumed parameter values.
- Support fixed and variable parameters where appropriate.
- Allow users to define initial conditions and boundary conditions when required.
- Preserve parameter values and configurations associated with individual modelling operations.
- Communicate when parameter combinations are invalid or incompatible.
- Support saving and reusing suitable model configurations.
- Allow users to compare different parameter configurations without losing previous results.
- Identify the source and scientific basis of relevant input parameters where available.

### Design Guidance

Model parameters can substantially influence scientific results.

The application should make their meaning and role understandable, particularly when values are assumed, estimated or derived from external sources.

Reusing a configuration should not imply that its parameters remain suitable for every object, dataset or investigation.

## 3.7.4 Analytical and Numerical Calculations

### Core Requirements

- Support appropriate analytical calculations relevant to astronomical research.
- Accommodate numerical methods for problems that cannot be solved conveniently through analytical expressions.
- Support calculations involving physical properties, relationships and scientific quantities.
- Preserve relevant units and numerical conventions.
- Allow users to inspect calculation inputs and resulting outputs.
- Communicate relevant assumptions and approximations.
- Support appropriate numerical precision and error handling.
- Allow calculation results to be reused in subsequent analyses.
- Distinguish direct calculations from estimates that depend on additional assumptions.

### Design Guidance

Some scientific models can be evaluated using relatively straightforward calculations, while others require numerical methods or iterative procedures.

The application should support both without obscuring the mathematical or physical basis of the results.

Numerical output should not imply greater scientific precision than the inputs, assumptions and calculation methods justify.

## 3.7.5 Physical Simulation

### Core Requirements

- Support simulations of relevant astronomical and physical processes.
- Accommodate time-dependent and condition-dependent simulations.
- Allow users to configure relevant initial conditions, parameters and simulation settings.
- Support appropriate numerical integration and iterative calculations.
- Allow examination of simulation outputs at relevant stages or intervals.
- Support repeated simulations using different parameters or assumptions.
- Preserve simulation configurations and outputs.
- Communicate computational limitations and relevant assumptions.
- Allow simulation results to be compared with observations and alternative models.
- Identify incomplete, failed or interrupted simulation operations.

### Design Guidance

Simulation capabilities may vary substantially in complexity and computational requirements.

The application should support useful scientific simulations without requiring every research area to use the same computational approach.

Where a simulation involves significant approximations, numerical instability or restricted validity, these limitations should remain accessible to users.

## 3.7.6 Astronomical and Planetary Modelling

### Core Requirements

Support modelling relevant to astronomical and planetary research, including:

- Planetary physical properties.
- Planetary mass, radius and density.
- Planetary interior and structural models.
- Planetary atmospheric structure.
- Atmospheric temperature and pressure profiles.
- Atmospheric composition and chemical processes.
- Stellar properties and atmospheric models.
- Stellar and planetary evolution.
- Orbital and dynamical systems.
- Radiation and energy balance.
- Surface and environmental conditions where appropriate.
- Other relevant physical and astrophysical processes.

Allow models to incorporate observational constraints and relevant external scientific information.

Support comparison between different model assumptions and predicted physical properties.

### Design Guidance

Different astronomical subjects require different physical models.

Planetary atmospheric modelling, stellar structure calculations and orbital dynamics may have little methodological similarity despite sharing common scientific principles.

The application should provide specialized modelling capabilities where appropriate while allowing their results to contribute to broader investigations.

The initial implementation priority for planetary modelling is atmospheric characterization, as described in Section 3.7.15. Other planetary and astrophysical modelling disciplines should remain part of the broader scope without unnecessarily complicating initial development.

## 3.7.7 Atmospheric and Spectral Modelling

### Purpose

Atmospheric and spectral modelling should be a major initial modelling capability, particularly for investigating the physical and chemical properties of planetary and exoplanet atmospheres.

These capabilities should connect directly with the application's spectroscopy, observational analysis and planetary research environments.

### Core Requirements

Support theoretical and computational modelling of astronomical spectra, including:

- Synthetic spectral generation.
- Atmospheric transmission, emission and reflection.
- Atmospheric absorption and emission processes.
- Molecular and atomic contributions to spectra.
- Atmospheric composition and molecular abundances.
- Temperature and pressure structures.
- Temperature-pressure profiles.
- Atmospheric chemistry and relevant chemical processes.
- Radiative transfer.
- Clouds and hazes.
- Atmospheric thermal properties.
- Atmospheric circulation and thermal structure where scientifically and computationally feasible.

Allow users to configure relevant atmospheric parameters and investigate how changes affect predicted observable properties.

Support comparison between synthetic and observed spectra.

Allow examination of modelled spectral features and their possible physical origins.

Support investigation of alternative atmospheric configurations and competing explanations for observed features.

Preserve model assumptions, input parameters, model identity, version information and relevant reference information.

Distinguish synthetic spectra from observational measurements and other derived datasets.

### Forward and Inverse Modelling

The application should support both forward and inverse modelling approaches where appropriate.

**Forward modelling:** Users specify planetary and atmospheric conditions, such as composition, molecular abundances and temperature-pressure structure, and calculate the expected observable properties.

**Inverse modelling:** Users begin with observational measurements and investigate which physical conditions, atmospheric structures and compositions could plausibly explain those observations.

Inverse modelling should accommodate appropriate parameter estimation and atmospheric retrieval approaches, subject to the assumptions and limitations of the selected scientific methods.

Users should be able to:

- Compare model predictions with actual observations.
- Investigate how changing atmospheric parameters affects predicted spectra.
- Examine alternative atmospheric configurations that may explain the same observations.
- Evaluate parameter constraints and degeneracies.
- Identify when available observations are insufficient to constrain a particular atmospheric property.
- Distinguish between retrieved or inferred properties and directly measured quantities.

### Integration with Planetary and Orbital Models

Atmospheric and spectral modelling should integrate with relevant planetary and orbital models where scientifically appropriate.

Where supported by the selected physical models, allow planetary and orbital configurations to contribute to the calculation of predicted spectral outputs.

Relevant model inputs may include:

- Planetary position and orbital phase.
- Transit and secondary eclipse geometry.
- Observer viewing angle and planetary orientation.
- Stellar illumination and irradiation conditions.
- Day-side and night-side atmospheric properties.
- Changes in observable atmospheric properties throughout an orbit.
- Relevant planetary and atmospheric parameters established by associated models.

Support investigation of how changing orbital configurations, viewing geometry, illumination and atmospheric conditions affect predicted spectra.

Where appropriate, allow users to generate and compare synthetic spectra for different orbital phases, transit configurations, eclipse conditions and planetary viewing geometries.

Preserve the relationships between the resulting spectra, their originating planetary and orbital models, input parameters, assumptions and calculation history.

**Important distinction:** Interactive visual representations of planetary systems should not independently determine scientific spectral outputs. Spectral calculations must be produced by appropriate physical and computational models using the relevant parameters and assumptions.

The application should distinguish model-generated spectral predictions from observational measurements and preserve the provenance of both.

### Design Guidance

Atmospheric and spectral modelling can help interpret observed features and investigate possible physical conditions.

A model-generated spectrum represents the predictions of a particular model and parameter configuration. It should not be presented as equivalent to an observed spectrum.

Forward modelling and inverse modelling are related but distinct activities. The application should preserve this distinction in its workflows, outputs and interpretation.

The application should investigate established atmospheric modelling and retrieval frameworks, their scientific capabilities, assumptions, limitations and suitability for integration.

## 3.7.8 Model Fitting and Parameter Estimation

### Core Requirements

- Support fitting scientific models to observational data.
- Allow users to select appropriate fitting methods.
- Support estimation of model parameters from available observations.
- Accommodate relevant parameter constraints and initial values.
- Support different fitting approaches where scientifically appropriate.
- Provide access to fitted parameters and associated uncertainties.
- Allow examination of residuals and fitting quality.
- Support comparison of alternative models and parameter configurations.
- Communicate convergence problems, degeneracies and other fitting limitations.
- Preserve the observations, model configurations and outputs associated with each fitting operation.
- Identify when the available observations cannot adequately constrain the requested parameters.

### Design Guidance

Model fitting should be treated as a method of evaluating how well a particular model and its parameters represent available observations.

A successful fit does not automatically establish that the model is physically correct or uniquely supported by the evidence.

The application should allow users to examine parameter constraints, alternative solutions and potential limitations rather than presenting fitted values without context.

## 3.7.9 Uncertainty, Sensitivity and Parameter Exploration

### Core Requirements

- Support examination of uncertainty in model inputs and outputs.
- Accommodate parameter ranges and probability distributions where appropriate.
- Support sensitivity analysis.
- Allow users to investigate how changes in model parameters affect predicted results.
- Support uncertainty propagation through appropriate modelling procedures.
- Accommodate parameter correlations and degeneracies where relevant.
- Allow comparison of results produced under different assumptions.
- Distinguish observational uncertainty from model uncertainty and uncertainty associated with assumptions.
- Communicate when a model is sensitive to poorly constrained parameters.
- Identify when numerical or methodological limitations prevent reliable uncertainty estimation.

### Design Guidance

Model outputs may depend strongly on input parameters, assumptions and numerical methods.

Users should be able to investigate these dependencies and understand which parameters have the greatest influence on a result.

Where uncertainty cannot be quantified reliably, the application should communicate that limitation rather than imply that a model output is more certain than the evidence supports.

## 3.7.10 Model Comparison and Evaluation

### Core Requirements

- Allow users to compare multiple models addressing the same or related research questions.
- Support comparison of predicted and observed measurements.
- Provide appropriate measures of model agreement and fitting quality.
- Allow examination of residuals and systematic differences.
- Support comparison of alternative assumptions and parameter configurations.
- Preserve information about the methods and criteria used for comparison.
- Communicate limitations of individual comparison methods.
- Avoid automatically treating the best numerical fit as the most scientifically appropriate model.
- Support evaluation of model suitability against the available observational evidence.

### Design Guidance

Different models may explain the same observations with different assumptions or levels of complexity.

Model comparison should consider scientific suitability, observational constraints and methodological limitations rather than relying exclusively on numerical agreement.

The application should help users understand why models differ and what those differences imply for the investigation.

## 3.7.11 Predictions and Scientific Forecasting

### Core Requirements

- Support generation of predictions from appropriate scientific models.
- Allow users to specify relevant prediction conditions and time ranges.
- Support predictions of observable and physical quantities where appropriate.
- Allow predicted results to be compared with subsequent observations.
- Preserve the assumptions and parameters used to generate predictions.
- Communicate uncertainty and limitations associated with predicted values.
- Distinguish predictions from observations and confirmed scientific findings.
- Support updating or reassessing predictions when new observations become available.

### Design Guidance

Predictions can support observational planning, hypothesis testing and investigation of future or unobserved conditions.

Their scientific value depends on the assumptions, input data and validity of the underlying model.

The application should make clear that a prediction represents an expected outcome under specified conditions rather than a confirmed observation.

## 3.7.12 Reproducibility and Model Records

### Core Requirements

- Preserve the identity and version of the model used where available.
- Record relevant input datasets and parameter configurations.
- Preserve assumptions, initial conditions and computational settings.
- Maintain relationships between model inputs, outputs and associated analyses.
- Allow users to revisit previous model configurations and results.
- Support comparison between successive model runs.
- Preserve historical outputs when models or parameters change.
- Identify relevant external dependencies and reference information.
- Provide sufficient information to understand and reproduce modelling operations where technically possible.
- Distinguish original model outputs from subsequently processed or transformed results.

### Design Guidance

Model results should remain understandable after the original modelling operation has been completed.

Users should be able to determine which model, data, assumptions and parameters produced a particular output.

Detailed analysis records and reproducibility requirements are established in Section 5. Project-level preservation and organization are addressed in Section 6.4.

## 3.7.13 Computational Requirements and Resource Management

### Core Requirements

- Accommodate modelling operations with different computational requirements.
- Identify when an operation may require substantial processing time or resources.
- Support monitoring of ongoing modelling operations.
- Allow users to inspect progress where practical.
- Support cancellation of operations where technically possible.
- Communicate failures, resource limitations and incomplete operations.
- Preserve completed results when a subsequent operation fails.
- Allow computational approaches to expand as the application develops.
- Avoid requiring advanced computational resources for every scientific modelling activity.
- Communicate when a modelling method requires external software, services or computational resources.

### Design Guidance

Some scientific calculations may complete almost immediately, while advanced simulations may require substantial computational resources.

The application should account for these differences and communicate relevant requirements without unnecessarily complicating routine scientific work.

## 3.7.14 Integration with Other Scientific Capabilities

### Core Requirements

- Allow models to use compatible observational measurements and derived datasets.
- Support integration with spectroscopy, photometry, imaging and specialized observational analysis.
- Allow model outputs to contribute to comparative and integrated investigations.
- Support the use of model results in subsequent scientific calculations.
- Preserve units, uncertainty, provenance and relevant parameter information.
- Identify compatibility requirements before combining model outputs with other data.
- Maintain distinctions between observations, model predictions and derived interpretations.
- Support integration with relevant scientific reference resources and external modelling tools where appropriate.

### Design Guidance

Modelling should be integrated throughout the research environment.

For example:

- Atmospheric models may be compared with observed spectra.
- Orbital models may be constrained by transit and radial velocity measurements.
- Stellar models may provide parameters needed for planetary characterization.
- Planetary models may be compared across Solar System objects and exoplanets.
- Model predictions may be incorporated into broader investigations alongside observational evidence.

Detailed orbital and dynamical modelling is addressed in Section 3.8. Spectral observations and their analysis are addressed in Section 3.3, while photometric and transit observations are addressed in Section 3.4.

Scientific visualization of model outputs should be coordinated with Section 3.10 and the associated application visualization requirements.

The application should support these relationships without obscuring the origin or scientific status of individual results.

## 3.7.15 Planetary and Exoplanet Modelling Priorities

### Initial Priority: Atmospheric Characterization and Modelling

The initial focus of planetary and exoplanet modelling should be atmospheric science.

The application should support investigation of the physical and chemical properties of planetary atmospheres using observational data, scientific models and established analytical methods.

Initial research and capability development should prioritize:

- Atmospheric composition and molecular abundances.
- Atmospheric temperature and pressure structures.
- Temperature-pressure profiles.
- Atmospheric chemistry.
- Radiative transfer.
- Absorption and emission processes.
- Clouds and hazes.
- Atmospheric thermal properties.
- Atmospheric structure and relevant physical conditions.
- Model-generated spectra.
- Forward modelling and inverse modelling.
- Comparison between predicted and observed atmospheric properties.

These capabilities should connect directly with spectroscopy, observational analysis, planetary research and comparative investigations.

### Comparative Planetary Research

The application should support comparisons between different planetary atmospheres and their relevant physical properties.

This includes:

- Solar System planets.
- Exoplanets.
- Different types and classes of exoplanets.
- Planets orbiting different stellar types.
- Planets with different atmospheric compositions.
- Modelled and observed atmospheric properties.

The Solar System research environment should provide valuable reference cases for comparative planetary research.

Users should be able to investigate similarities and differences between planetary environments while accounting for differences in observational coverage, data quality, measurement methods and model assumptions.

Comparative results should not imply that different objects or datasets are directly equivalent when their underlying conditions or measurement limitations differ.

### Modelling Visualization Requirements

Where appropriate, users should be able to visualize atmospheric properties and modelling results.

Potential capabilities include:

- Atmospheric profiles.
- Temperature-pressure distributions.
- Molecular abundance profiles.
- Synthetic spectral predictions.
- Observed-versus-modelled comparisons.
- Interactive model parameter exploration.
- Planetary structure representations.
- Atmospheric layers and profiles.
- Orbital configurations.
- Comparative planetary visualizations.

These visualizations should be scientifically informative and integrated into the wider research environment without creating unnecessary interface clutter.

The visualization requirements in this subsection establish the scientific information that should be represented. General visualization tools, presentation and interaction requirements are addressed in Section 3.10.

### Future Modelling Expansion

Additional planetary modelling disciplines should remain within the longer-term vision but should not unnecessarily complicate initial development.

Potential future areas include:

- Planetary interiors and internal structure.
- Planetary formation.
- Planetary evolution.
- Orbital dynamics.
- Planetary geophysics.
- Other physical and computational investigations.

Their development priorities should be determined through research, considering scientific value, dependencies, implementation complexity, computational requirements and their relationship with existing capabilities.

The application should not attempt to implement these areas prematurely simply because they form part of the broader scientific scope.

### Scientific Research Requirement

The initial research phase must thoroughly investigate:

- Atmospheric physics.
- Atmospheric chemistry.
- Radiative transfer.
- Forward modelling.
- Inverse modelling.
- Atmospheric retrieval frameworks.
- Computational approaches.
- Molecular abundance estimation.
- Temperature-pressure profile estimation.
- Uncertainty estimation and propagation.
- Parameter sensitivity and degeneracy.
- Model validation and comparison methods.

Research should identify established scientific software, models and frameworks that could be integrated, including their scientific capabilities, assumptions, limitations, dependencies and computational requirements.

Future modelling disciplines should also be investigated sufficiently to understand their potential dependencies and architectural implications, without requiring detailed implementation planning for every area immediately.

## General Principles

Scientific modelling, simulation and prediction should:

- Support analytical, numerical and computational approaches.
- Provide access to established scientific models and configurable methods.
- Make model assumptions, parameters and inputs understandable.
- Support simulations of relevant physical and astronomical processes.
- Prioritize planetary and exoplanet atmospheric characterization during initial development.
- Support forward and inverse modelling where scientifically appropriate.
- Allow quantitative model fitting and parameter estimation.
- Provide tools for uncertainty, sensitivity and parameter exploration.
- Support comparison between alternative models and observational evidence.
- Distinguish observations, model outputs, predictions and interpretations.
- Preserve model configurations, dependencies and results.
- Accommodate different computational requirements.
- Integrate model outputs with broader scientific investigations.
- Remain extensible to additional scientific disciplines as the application develops.

## General Principle

Scientific modelling should help users investigate physical processes, evaluate hypotheses and interpret observations while making the assumptions, limitations and uncertainty of model-dependent results clear.
