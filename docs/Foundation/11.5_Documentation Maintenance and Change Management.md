# 11.5 — Documentation Maintenance and Change Management

## Purpose

Establish consistent procedures for maintaining, updating, reviewing and correcting project documentation throughout the application's development and long-term operation.

Documentation must remain aligned with the approved requirements, actual implementation, scientific understanding and development history.

Changes must preserve important context and prevent outdated or contradictory information from becoming an unreliable source of truth.

## 11.5.1 Documentation as Part of Development

**Core requirements**

- Treat documentation as an integral part of research, planning, implementation, testing and maintenance.
- Identify documentation affected by significant development changes.
- Update relevant documentation as part of the corresponding authorized work.
- Avoid postponing necessary documentation updates indefinitely.
- Keep technical documentation consistent with actual implementation.
- Preserve relevant scientific findings, assumptions, limitations and references.
- Include documentation updates in development planning and completion criteria where appropriate.
- Do not claim work is fully documented when relevant records remain incomplete.

**Design guidance**

Documentation effort should be proportionate to the significance of the work.

Routine changes may require only a small update, while architectural, scientific or structural changes may require several documents to be reviewed.

## 11.5.2 Events Requiring Documentation Updates

**Core requirements**

Review and update relevant documentation when:

- New or revised application requirements are approved.
- Scientific research produces significant new findings.
- A scientific method, model or analytical approach is introduced or modified.
- Architectural or technical decisions are approved.
- New capabilities or major functionality are implemented.
- Existing functionality is modified, replaced or removed.
- Dependencies, frameworks, libraries or external integrations change.
- Data structures, storage arrangements or project formats change.
- Testing identifies defects, limitations or unexpected behaviour.
- Scientific verification or validation produces significant findings.
- Problems are resolved, deferred or escalated.
- Development priorities, milestones or dependencies change.
- Significant risks, blockers or future opportunities are identified.
- Previous decisions or assumptions become outdated.
- New requirements or implementation limitations affect other application areas.

Not every event requires updating every document. The AI must identify which authoritative records are actually affected.

## 11.5.3 Documentation Consistency and Accuracy

**Core requirements**

- Maintain consistency between requirements, architecture, implementation, testing and development records.
- Verify information against the relevant authoritative source before updating dependent documents.
- Ensure documentation describes actual functionality rather than intended or assumed functionality.
- Identify outdated descriptions, broken references and contradictory statements.
- Correct inaccurate information when discovered.
- Preserve important historical context when correcting or replacing information.
- Clearly distinguish planned, approved, implemented, tested and scientifically validated capabilities.
- Identify incomplete or experimental functionality.
- Avoid copying large sections of information into multiple documents when references are sufficient.

**Design guidance**

Documentation consistency does not mean every document must contain identical information.

Each document should maintain its own purpose and level of detail while accurately reflecting related authoritative records.

## 11.5.4 Documentation Review and Maintenance

**Core requirements**

- Periodically review important documentation for accuracy and continued relevance.
- Prioritize reviews of frequently referenced and authoritative records.
- Check that technical documentation remains consistent with the codebase.
- Identify obsolete dependencies, unavailable resources and outdated references.
- Review documentation affected by significant scientific or technical developments.
- Identify missing documentation that could obstruct development continuity.
- Update indexes and cross-references when documentation changes.
- Record significant corrections and revisions.

**Future possibilities**

- Automated documentation consistency checks.
- Broken-link detection.
- Identification of potentially outdated technical references.
- Automated comparison between documented capabilities and implementation.
- Documentation coverage reports.

## 11.5.5 Change History and Revision Tracking

**Core requirements**

- Preserve significant changes to authoritative documentation.
- Record what changed, when and why where appropriate.
- Identify the source of consequential changes, including user approvals and verified findings.
- Preserve previous decisions and superseded requirements when they provide useful historical context.
- Distinguish corrections, clarifications, requirement changes and implementation updates.
- Avoid silently rewriting historical records.
- Use version control where available to preserve document history.
- Maintain revision information for records that require independent historical tracking.

**Design guidance**

Not every minor wording correction requires a separate decision record.

Use version-control history for ordinary document changes and dedicated records for consequential decisions or changes that require additional explanation.

## 11.5.6 Handling Outdated and Superseded Documentation

**Core requirements**

- Identify documents or sections that are no longer authoritative.
- Mark superseded documents clearly.
- Provide references to their replacements where available.
- Preserve historical documents when they explain earlier development stages or decisions.
- Avoid leaving multiple apparently current versions of the same authoritative document.
- Review dependent documents when a major source is superseded.
- Identify outdated external scientific or technical references.
- Do not silently substitute newer scientific data, methods or results for historical information.
- Preserve the distinction between historical and current scientific understanding.

**Design guidance**

Superseded information should remain accessible when it contributes to understanding the project's history, but it must not be mistaken for current guidance.

## 11.5.7 Documentation Change Control and Approval

**Core requirements**

- Routine corrections and updates may be performed independently by the AI when they accurately reflect approved requirements or verified implementation.
- Significant changes to established requirements must follow the approval boundaries in Section 10.
- Consequential architectural, scientific, financial, security or privacy decisions must not be silently introduced through documentation edits.
- Proposed changes must remain distinguishable from approved changes.
- Record significant user decisions and approval conditions.
- Update affected documentation only after the relevant decision has been established.
- Preserve previous information when an approved change replaces an existing requirement or decision.

**Design guidance**

Documentation maintenance must not become an indirect way of expanding project scope or changing previously approved decisions.

## 11.5.8 Documentation Completion and Verification

**Core requirements**

- Identify documentation updates required by an implementation or research task.
- Check that relevant documents have been updated before reporting the task as fully documented.
- Verify that cross-references and authoritative locations remain correct.
- Ensure records contain sufficient context to be understood independently.
- Identify outstanding documentation work explicitly.
- Include documentation status in relevant development reports and handoffs.
- Update the Master Development Roadmap and rolling development record where appropriate.

Documentation completion should be assessed separately from software implementation and scientific validation.

## General Principles

- Documentation is part of development, not an optional afterthought.
- Updates should occur alongside the work that makes them necessary.
- Authoritative information must remain accurate and consistent.
- Significant changes must preserve their history and reasoning.
- Superseded information must be distinguishable from current guidance.
- Approval boundaries apply to documentation changes as well as implementation.
- Reviews should prioritize important and frequently used records.
- Documentation effort should remain proportionate to the significance of the work.

**General principle:** Documentation must evolve alongside the application while preserving accuracy, authority, traceability and historical context. It should remain a reliable representation of the project rather than gradually becoming an outdated description of what the application once intended to be.
