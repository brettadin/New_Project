

# 4.1 — Data Discovery and Resource Framework

## Purpose

The application should provide an integrated environment for discovering astronomical data, scientific information and relevant external resources.

Astronomical data is distributed across numerous archives, observatories, research institutions, databases and specialized repositories. Users should not be required to understand the structure and organization of every external provider before they can locate information relevant to their research.

The application should bring discovery capabilities together through a consistent interface while preserving the identity, scientific context and limitations of individual sources.

Discovery should accommodate both users who know exactly what object or dataset they are looking for and those who are exploring a broader scientific question.

The system should make it possible to begin with a straightforward search and progressively investigate more specific information without requiring unnecessary technical knowledge or configuration.

## 4.1.1 Unified Discovery Environment

### Core Requirements

- Provide a unified environment for discovering astronomical data and scientific resources.
- Allow searches to draw from multiple relevant external sources where integrations are available.
- Support discovery of observations, datasets, measurements, object information, scientific references and other relevant resources.
- Provide a consistent search experience across supported sources.
- Preserve the identity of the original provider for every discovered resource.
- Communicate which sources were searched and whether relevant integrations are available.
- Accommodate different resource types without treating them as interchangeable.
- Allow users to access more detailed information about individual sources and results.
- Support expansion as additional archives, databases and scientific resources become available.

### Design Guidance

The purpose of unified discovery is to reduce the fragmentation researchers encounter when searching across multiple scientific resources.

The application should provide a common entry point without pretending that all external sources contain the same information or support identical search capabilities.

Some resources may provide direct dataset retrieval, while others may provide object information, scientific references, catalogued measurements or access to external tools.

These distinctions should remain clear throughout the discovery experience.

## 4.1.2 Object-Focused Searches

### Core Requirements

- Support searches focused on specific astronomical objects or systems.
- Accommodate common object names, catalogue identifiers and other recognized designations.
- Support searches for individual objects and related systems where appropriate.
- Allow users to discover relevant observations, datasets, measurements, publications and reference information associated with an object.
- Identify potential matches when different sources use different names or identifiers for the same object.
- Communicate ambiguity when multiple objects may match a search.
- Allow users to inspect the identity and relevant properties of a matched object before proceeding.
- Support refinement of object-focused searches using relevant observational and scientific criteria.

### Examples

- Search for Jupiter and discover available observations, images, spectra and scientific references.
- Search for WASP-39 b and locate relevant observations, atmospheric measurements and publications.
- Search for a particular star and discover its catalogued properties, observations and associated planetary system.
- Search using an alternative catalogue designation and identify the corresponding astronomical object.

### Design Guidance

Object-focused searches should prioritize identifying the intended astronomical subject and locating resources associated with it.

The application should account for alternative names, catalogue identifiers, naming conventions and possible ambiguities.

A search result should not automatically be treated as a confirmed match merely because its name resembles the user's search.

## 4.1.3 Research-Focused Searches

### Core Requirements

- Support searches based on scientific subjects, research questions and investigative goals.
- Accommodate scientific terminology, general topic descriptions and relevant keywords.
- Allow users to discover datasets and resources that may contribute to a research question.
- Support searches involving scientific phenomena, physical processes, measurement types, astronomical environments and observational characteristics.
- Allow searches to identify potentially relevant resources across multiple astronomical objects.
- Support progressively refining broad research topics into more specific investigations.
- Preserve the distinction between research-topic relevance and confirmed scientific evidence.
- Allow users to explore related topics and resources where appropriate.

### Examples

- Search for water absorption in exoplanet atmospheres.
- Search for stellar variability and periodic brightness changes.
- Search for infrared observations of planetary atmospheres.
- Search for comparisons of atmospheric composition across multiple exoplanets.
- Search for observational evidence related to planetary atmospheric escape.

### Design Guidance

Research-focused searches should help users discover information even when they do not already know which astronomical objects or datasets are relevant.

The application should accommodate broader scientific language while helping users progressively identify more specific observations, measurements and resources.

Research-focused results should not be indiscriminately mixed with object-identification results. Their presentation should make the type and relevance of each result understandable.

## 4.1.4 Separation of Search Approaches

### Core Requirements

- Maintain a clear distinction between object-focused and research-focused searches.
- Allow users to select the appropriate search approach.
- Present results according to the purpose and context of the search.
- Avoid indiscriminately combining unrelated object matches, scientific topics, datasets and publications into one undifferentiated result list.
- Allow users to move between related search approaches where useful.
- Preserve the original search context when users refine or transition between searches.
- Support combined discovery when a research question requires both an astronomical object and a scientific subject.

### Design Guidance

Object-focused and research-focused searches may lead to overlapping resources, but they serve different purposes.

For example, searching for WASP-39 b should prioritize identifying the object and locating its associated observations. Searching for water absorption in exoplanet atmospheres should prioritize relevant scientific information and potentially useful observations across multiple objects.

The application should preserve these distinctions while allowing users to connect related discoveries.

A combined search should be presented as an intentional refinement rather than an uncontrolled mixture of unrelated results.

## 4.1.5 Search Input and Query Interpretation

### Core Requirements

- Support straightforward search input without requiring users to configure technical parameters first.
- Accommodate object names, catalogue identifiers, scientific terms, keywords and descriptive research questions.
- Support relevant variations in object naming and scientific terminology.
- Identify potential differences between an object search, a research-topic search and a search for a particular resource where practical.
- Allow users to correct or refine interpreted search terms.
- Communicate when a query is ambiguous or cannot be interpreted confidently.
- Avoid silently changing the scientific meaning or intended subject of a search.
- Support more advanced query options for users who need greater control.

### Design Guidance

Search interpretation should help users express what they are looking for without requiring them to understand the technical structure of every external database.

Automatic interpretation may assist with identifying likely objects, topics or search criteria, but users should retain control over the resulting query.

When interpretation is uncertain, the application should communicate the ambiguity rather than silently choosing an unsupported interpretation.

## 4.1.6 Progressive Search Refinement and Filtering

### Core Requirements

- Allow users to begin searching without first configuring filters.
- Make filtering optional rather than a prerequisite for discovery.
- Allow users to progressively narrow results as their research requirements become clearer.
- Provide filters relevant to the current search and available resource types.
- Allow users to refine an existing search without unnecessarily starting over.
- Preserve applicable search criteria when users move between result views.
- Support both straightforward filters and more advanced scientific criteria.
- Avoid requiring users to understand technical parameters they may not know.
- Communicate when a filter is unavailable or unsupported by a particular source.

### Examples

- Search for Jupiter, then narrow results to infrared observations.
- Search for JWST observations, then select a particular instrument.
- Search for an exoplanet, then narrow results by telescope, observation date or wavelength.
- Search for a broad research topic, then refine the results by measurement type or astronomical object.
- Search for stellar observations, then narrow results to a particular time range or observational technique.

### Design Guidance

Available filters should adapt to the search context and the types of resources being explored.

The application should not present every possible technical filter immediately. Common and understandable options should be accessible first, with more specialized criteria available when needed.

Filtering should help users investigate available resources without unnecessarily restricting discovery.

## 4.1.7 Search Results and Resource Presentation

### Core Requirements

- Present search results in a structured and understandable manner.
- Distinguish between astronomical objects, observations, datasets, measurements, publications, databases and other resource types.
- Identify the original source or provider of each result.
- Provide a useful summary of what each result represents.
- Display relevant identifying information and available metadata.
- Allow users to inspect more detailed information when needed.
- Communicate whether a result is directly accessible, requires additional access or links to an external resource.
- Identify potentially relevant limitations or compatibility concerns.
- Support sorting and filtering appropriate to the result type.
- Avoid presenting search results as scientifically validated merely because they were retrieved successfully.

### Design Guidance

Search results should provide enough information for users to decide whether a resource is worth investigating without overwhelming them with technical metadata.

The amount of detail displayed should depend on the resource type and the user's immediate needs.

Detailed metadata, technical information and source documentation should remain accessible without requiring every result to display all available information at once.

## 4.1.8 Search Relevance and Result Ranking

### Core Requirements

- Rank results according to their relevance to the user's search where appropriate.
- Consider relevant factors such as object identity, scientific subject, observation type, measurement characteristics and available metadata.
- Distinguish strong matches from potentially relevant or loosely related results.
- Avoid excluding potentially useful results solely because they are not the closest match.
- Allow users to inspect results beyond the highest-ranked entries.
- Communicate relevant reasons for ranking where practical.
- Keep ranking methods and criteria adjustable as the application develops.
- Document significant changes to ranking methods or search behaviour.

### Design Guidance

Relevance ranking should help users identify useful resources without creating the impression that ranking determines scientific validity.

A highly ranked dataset is not necessarily the highest-quality dataset or the most suitable resource for every research question.

The application should distinguish search relevance from data quality, scientific authority and analytical compatibility.

## 4.1.9 Search History and Discovery Continuity

### Core Requirements

- Allow users to revisit previous searches where appropriate.
- Preserve useful search terms and refinement criteria.
- Allow users to repeat or modify previous searches.
- Support continuity when users move between related searches.
- Allow relevant discoveries to be retained or associated with research projects through the appropriate project-management functionality.
- Avoid automatically adding discovered resources to projects or permanently retaining datasets without user authorization.
- Respect user preferences regarding search-history retention and privacy.

### Design Guidance

Scientific discovery is often iterative. Users may return to earlier searches, compare different search criteria or investigate related subjects over an extended period.

Preserving useful search context can reduce repetitive work and support continuity between research sessions.

Search history should remain distinct from saved datasets, project materials and formal research records.

## 4.1.10 Search Availability and Source Transparency

### Core Requirements

- Communicate which external sources are available to a search.
- Distinguish successful searches from sources that could not be reached or queried.
- Identify partial search results when some sources are unavailable.
- Communicate relevant access restrictions, authentication requirements and service limitations.
- Avoid implying that a search covered all possible astronomical resources when only a subset was queried.
- Preserve enough information to identify the sources that contributed results.
- Allow users to investigate alternative sources when a preferred provider is unavailable.
- Maintain a record of supported discovery sources and their integration status.

### Design Guidance

Unified discovery depends on external services that may have different availability, query capabilities, access requirements and maintenance conditions.

A search that returns no results does not necessarily establish that no relevant data exists.

The application should communicate whether the result reflects an unsuccessful search, an unavailable provider, a restricted resource or a genuine absence of matching records within the sources searched.

## General Principles

The data discovery and search environment should:

- Provide an integrated entry point for finding astronomical data and scientific resources.
- Support distinct object-focused and research-focused searches.
- Allow users to begin with simple searches and progressively refine their results.
- Accommodate different levels of scientific and technical knowledge.
- Preserve the identity and context of individual search results.
- Distinguish search relevance from scientific quality and analytical compatibility.
- Communicate ambiguity, limitations and source availability.
- Preserve useful search context without automatically retaining or importing discovered data.
- Remain extensible as additional scientific resources become available.

## General Principle

Scientific data discovery should make it easier for users to find relevant information without requiring them to understand the organization of every external archive, database or scientific resource.

The application should provide a unified discovery experience while preserving the distinctions, context and limitations necessary for responsible scientific research.
